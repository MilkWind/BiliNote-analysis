## 2. Number 静态方法：类型检查 *Content-[00:45]
`Number` 对象上的静态方法主要用于严格的数据类型检查。

### 2.1 Number.isInteger()
该方法用于判断一个值是否为整数。
- **底层机制**：在 JavaScript 中，`1` 和 `1.0` 的底层是同一个值，因此对它们使用该方法都会返回 `true`。
- **严格类型检查**：`Number.isInteger()` 非常严格，**不会进行隐式类型转换**。即使字符串 `"1"` 看起来像个整数，但由于其本质是字符串类型，该方法会直接返回 `false`。

### 2.2 Number.isNaN()
这是前端面试的高频考点，需要对比新旧方法的区别：
- **旧版全局 `isNaN()` 的缺陷**：全局函数在判断前，会先尝试将参数转换成数字。例如传入字符串 `"hello"`，转换数字失败后会变成 `NaN`，从而导致全局 `isNaN("hello")` 误报返回 `true`。
- **新版 `Number.isNaN()` 的优势**：挂载在 `Number` 对象上，**不会做类型转换**。只有当参数真正是 `NaN` 这个特殊值时，才会返回 `true`。
- **最佳实践**：建议在当前版本的开发中，全面使用 `Number.isNaN()` 去替代之前的全局版本，以避免误判。

## 3. 核心概念：安全整数与精度丢失 *Content-[02:36]
在处理后端返回的大 ID 时，“安全整数”是一个极其重要的核心概念。

- **底层存储限制**：JavaScript 使用双精度浮点数（IEEE 754 标准）存储所有的数字，这导致它能够精确表示的整数范围是有限的。
- **安全整数上限**：整数的安全上限是 `Number.MAX_SAFE_INTEGER`，其值为 $2^{53} - 1$（大约是 9000 万亿，即 `9007199254740991`）。在这个范围内，整数是安全的。
- **精度丢失现象**：一旦超过这个范围，就会发生可怕的精度丢失。
  - **相等误判**：`9007199254740992` 和 `9007199254740993` 这两个完全不同的数字，在 JavaScript 中竟然会被判定为相等。
  - **运算异常**：在进行加法运算时，`+1` 没有任何反应，而 `+2` 会直接跳过中间值。这是因为底层的尾数位不够用了。
- **业务影响**：如果业务涉及到高精度的金融计算，或者是数据库大整数 ID 等场景，这种精度丢失错误是致命的。

## 4. 应对大数值与精度丢失的方案 *Content-[04:04]
既然存在精度丢失的风险，JavaScript 提供了以下两种主要应对方案：

### 4.1 使用 Number.isSafeInteger() 进行检测
- 在进行关键运算或接收外部数据时，可以使用 `Number.isSafeInteger()` 来检测数值是否在安全范围内。
- 只要该方法返回 `false`，就意味着这个数值可能已经失去了精度，或者它根本就不是一个整数，此时需要触发警告或采取其他处理逻辑。

### 4.2 使用 BigInt 类型
- 如果业务需求确实需要处理超出安全范围的整数，必须放弃 `Number` 类型，转而使用 `BigInt`。
- **使用方法**：在数字后面加上字母 `n`（例如 `9007199254740992n`）。
- **优势**：`BigInt` 能够进行任意精度的整数运算，从根本上解决大数值精度丢失的问题。

## 5. 其他 Number 静态方法 *Content-[05:08]
除了上述方法，`Number` 对象上还有其他几个常用的静态方法：

### 5.1 Number.isFinite()
- 用于检测一个值是否是有限的（即不是无穷大，也不是 `NaN`）。
- 如果是无穷大或者 `NaN`，该方法都会返回 `false`。
- 同样属于严格类型检查，不会接收字符串进行隐式转换。

### 5.2 Number.parseInt() 与 Number.parseFloat()
- **历史背景**：在 ES6 之前，`parseInt` 和 `parseFloat` 是挂载在全局对象上的方法。
- **ES6 规范化**：为了语言的规范性，ES6 将这两个全局方法搬到了 `Number` 对象上。
- **功能与优势**：它们的功能与全局版本完全一样。但是使用 `Number.parseInt()` 这种写法，使得代码的命名空间更加清晰，也更加符合 JavaScript 模块化的设计规范。
