## Symbol 替代常量的实战场景 *Content-[00:00]
在前端开发中，我们经常需要定义一组常量来表示不同的业务类型（如文件类型、状态类型等）。其核心目标是**保证常量值的唯一性**，从而避免业务逻辑出错。
- **传统痛点**：在 ES5 中，通常使用字符串或数字来定义常量。这种方式极易出现值重复或拼写错误的问题。
- **现代解决方案**：使用 `Symbol` 来定义常量，可以保证每个常量值都是绝对唯一的。即使两个常量的描述（description）完全相同，它们在内存中也不会发生冲突。

## ES5 常量定义的痛点与错误示例 *Content-[00:34]
为了直观展示传统字符串常量的缺陷，视频演示了一个极易踩坑的业务场景。

### 1. 错误场景复现
假设我们需要定义一组文件类型常量，并编写一个处理文件的函数：
```javascript
// 使用字符串定义常量
const TYPE_AUDIO = 'audio';
const TYPE_VIDEO = 'video';
const TYPE_IMAGE = 'image'; 

function handleFile(type) {
  switch (type) {
    case TYPE_AUDIO:
      console.log('处理音频文件');
      break;
    case TYPE_VIDEO:
      console.log('处理视频文件');
      break;
    case TYPE_IMAGE:
      console.log('处理图片文件');
      break;
  }
}
```

### 2. 潜在的 Bug
如果在定义常量时，开发者不小心发生了拼写错误或复制粘贴错误，例如将 `TYPE_IMAGE` 的值也写成了 `'audio'`：
```javascript
const TYPE_AUDIO = 'audio';
const TYPE_IMAGE = 'audio'; // 不小心写错，导致值重复
```
此时，如果调用 `handleFile(TYPE_IMAGE)`，由于 `TYPE_IMAGE` 的实际值已经是 `'audio'`，`switch` 语句会错误地匹配到第一个 `case`，导致**本应处理图片，却执行了处理音频的逻辑**。
- **根本原因**：字符串作为常量值时，只要字面量相同，它们的值就相等，语言层面无法防止人为的重复赋值或拼写错误。

## 使用 Symbol 解决常量冲突问题 *Content-[04:40]
为了解决上述常量值重复导致的逻辑错误，我们可以将常量的值从字符串替换为 `Symbol`。

### 1. Symbol 解决方案
```javascript
// 使用 Symbol 定义常量
const TYPE_AUDIO = Symbol('audio');
const TYPE_VIDEO = Symbol('video');
const TYPE_IMAGE = Symbol('image'); // 即使这里不小心写成了 Symbol('audio') 也没关系
```

### 2. 唯一性保证
- `Symbol` 的核心特性是：每次调用 `Symbol()` 都会返回一个全新的、唯一的值。
- 即使在定义时，开发者不小心将 `TYPE_IMAGE` 的描述也写成了 `'audio'`（即 `Symbol('audio')`），由于 `Symbol` 的唯一性，`TYPE_AUDIO` 和 `TYPE_IMAGE` 在内存中依然是两个完全不同的引用。
- 它们的值**不相等**（`!==`），因此 `switch` 语句能够精准匹配到正确的 `case`，完美避免了因常量值重复导致的业务逻辑出错。

## Symbol 在状态管理中的规范约束作用 *Content-[07:25]
除了防止拼写错误，`Symbol` 在状态管理中还能起到**强制规范代码**的作用，避免开发者绕过常量定义。

### 1. 场景描述
定义一个状态对象（如 `status`），包含 `pending`（处理中）和 `success`（成功）等状态，并使用 `Symbol` 进行初始化：
```javascript
const status = {
  pending: Symbol('pending'),
  success: Symbol('success')
};

function processStatus(state) {
  switch (state) {
    case status.pending:
      console.log('处理中');
      break;
    case status.success:
      console.log('成功');
      break;
  }
}
```

### 2. 字符串方式的隐患
如果上述状态对象使用的是普通字符串（如 `pending: 'pending'`），开发者在调用函数时，可能会为了图方便，绕过 `status` 对象，直接硬编码传入字符串：
```javascript
// 不规范的做法：直接传入硬编码字符串
processStatus('success'); 
```
- 虽然直接传入 `'success'` 也能匹配成功，但这**破坏了代码规范**。
- **更严重的风险**：如果开发者随意编造一个未定义的状态字符串（如直接传入 `'fail'`），由于没有值的严格约束，可能会导致未预期的逻辑分支或静默失败。

### 3. Symbol 的优势
- 使用 `Symbol` 可以强制开发者必须引用预先定义好的常量对象（如 `status.success`）。
- 因为 `Symbol` 是唯一的，如果开发者直接传入一个硬编码的 `Symbol('fail')`，它无法与对象中定义的 `Symbol` 匹配，从而在运行时就暴露出这种“瞎编”状态的不规范行为。
- 这种机制保证了业务逻辑的严谨性，确保所有状态流转都严格遵循预先定义的规范。
