## 场景一：多个元素添加相同事件处理程序 *Content-[00:11]

- **传统实现方式**
  - 当多个 DOM 元素（例如 100 个 `li`）需要添加相同的事件处理程序时，常规思路是通过循环遍历所有元素，逐个绑定事件。
  - 代码实现思路：使用 `document.getElementsByTagName('li')` 获取所有 `li` 元素，然后通过 `for` 循环为每一个 `li` 绑定 `click` 事件。

- **传统方式的性能缺陷**
  - **DOM 交互与重绘重排**：给元素绑定的 `click` 事件处理程序数量直接关系到页面的整体运行性能。事件需要不断与 DOM 节点进行交互，访问 DOM 次数越多，引起浏览器**重绘（Repaint）** 与**重排（Reflow）** 的次数就越多，从而延长整个页面的交互就绪时间。
    - *重绘（Repaint）*：当元素样式改变时，浏览器会根据元素的新样式重新绘制元素的外观（相当于换了一身衣服，身高体重不变）。
    - *重排（Reflow）*：当文档的一部分发生变化（例如元素的尺寸改变），浏览器会重新创建 DOM 树。（注：重绘和重排也是 CSS 领域的高频面试题）。
  - **内存占用过大**：在循环中创建的匿名函数虽然代码看起来一模一样，但在内存中并不是同一个函数。每个函数都会独立占用内存空间，函数越多，内存占用率越大。例如 100 个 `li` 就会占用 100 个内存空间，若数量达到 1000 或 10000，将导致严重的内存和性能问题。

## 事件委托的实现与优势 *Content-[06:29]

- **基本实现思路**
  - 使用事件委托时，不再将事件直接绑定给每个子元素 `li`，而是绑定给它们的共同父元素（如 `ul`）。
  - 代码实现思路：获取父元素 `ul`（如 `document.getElementById('ul')`），直接给 `ul` 绑定 `click` 事件。

- **工作原理**
  - 利用**事件冒泡**原理：当子元素 `li` 被点击时，事件会向上冒泡到父元素 `ul`，从而触发绑定在 `ul` 上的事件处理程序。

- **核心优势**
  - 只需要绑定一次事件，使用一个函数，大大节省了内存空间，降低了内存占用率，提升了页面性能。

## 事件委托的优化：精确控制触发元素 *Content-[09:21]

- **事件委托带来的新问题**
  - 当把事件处理程序改给父元素 `ul` 后，处理程序会对容器内**任意位置**的事件做出反应。
  - 例如：如果点击了 `ul` 内部的空白区域（非 `li` 区域），事件依然会被触发。虽然这种额外操作通常可忽略不计，但对性能而言仍是一种损害，因此需要解决“误触发”的问题，让不该触发的地方不触发。

- **解决方案：利用事件源（target）**
  - **思路**：只让点击 `li` 时触发事件，点击其他区域不触发。
  - **实现**：事件对象中提供了一个 `target` 属性，它可以返回事件的目标节点（即事件源，具体点击了哪个 DOM 节点）。
  - 通过 `event.target.nodeName` 获取具体的标签名称（注意：该属性返回的是大写字符串，如 `'LI'`），然后进行条件判断。

- **代码逻辑**
  - 在 `ul` 的点击事件回调中，获取事件对象 `e`。
  - 判断 `e.target.nodeName === 'LI'`。
  - 如果条件成立，则执行具体逻辑（例如 `alert(e.target.innerHTML)` 弹出当前内容）。
  - 这样修改后，只有点击 `li` 才会触发事件，点击 `ul` 空白区域则不会触发，完美解决了误触发问题。

## 总结：事件委托与性能优化 *Content-[14:13]

- 事件委托将事件绑定在父元素上，每次操作只执行一次事件处理函数。
- 大大减少了 DOM 的交互次数，使得性能得到大幅提升。
- **核心思想**：减少 DOM 操作是前端性能优化的主要思想之一。使用事件委托只需给父元素绑定一次事件，有效减少了与 DOM 的交互次数，从而显著提高页面整体性能。
