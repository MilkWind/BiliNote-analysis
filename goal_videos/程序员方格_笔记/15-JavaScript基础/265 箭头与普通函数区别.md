## 箭头函数不能使用 new 实例化的原因 *Content-[02:11]
箭头函数不能使用 `new` 实例化是两者最大的区别之一，主要原因包含以下三点：

### 1\. 缺失 prototype 属性 *Content-[03:04]
- **普通函数的实例化过程**：当使用 `new` 调用普通函数（构造函数）时，会创建一个新对象，并将该新对象的原型（`__proto__`）指向构造函数的 `prototype` 属性。
- **指向 `prototype` 的作用**：
  1. 表明该实例化对象是由该构造函数诞生和延伸出来的。
  2. 使实例化对象能够继承并使用原型链上添加的属性和方法。
- **箭头函数的缺陷**：箭头函数缺失 `prototype` 属性。如果在 `new` 操作时无法为其创建原型链，JavaScript 引擎会直接报错，提示“箭头函数不是一个构造函数”，因为其原型链不完整。

### 2\. 缺失 [[Construct]] 内部方法 *Content-[06:50]
- **内部方法要求**：JavaScript 引擎要求构造函数必须实现 `[[Construct]]` 内部方法，用于在 `new` 调用时初始化实例。
- **箭头函数的机制**：箭头函数内部只有 `[[Call]]` 方法，没有 `[[Construct]]` 方法。当尝试使用 `new` 实例化时，引擎检测到缺少该方法，会直接抛出错误。

### 3\. 违背设计初衷与 this 指向混乱 *Content-[08:02]
- **设计初衷**：箭头函数的设计目标是为了解决普通函数在回调中 `this` 动态绑定导致丢失的问题。箭头函数中的 `this` 是静态继承自外部上下文的。
- **矛盾点**：如果允许箭头函数使用 `new` 创建实例，`this` 就会自动指向新创建的实例化对象。这与箭头函数期望 `this` 从外部上下文继承下来的设计逻辑相矛盾，会导致 `this` 指向混乱。因此，从设计逻辑上必须排除其作为构造函数的能力。

## 箭头函数的其他局限性 *Content-[11:01]
箭头函数实际上是一个“浓缩版”的函数，为了简化表达式和解决 `this` 绑定问题，它牺牲了许多普通函数具备的能力：
- **不能复写 `this`**：箭头函数的 `this` 在定义时就已经确定（继承自外部上下文），无法通过 `call`、`apply` 或 `bind` 方法来修改。
- **不支持 `new.target`**：无法使用 `new.target` 等与构造函数相关的特性。
- **不能作为生成器函数**：不支持 `function*` 语法，不能包含 `yield` 关键字，因此不能作为生成器（Generator）函数使用。

## 箭头函数与普通函数完整特性对比 *Content-[12:45]
| 特性 | 普通函数 | 箭头函数 |
| :--- | :--- | :--- |
| **`this` 指向** | 动态绑定（取决于调用方式） | 静态继承（继承自定义时的外部上下文） |
| **`prototype` 属性** | 有 | 无 |
| **构造函数能力** | 可配合 `new` 生成实例 | 不能调用 `new` 生成实例 |
| **`arguments` 对象** | 存在，可调用获取参数 | 不存在（需使用 rest 参数 `...args` 替代） |
| **`super` 关键字** | 可用 | 不可用 |
| **生成器（Generator）**| 支持（可使用 `function*`） | 不支持 |
| **异步（Async）** | 支持（可使用 `async` 修饰） | 支持（可使用 `async` 修饰） |

## AI 总结
箭头函数与普通函数的核心差异源于它们的设计初衷不同。普通函数功能全面，支持原型链、`this` 动态绑定以及作为构造函数实例化；而箭头函数是为了简化函数表达式并彻底解决回调函数中 `this` 指向丢失的问题而设计的“浓缩版”。为了保持 `this` 的静态词法作用域，箭头函数牺牲了 `prototype` 属性、`[[Construct]]` 内部方法、`arguments` 对象以及生成器语法等能力，因此绝对不能使用 `new` 关键字进行实例化。在面试中，从底层原理和设计初衷两个维度进行解答，能够展现出对 JavaScript 核心机制的深刻理解。
