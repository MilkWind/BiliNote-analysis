## 原型概念的引入背景 *Content-[00:01]
- **问题痛点**：在构造函数内部创建过多的对象方法，会导致每次实例化对象时都重新创建一份方法，造成内存资源的严重浪费。
- **解决思路**：为了解决这个问题，需要一个“公共空间”。这个公共空间必须与构造函数相互绑定，并供所有由该构造函数创建的实例对象共享。
- **共享的唯一性**：提到“共享”就意味着资源有限或独一份。在 JavaScript 的机制中，这个供所有对象共享的公共空间必须是唯一的。

## 系统自带方法的来源与原型对象的诞生 *Content-[01:43]
- **现象观察**：通过代码示例 `let p = new Person()` 创建实例对象 `p`。即使没有手动为 `p` 编写任何方法，`p` 依然可以调用系统自带的方法（如 `toString` 等），且不会报错。
- **核心疑问**：系统是如何悄无声息地为构造函数创建的对象绑定这些自带方法的？这必须符合 JavaScript 的代码逻辑规则。
- **概念引出**：为了解答这个问题，正式引入“原型（Prototype）”的概念。每创建一个构造函数，系统就会自动为其绑定一个神秘且强大的对象，这个对象就是原型对象。

## 原型对象的作用与“爹妈”比喻 *Content-[04:10]
- **核心作用**：原型对象是所有由该构造函数 `new` 出来的实例对象的公有空间。
- **形象比喻（爹妈与孩子）**：
  - **构造函数** = 爹
  - **原型对象** = 妈（系统自动分配并绑定，无需“自由恋爱”，只要构造函数诞生，就自动绑定一个原型）
  - **实例对象** = 孩子
- **共享机制**：一个构造函数可以创建出无数个实例对象（无数个孩子），这些孩子都共享同一个原型对象（同一对爹妈）。爹有爹的作用，妈有妈的作用，原型对象就充当了孩子们共享的“妈”的角色。

## 访问原型对象与原型三角关系 *Content-[07:11]
- **访问方式**：通过 `构造函数.prototype` 来访问原型对象。例如：`Person.prototype`。
- **初始状态**：直接打印 `Person.prototype` 会输出一个空对象 `{}`。系统只负责提供公共空间，具体在里面存放什么属性和方法，完全由开发者自己决定。
- **原型的本质**：原型本身就是一个对象，因此可以为其绑定属性和方法。在原型中绑定的属性和方法，会被当前构造函数 `new` 出来的所有对象所共有。
- **原型三角关系**：
  - **构造函数 与 原型对象**：绑定关系（通过 `prototype` 属性连接）。
  - **构造函数 与 实例对象**：`new` 的关系。
  - **实例对象 与 原型对象**：公共关系（实例对象可以直接访问原型对象中的共有内容）。
- **生活映射**：就像小时候孩子找妈妈要东西（访问原型方法），如果爸爸（构造函数）不知道，就会说“去找你妈”，这正是原型机制的生动体现。

## 原型方法的绑定与代码实践 *Content-[10:47]
- **绑定方法**：将方法直接绑定到原型对象上，而不是写在构造函数内部，从而避免每次实例化都创建新函数。
  ```javascript
  Person.prototype.sayHi = function() {
      console.log('你好');
  };
  Person.prototype.eat = function() {
      console.log('吃吃吃');
  };
  ```
- **实例调用**：创建多个实例对象（如 `p1`, `p2`），它们都可以成功调用绑定在原型上的 `sayHi` 和 `eat` 方法。
- **优势总结**：
  - **无全局污染**：方法绑定在原型对象上，并没有在全局作用域创建变量。
  - **解决资源浪费**：所有实例对象共享同一份方法代码，完美解决了构造函数内部创建过多方法导致的内存浪费问题。

## 原型中 this 指向的思考与总结 *Content-[13:50]
- **抛出问题**：如果在原型对象的方法中使用 `this.name`（例如 `console.log(this.name)`），能否正确获取到当前调用该方法的实例对象的 `name` 属性？
- **思考点**：虽然函数是定义并绑定在原型对象上的，但当通过具体的实例对象（如 `p1.sayHi()`）去调用时，`this` 的指向究竟是指向原型对象，还是指向调用它的实例对象？（此问题留作思考，用于引出后续关于 `this` 指向和原型链的深度解析）。
