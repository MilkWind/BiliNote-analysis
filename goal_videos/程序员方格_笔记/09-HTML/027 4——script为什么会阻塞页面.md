## 1. 核心概念：什么是“阻塞” *Content-[00:19]
- **常见误区**：很多人在面试时回答“因为JS慢”或“需要等下载”，这虽然描述了现象，但并没有触及核心本质。
- **准确定义**：`<script>` 阻塞页面，指的并不是页面打不开或白屏时间更久，而是 **HTML的解析过程会停下来**。
- **具体表现**：浏览器从上到下读取HTML时，遇到 `<script>` 标签会暂停，不再往下解析后面的标签。只有等该脚本的下载和执行流程全部走完，才会继续向下解析。
- **核心结论**：**阻塞 = 停止解析**，而非单纯的渲染慢。

## 2. HTML解析机制与DOM树的构建 *Content-[01:16]
- **流式解析（Streaming）**：浏览器不是拿到整个HTML文件再统一处理，而是“一边读、一边解析、一边构建”。
- **解析过程**：解析器拿到HTML字节流 -> 读一段 -> 解析成 Token -> 生成节点 -> 拼接到 DOM 树上 -> 继续读下一段。
- **关键伏笔**：DOM 树不是瞬间生成的，而是一个**逐步生长**的过程。如果在生长到一半时遇到 JS，就会引发后续的结构冲突问题。

## 3. 核心原因一：JavaScript对DOM的“破坏力” *Content-[01:56]
- **JS不是被动资源**：与图片、CSS不同，JS不是被动等待加载的资源，它最常做的事情是**直接读写 DOM**。
- **代码示例说明**：
  - HTML中有一个 `<div id="app">`，后面跟着 `<script src="main.js">`，再后面是 `<footer>`。
  - 在 `main.js` 中，通过 `document.querySelector('#app')` 获取节点，并使用 `innerHTML` 修改其内容（如插入 `<span>inner app</span>`）。
- **破坏力分析**：
  - 如果 JS 在 HTML 未解析完时执行，它可以修改已经解析出来的“半成品” DOM。
  - 如果浏览器不暂停，继续解析出 `<footer>`，此时 JS 回头删除、移动或替换了上面的节点，会导致 **DOM 树结构变得不可预测**。
  - 解析器刚拼好的结构可能瞬间被脚本改写，导致解析和脚本修改“互相打架”。
- **结论**：为了保证解析顺序和脚本修改之间不冲突，浏览器必须等待 JS 执行完毕。

## 4. 核心原因二：脚本执行顺序与上下文一致性 *Content-[04:28]
- **依赖后续 DOM**：脚本的正确执行往往依赖于它在 HTML 文本中的插入位置。
- **代码示例说明**：
  - 在 `<script>` 后放置一个 `<button id="btn">`。
  - 在 JS 中尝试获取该按钮并绑定 `click` 事件。如果脚本在按钮之前，会报错（获取不到节点）；将脚本移到按钮之后，事件才能正确绑定并输出 log。
- **语义一致性**：
  - 开发者将脚本写在特定位置，意味着希望它在该上下文环境中执行。
  - 浏览器必须尊重这种顺序表达，不能跳过去先解析后面，再回头补发执行，否则会破坏脚本执行时的**上下文一致性**。

## 5. 阻塞的本质与浏览器处理流程 *Content-[06:06]
- **核心顾虑**：浏览器不知道 `<script>` 会做什么，但必须保证 DOM 构建是确定的，且脚本执行顺序符合开发者的书写顺序。
- **阻塞本质**：**保证 DOM 构建的确定性** 与 **脚本执行顺序的一致性**。
- **遇到 `<script>` 时浏览器的具体动作**：
  1. 暂停 HTML 的解析。
  2. 如果是外链脚本，发起网络下载。
  3. 脚本下载完成后，立即执行。
  4. 执行结束后，继续向下解析 HTML。
- **阻塞的两个阶段**：**下载阶段** 和 **执行阶段**，这两个阶段都会让解析器停住。

## 6. 对比分析：JavaScript与CSS的阻塞差异 *Content-[06:42]
- **CSS 不阻塞 HTML 解析**：
  - CSS 不会像 JS 一样主动修改 DOM 结构，因此浏览器可以放心继续往下构建 DOM。
- **CSS 阻塞首次渲染（First Paint）**：
  - 虽然 DOM 可以继续生成，但在首次绘制前，浏览器需要拿到关键的 **CSSOM**（CSS对象模型）才能计算出正确样式。
  - 如果缺少 CSSOM 强行渲染，会导致页面闪烁、重排等问题。
- **一句话总结**：**JavaScript 阻塞的是解析，而 CSS 阻塞的是首次绘制。**

## 7. 历史原因：为什么默认阻塞而非异步？ *Content-[07:27]
- **兼容性考量**：早期网页的大量脚本依赖于 `document.write`、依赖严格的执行顺序、依赖同步注入 DOM 节点。
- **避免崩溃**：如果浏览器默认异步执行，早期的网页会大规模崩溃。
- **保守策略**：默认同步执行（阻塞）是最保守、最确定的策略。开发者写的顺序就是执行顺序，浏览器不需要去“猜”。
- **结论**：默认阻塞不是因为浏览器笨，而是为了**正确性与兼容性**。

## 8. 面试高分回答模板 *Content-[08:06]
- **标准回答参考**：
  > “`<script>` 会阻塞页面的原因是：浏览器在解析 HTML 的过程中，必须保证 DOM 构建的正确性，以及脚本执行顺序的语义一致性。JavaScript 可能读取或修改当前 DOM，甚至影响后续解析的结果。所以解析器遇到 `<script>` 会暂停，等待脚本下载并执行完成之后，再继续解析。”

本视频深入剖析了前端面试中的高频问题“为什么 `<script>` 会阻塞页面”。核心观点指出，阻塞的本质并非单纯的渲染慢，而是浏览器为了保证 **DOM 构建的确定性** 与 **脚本执行顺序的一致性**，必须暂停 HTML 解析。由于 JavaScript 具有直接读写 DOM 的“破坏力”，且其执行高度依赖上下文位置，浏览器只能采取同步等待的策略。此外，视频还对比了 CSS 仅阻塞首次绘制而不阻塞解析的特性，并从历史兼容性角度解释了默认阻塞机制的合理性。最后提供了标准的面试回答模板，帮助求职者清晰、专业地应对此类问题。
