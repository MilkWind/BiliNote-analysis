## 1. 核心概念：流式解析 *Content-[00:18]
- **流式解析**：现代浏览器解析 HTML 的核心特点是“流式解析”，即**边下载边解析，边解析边建树**。
- **工作机制**：HTML 文件从网络传输时是一段一段的字节流，浏览器拿到一段就开始处理，而不是等整个文件下载完毕才开始渲染。
- **纠正误区**：HTML 不是“从上到下解析”的简单程序，而是一份描述文档。HTML 解析器读到一个标签，就会创建节点。这就像看书时“边看边做笔记”，而不是看完再做。
- **重要性**：流式解析直接决定了首屏加载速度、资源提前请求的时机、脚本卡住页面的原因，以及 JS 获取 DOM 节点的时序问题。这些高频面试题背后的共同起点，都是 HTML 被逐行解析。

## 2. 浏览器解析 HTML 的流水线过程 *Content-[02:24]
浏览器内部解析 HTML 经历了一个典型的流水线过程，将网络数据逐步转化为页面结构：
1\. **字节流到字符流**：网络传输的是字节（Bytes），浏览器根据编码（如 UTF-8）将其解码为字符。
2\. **字符流到 Token**：浏览器的 Tokenizer 将字符流识别为一个个 Token。例如 `<div>` 是开始标签 Token，`hello` 是文本 Token，`</div>` 是结束标签 Token。
3\. **Token 到 DOM 节点**：浏览器的 Tree Builder 根据 Token 的顺序和 HTML 规则，逐步构建出 DOM 树。

- **核心认知**：DOM 树不是一瞬间生成的，而是**持续生长**的。浏览器每拿到一点字符就能吐出 Token，进而生长出 DOM 节点。
- **三个关键词**：**流式**、**顺序**、**增量**。

## 3. 代码示例：逐行解析与 DOM 树的生长 *Content-[03:54]
通过标准 HTML 结构演示 DOM 树的机械生长过程：
- 读到 `<!DOCTYPE html>`：确定渲染模式。
- 读到 `<html>`：创建 `html` 节点，挂在 `document` 下。
- 读到 `<head>`：创建 `head` 节点，成为 `html` 的子节点。
- 读到 `<title>` 及文本：创建 `title` 节点挂在 `head` 下，内部创建文本节点。
- 读到 `<body>` 和 `<div id="app">`：依次创建节点，并为 `div` 设置 `id="app"` 属性。
- 读到文本 `hello`：在 `div` 内创建文本节点。
- 读到闭合标签：依次闭合 `div`、`body`、`html`。

- **结论**：DOM 生长过程非常机械且确定。解析器严格将 Token 转为节点，因此可以解释为何在 `head` 中无法访问 `body` 里还未解析到的 DOM 节点（因为那部分 Token 还没有解析到，自然不会构建节点）。

## 4. 解析过程中的外部资源处理 *Content-[06:16]
- **CSS 与 Image 资源**：当解析器在 `head` 中读到 `<link>` 引入 CSS，或在 `body` 中读到 `<img>` 标签时，不会等待整个 HTML 解析结束，而是立刻将资源交给网络层请求。
- **性能意义**：CSS 往往会影响渲染，尽早请求能尽早完成布局与绘制。
- **Preload Scanner（预加载扫描器）**：HTML 解析器负责发现资源并触发请求。浏览器内部的 Preload Scanner 机制会尽量提前扫描并预加载关键资源，使得“边解析边请求”成为可能，从而大幅提升页面加载性能。

## 5. Script 标签的特殊性与阻塞问题 *Content-[07:18]
- **Script 的危险性**：与 CSS 等静态资源不同，`<script>` 不仅仅是资源，它是会执行的代码。
- **脚本执行的影响**：
  1\. 可能读写 DOM（如使用 `querySelector` 或 `getElementById`）。
  2\. 可能改变解析流程（如使用 `document.write` 插入新 HTML，解析器必须将插入的内容也解析掉）。
- **同步点与阻塞**：为了保证脚本执行时 DOM 处于确定的状态（否则脚本读到的结构可能是错的），解析器会在 `<script>` 处暂停，等待脚本加载并执行完毕后再继续往下解析。因此，`<script>` 被视为解析过程中的**同步点**。
- **面试题解析**：
  - **现象**：在 `head` 中用 JS 获取 `body` 里的 `#app` 节点结果为 `null`，而将脚本放在 `body` 末尾则能正确获取到 DOM 节点。
  - **原因**：在 `head` 中执行脚本时，解析器只解析到了 `head`，`body` 里的 `div` 还未出现，DOM 树还没生长到该节点。放在 `body` 末尾时，前面的 DOM 已经构建完毕，因此可以正常获取。

## 6. 面试总结与回答模型 *Content-[09:26]
在面试中，可以通过以下 5 句核心模型来复述浏览器解析 HTML 的过程，展现对底层原理的深刻理解：
1\. 浏览器对 HTML 是**流式解析**的，不是下载完一次处理。
2\. 大体流程是：Bytes 解码成字符，字符转 Token，Token 逐步构建成 DOM。
3\. DOM 是**增量构建**的，资源请求可以提前发出。
4\. `<script>` 因为可以读写 DOM，会成为解析过程中的**同步点**，导致阻塞或者时序的差异。
5\. 因此，`head` 中的脚本拿不到 `body` 后面的节点，而 `body` 末尾的脚本可以拿到。
