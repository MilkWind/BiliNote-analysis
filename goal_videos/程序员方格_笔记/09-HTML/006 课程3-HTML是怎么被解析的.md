## 1. 核心视角：HTML的流式解析 *Content-[00:18]
- **视角转换**：在前端面试中，我们不是在单纯学习如何写页面，也不是向面试官解释为什么这么写页面，而是要展示**浏览器是如何理解我们写的代码的**。
- **常见误区**：很多人直觉上认为，浏览器需要把整个 HTML 文件下载完之后，才开始生成和渲染页面。
- **真实机制**：现代浏览器解析 HTML 的核心特点是**流式解析**（边下载边解析，边解析边建树）。
  - HTML 文件从网络传输过来是一段一段的字节流。
  - 浏览器拿到一段就开始处理这一段，而不是等到全部结束。
- **流式解析的重要性**：
  - 决定了首屏为什么能那么快出现。
  - 决定了某些资源为什么会被提前请求。
  - 决定了某些脚本为什么会卡住页面。
  - 决定了在 JS 中有时能拿到前面的 DOM，却拿不到后面的 DOM。
  - 这些面试题背后共同的起点都是：HTML 是被逐行解析的。

## 2. HTML解析的本质与流水线过程 *Content-[01:48]
- **解析本质**：
  - HTML 本身没有“解析”这件事情，它不是一段会运行的程序，而是一份**描述文档**。
  - 更精准的表达是：HTML 解析器读到一个标签，就会创建节点。
  - 浏览器不是看完再干活，而是**一边看一边干**（就像边看书边做笔记）。
- **浏览器解析的流水线过程**：
  - **Bytes（字节流）**：网络传输的最开始是字节（Network bytes）。
  - **Characters（字符流）**：浏览器根据编码（如 UTF-8）将字节解码成字符。
  - **Token 化**：浏览器的 Tokenizer 会把字符流识别成一个个 Token（如 `<div>` 是开始标签 Token，`hello` 是文本 Token，`</div>` 是结束标签 Token）。
  - **构建 DOM 树**：浏览器的 Tree Builder 会根据 Token 的顺序和 HTML 规则，逐渐构建出 DOM 树。
- **关键特性**：
  - 这不是一次性的转换，而是一个循环、流式的分析过程。
  - 浏览器每拿到一点字符就能吐出一点 Token，吐出 Token 就能生长出一些 DOM 节点。
  - DOM 是边造边完善的，**DOM 树不是一瞬间生成，而是持续生长**。
  - 核心记忆关键词：**流式、顺序、增量**。

## 3. 代码示例：DOM树的逐行生长 *Content-[03:54]
- **基础 HTML 结构示例**：
  ```html
  <!DOCTYPE html>
  <html>
  <head>
    <title>HTML解析</title>
  </head>
  <body>
    <div id="app">hello</div>
  </body>
  </html>
  ```
- **浏览器逐行解析与 DOM 生长过程**：
  - 读到 `<!DOCTYPE html>`：确定渲染模式。
  - 读到 `<html>`：创建 HTML 节点，挂在 `document` 下面。
  - 读到 `<head>`：创建 head 节点，成为 HTML 的子标签。
  - 读到 `<title>`：创建 title 节点，挂在 head 下面。
  - 读到文本 `HTML解析`：创建文本节点，挂在 title 下面。
  - 读到 `</title>` 和 `</head>`：处理闭合标签。
  - 读到 `<body>`：创建 body 节点。
  - 读到 `<div id="app">`：创建 div 节点，并设置属性 `id="app"`。
  - 读到文本 `hello`：创建文本节点，挂在 div 下面。
  - 读到 `</div>`、`</body>`、`</html>`：依次闭合。
- **结论**：DOM 的生长过程非常机械且确定，解析器严格地把 Token 转成节点。
- **面试追问解答**：为什么在 `head` 里写一个脚本，能访问到 `body` 里还没出现的 DOM？答案是**访问不到**，因为那部分 Token 还没有解析到，自然不会创建节点。

## 4. 解析过程中的外部资源处理 *Content-[06:26]
- **遇到 CSS/Link 标签**：
  - 解析器读到引入 CSS 文件的 `<link>` 标签时，不会等整个 HTML 结束，而是立刻把资源交给网络层去请求。
  - CSS 请求可以非常早发出去，这对性能很重要，因为 CSS 影响渲染，早请求能早完成布局与绘制。
- **遇到 Image 标签**：
  - 浏览器也会尽可能早发出图片请求。
- **资源发现机制**：
  - HTML 解析器负责发现资源，发现了就会触发请求。
  - 浏览器内部有 **Preload Scanner**（预加载扫描器）机制，会尽量提前扫描并预加载关键资源。
  - 流式解析的结构天然让“边解析边请求”成为可能。
- **遇到 Script 标签（危险而特殊的角色）**：
  - 同样是外部资源，`<link>` 很顺滑，而 `<script>` 经常卡住页面。
  - 原因：`<script>` 不仅仅是资源，它是**会执行的**。
  - 脚本执行可能做两件事：
    1. 读写 DOM（如 `querySelector` 或 `getElementById`）。
    2. 改变解析流程（如使用 `document.write` 插入新 HTML，解析器必须把插入的内容也解析掉）。
  - 为了保证确定性：浏览器必须保证脚本执行时 DOM 处在一个确定的状态，否则脚本读到的结构就是错的。
  - 结果：解析器通常会在脚本处**暂停**，等脚本加载并执行结束再继续往下解析。
  - 核心概念：脚本会影响 DOM，而 DOM 正在生长，所以脚本在解析过程中会被当作**同步点**。

## 5. 高频面试题：Script标签的阻塞与DOM获取 *Content-[08:26]
- **面试场景**：
  - 在 `<head>` 里写一个脚本去选择 `#app`，结果是 `null`。
  - 把脚本放到 `<body>` 末尾，就能选到了。为什么？
- **原理分析**：
  - 当 `<head>` 中的脚本执行的那一刻，解析器可能只解析到了 `head`，`body` 里的 `div` 还没出现，DOM 树还没生长到那个节点，自然拿不到。
  - 当脚本放在 `<body>` 末尾时，前面的 DOM 已经解析并构建完成，所以可以正确获取。
- **代码演示**：
  ```html
  <head>
    <script>
      // 输出: null，因为此时 DOM 树还没生长到 body
      console.log(document.querySelector('#app')); 
    </script>
  </head>
  <body>
    <div id="app">hello</div>
    <script>
      // 输出: <div id="app">hello</div>，此时 DOM 已构建完成
      console.log(document.querySelector('#app')); 
    </script>
  </body>
  ```

## 6. 面试回答模型总结 *Content-[09:26]
在面试中，可以将 HTML 解析过程收束为以下五句话的模型，以展现对浏览器底层机制的深刻理解：
1. 浏览器对 HTML 是**流式解析**的，不是下载完一次处理。
2. 大体流程是：Bytes 解码成 Characters，Characters 转成 Token，Token 逐步构建成 DOM。
3. 因此，DOM 是**增量构建**的。
4. 资源请求可以提前发出（得益于 Preload Scanner）。
5. Script 因为可以读写 DOM，会成为解析过程中的**同步点**，导致阻塞或者时序的差异（所以 `head` 的脚本中拿不到 `body` 后面的节点，而 `body` 末尾的脚本可以拿到）。

## AI 总结 *Content-[10:09]
本节课深入剖析了浏览器解析 HTML 的底层机制，核心在于理解**流式解析**与**增量构建**的概念。浏览器并非等待 HTML 文件完全下载后才开始工作，而是通过字节流解码、Token 化、DOM 树构建的流水线实时处理。这种机制直接影响了外部资源的加载时机以及 Script 标签的阻塞行为。掌握“DOM 是持续生长的”这一核心逻辑，能够完美解释为何在 `head` 中无法获取 `body` 中的 DOM 节点等高频面试题，帮助候选人在面试中展现出扎实的前端底层基础。
