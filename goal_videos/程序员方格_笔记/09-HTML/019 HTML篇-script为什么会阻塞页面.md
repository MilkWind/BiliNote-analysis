## 引入与“阻塞”的准确定义 *Content-[00:00]
- **澄清常见误区**：在面试中，很多人回答“因为 JS 慢”或“因为要等下载”，这些说法虽然没有完全错误，但并没有触及核心本质。
- **阻塞的具体含义**：`<script>` 阻塞的不是“页面打不开”或“白屏时间更久”，而是 **HTML 的解析过程会停下来**。
- **解析暂停机制**：浏览器从上到下读取 HTML，遇到 `<script>` 标签时会暂停，不再向下解析后续标签。只有等该 script 的下载和执行流程全部走完，才会继续向下解析。
- **核心结论**：**阻塞 = 停止解析**，而不是单纯的渲染慢。

## HTML的流式解析机制 *Content-[01:11]
- **流式解析（Streaming）**：HTML 的解析是流式的，浏览器不是拿到完整的 HTML 文档后再统一处理，而是边读边解析。
- **解析过程**：浏览器解析器拿到 HTML 字节流后，读一段、解析成 token、生成节点、拼接到 DOM 树上，然后继续读下一段。
- **DOM 树的生长**：DOM 树并不是瞬间生成的，而是一个**逐步生长**的过程。这也是理解 script 阻塞机制的重要伏笔。

## 核心原因一：JS对DOM结构的破坏力 *Content-[01:56]
- **代码场景示例**：
  - 创建一个 `<div id="app">`。
  - 引入本地 JS 文件 `main.js`。
  - 在 `<script>` 标签后添加文本和 `<footer>` 标签。
- **JS 的主动性**：与图片、CSS 等被动资源不同，JS 最常做的事情是**直接读写 DOM**。
- **修改 DOM 示例**：在 `main.js` 中，可以通过 `querySelector` 找到 `app` 节点，并使用 `innerHTML` 改变其内部结构（如插入 `<span>` 和文本节点）。
- **潜在风险**：
  - 如果 JS 在 HTML 还没解析完时，就把已经解析出来的 HTML 改掉，DOM 树的结构会变得**不可预测**。
  - 假设浏览器继续向下解析出了 `<footer>`，此时 JS 又回头删除、移动或替换了上面的某个节点，解析器刚拼好的结构会瞬间被脚本改写。
- **结论**：浏览器需要一个机制来保证解析顺序和脚本修改之间不会互相冲突，这就是必须等待 JS 执行的关键逻辑。

## 核心原因二：JS对DOM节点的依赖与执行顺序 *Content-[04:27]
- **代码场景示例**：
  - 在 `main.js` 中尝试获取一个 id 为 `btn` 的按钮，并绑定 `click` 事件。
  - 如果 `<script>` 放在按钮之前，浏览器会报错（无法正确绑定节点，因为此时 DOM 还未生成）。
  - 将 `<script>` 移到按钮之后，事件正确绑定，点击时控制台正常输出 `click button`。
- **依赖书写顺序**：脚本的正确执行**依赖它被插入到 HTML 文本中的位置**。
- **尊重开发者意图**：浏览器需要尊重开发者在 HTML 中的顺序表达（写在后面就意味着希望在后面发生）。
- **上下文一致性**：浏览器不能先跳过去解析后面的内容，再回头补发执行脚本，否则会破坏脚本执行时的**上下文一致性**。

## 浏览器的处理流程与阻塞本质 *Content-[05:52]
- **浏览器的核心顾虑**：浏览器不知道 script 具体会做什么，但它必须保证 DOM 构建是确定的，且脚本执行顺序符合开发者的书写顺序。
- **阻塞的本质**：浏览器要保证 **DOM 构建的确定性** 与 **脚本执行顺序的一致性**。
- **遇到 `<script>` 时的标准处理流程**：
  1\. 暂停 HTML 的解析。
  2\. 如果是外链脚本，发起下载。
  3\. 脚本下载完成后，立即执行。
  4\. 执行结束后，继续向下解析 HTML。
- **阻塞的两个阶段**：**下载** 和 **执行**，这两个阶段都会让解析器停住。

## 对比分析：JS与CSS的阻塞差异 *Content-[06:44]
- **CSS 的表现**：CSS 的加载通常**不会阻止 HTML 继续解析**。因为 CSS 不会像 JS 一样主动修改 DOM 结构，浏览器可以放心往下构建 DOM。
- **CSS 的影响**：CSS 会影响**首次渲染（First Paint）** 的时间。DOM 可以继续生成，但在首次绘制前，浏览器需要拿到关键的 CSSOM 才能计算出正确样式，否则会出现闪烁、重排等问题。
- **核心总结**：**JS 阻塞的是解析，而 CSS 阻塞的是首次绘制**。

## 历史原因：为何默认阻塞而非异步 *Content-[07:27]
- **早期网页的依赖**：早期网页上的大量脚本依赖于 `document.write`、依赖 script 的执行顺序、依赖同步注入 DOM 节点。
- **兼容性考量**：如果浏览器默认异步执行，早期的网页会大规模崩溃。为了**兼容性**，浏览器选择默认同步执行。
- **保守且确定的策略**：开发者写的顺序就是执行顺序，浏览器不用去猜。默认阻塞并不是因为浏览器“笨”，而是为了**正确性与兼容性**。
