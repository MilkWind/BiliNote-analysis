## 课程引入与核心视角：流式解析 *Content-[00:00]
- **核心视角转换**：学习HTML解析不是为了知道“怎么写页面”或“为什么这么写”，而是要理解“浏览器是怎么理解我们写的东西的”。
- **常见误区**：很多人认为浏览器是把整个HTML文件下载完之后才开始生成DOM和渲染页面。
- **真实机制：流式解析**：
  - 现代浏览器解析HTML的核心特点是**流式解析**（边下载边解析，边解析边建树）。
  - HTML文件从网络传输过来是一段一段的字节流，浏览器拿到一段就开始处理，而不是等待全部下载结束。
- **流式解析的重要性**：
  - 决定了首屏为什么能快速出现。
  - 解释了为什么某些资源会被提前请求。
  - 解释了为什么某些脚本会卡住页面。
  - 解释了为什么在JS中有时能拿到前面的DOM，却拿不到后面的DOM。
- **精准理解“解析”**：
  - HTML本身不是会运行的程序，而是一份描述文档，没有严格意义上的“运行解析”。
  - 更精准的表达是：HTML解析器读到一个标签，就会创建对应的节点。
  - 浏览器是“边看边做笔记”，而不是“看完再做”。

## 浏览器解析HTML的流水线过程 *Content-[02:24]
浏览器内部处理HTML经历了一个典型的流水线过程，将网络数据逐步转化为DOM树：

1\. **字节流 (Bytes)**：网络传输的最初形态是字节（Bytes）。
2\. **字符流 (Characters)**：浏览器根据编码（如 UTF-8）将字节解码成字符。
3\. **Token (Tokens)**：浏览器的 Tokenizer（词法分析器）将字符流识别成一个个 Token。
   - 例如：`<div>` 是一个开始标签 Token，`hello` 是一个文本 Token，`</div>` 是一个结束标签 Token。
4\. **DOM节点 (DOM Tree)**：浏览器的 Tree Builder（树构建器）根据 Token 的顺序和 HTML 规则，逐渐构建出 DOM 树。

- **关键特性**：这不是一次性的转换，而是一个循环、流式的分析过程。浏览器每拿到一点字符就能吐出一点 Token，进而生长出一些 DOM 节点。
- **三个核心关键词**：**流式**、**顺序**、**增量**。DOM 树不是一瞬间生成的，而是持续生长的。

## 逐行解析示例与DOM树的生长 *Content-[03:54]
通过一个标准的 HTML 结构示例，感受逐行解析与 DOM 树的机械生长过程：
- **代码结构**：包含 `<!DOCTYPE html>`、`<html>`、`<head>`、`<title>`、`<body>` 以及带有 `id="app"` 的 `<div>` 和文本 `hello`。
- **DOM 树的生长步骤**：
  1. 读到 `<!DOCTYPE html>`：确定渲染模式。
  2. 读到 `<html>`：创建 HTML 节点，挂在 `document` 下。
  3. 读到 `<head>`：创建 head 节点，成为 HTML 的子节点。
  4. 读到 `<title>`：创建 title 节点，挂在 head 下；接着创建文本节点挂在 title 下。
  5. 读到 `</title>` 和 `</head>`：依次闭合节点。
  6. 读到 `<body>` 和 `<div id="app">`：创建 body 和 div 节点，并为 div 设置 `id="app"` 属性。
  7. 读到 `hello`：在 div 内创建文本节点。
  8. 读到 `</div>`、`</body>`、`</html>`：依次闭合。
- **核心结论**：DOM 的生长过程非常机械且确定。解析器严格地把 Token 转成节点，而不是“聪明地理解页面”。
- **面试追问解答**：为什么在 `<head>` 里写的脚本访问不到 `<body>` 里还没出现的 DOM？因为那部分 Token 还没有被解析到，自然不会构建对应的节点。

## 解析过程中遇到外部资源的处理 *Content-[06:26]
既然是流式解析，浏览器在解析过程中遇到外部资源（如 CSS、图片）时会如何处理？
- **CSS 资源 (`<link>` 标签)**：
  - 解析器读到 `<link>` 标签时，不会等待整个文件结束，而是立刻将资源交给网络层去请求。
  - CSS 请求可以非常早地发出去，这对性能至关重要，因为 CSS 会影响渲染，早请求能早完成布局与绘制。
- **图片资源 (`<img>` 标签)**：
  - 同样，浏览器会尽可能早地发出图片请求。
- **Preload Scanner（预加载扫描器）机制**：
  - HTML 解析器负责发现资源，一旦发现就会触发请求。
  - 浏览器内部有 Preload Scanner 机制，会尽量提前扫描并预加载关键资源。
  - 流式解析的结构天然让“边解析边请求”成为可能。

## Script标签的特殊性与阻塞机制 *Content-[07:18]
同样是遇到外部资源，为什么 `<link>` 看起来很顺滑，而 `<script>` 经常会卡住页面？
- **Script 的特殊性**：
  - `<script>` 不仅仅是资源，它是**会执行**的代码。
  - 脚本一旦执行，可能会做两件事：
    1. **读写 DOM**：如使用 `querySelector` 或 `getElementById`。
    2. **改变解析流程**：如使用 `document.write` 直接插入新的 HTML，解析器必须把插入的内容也解析掉。
- **同步点机制**：
  - 为了保证脚本执行时 DOM 处于一个确定的状态（否则脚本读到的结构可能是错的），解析器通常会在 `<script>` 处**暂停**。
  - 等待脚本加载并执行结束后，再继续往下解析。
  - 因此，脚本在解析过程中会被当作**同步点**，导致阻塞或时序差异。
- **高频面试题解析**：
  - **现象**：在 `<head>` 中写脚本获取 `#app` 节点结果为 `null`；将脚本放到 `<body>` 末尾就能正确获取到。
  - **原因**：当 `<head>` 中的脚本执行时，解析器只解析到了 `<head>`，`<body>` 里的 `<div>` 还没出现，DOM 树还没生长到那个节点，因此拿不到。而 `<body>` 末尾的脚本执行时，前面的 DOM 已经构建完成。

## 面试复述模型与核心总结 *Content-[09:26]
将 HTML 解析的核心知识收束为面试中可复述的模型，建议熟记以下五句话：
1. 浏览器对 HTML 是**流式解析**的，不是下载完一次处理。
2. 大体流程是：Bytes 解码成 Characters，Characters 变成 Tokens，Tokens 逐步构建成 DOM。
3. 因此，DOM 是**增量构建**的，资源请求可以提前发出。
4. 脚本因为可以读写 DOM，会成为解析过程中的**同步点**，导致阻塞或者时序的差异。
5. 所以 `<head>` 的脚本中拿不到 `<body>` 后面的节点，而 `<body>` 末尾的脚本可以拿到。
