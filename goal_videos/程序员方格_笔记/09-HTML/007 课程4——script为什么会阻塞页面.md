## 核心问题：script 为什么会阻塞页面 *Content-[00:08]
- 这是前端面试中的高频场景题。
- 常见误区：很多候选人只会回答“因为 JS 慢”或“因为要等下载”。这些回答虽然没错，但没有触及真正的核心。
- 核心探讨：浏览器为什么**必须**要等它？我们需要深入理解其背后的机制。

## 明确“阻塞”的具体含义 *Content-[00:39]
- 阻塞**不是**指页面打不开，也**不是**指白屏时间更久。
- 阻塞的本质是：**HTML 的解析过程会停下来**。
- 浏览器在从上到下读取 HTML 时，一旦遇到 `<script>` 标签，就会停住当前动作，不再向下解析后续的标签。
- 只有等这个 `<script>` 的下载和执行流程全部走完，浏览器才会继续向下解析。
- 核心结论：**阻塞 = 停止解析**，而不是单纯的渲染慢。

## HTML 解析的流式特性与 DOM 构建 *Content-[01:16]
- HTML 的解析是**流式（Streaming）** 的。
- 浏览器并不是拿到完整的 HTML 文件后再统一处理，而是**一边读、一边解析、一边构建 DOM 树**。
- 解析器拿到 HTML 字节流后的工作流程：读一段 -> 解析成 token -> 生成节点 -> 拼接到 DOM 树上 -> 继续读下一段。
- 因此，DOM 树并不是瞬间生成的，而是一个**逐步长出来**的过程。这也是理解 script 阻塞的重要伏笔。

## JavaScript 阻塞解析的两大核心逻辑 *Content-[02:46]
要理解为什么必须暂停，需要搞清楚 JavaScript 的“破坏力”以及它对执行顺序的依赖。

### 逻辑一：JavaScript 对 DOM 结构的“破坏力”
- 与图片、CSS 等被动资源不同，JavaScript 最常做的事情是**直接读写 DOM**。
- 示例：在 JS 中通过 `querySelector` 找到某个节点，并使用 `innerHTML` 改变其内部结构或插入新节点。
- 风险：如果 JS 在 HTML 还没有解析完的时候，就把已经解析出来的 HTML 改掉，意味着 JS 随时可以拿“半成品”的 DOM 树动刀子。
- 后果：如果浏览器继续向下解析（例如解析出了 footer），此时 JS 又回头把上面的某个节点删除、移动或替换，DOM 树的结构就会变得**不可预测**，解析器刚拼好的结构可能瞬间被脚本改写。
- 机制：为了防止解析顺序和脚本修改之间“互相打架”，浏览器必须暂停解析，等待 JS 执行完毕。

### 逻辑二：脚本执行依赖 DOM 顺序与上下文
- 脚本可能依赖后面还没有解析到的 DOM 节点。
- 示例：在 JS 中获取一个按钮并绑定 click 事件。如果 JS 代码写在按钮标签之前，由于按钮还未解析，会导致获取不到节点而报错；只有写在按钮之后，事件才能正确绑定。
- 逻辑：脚本的正确执行**依赖它被插入到 HTML 文本中的位置**。
- 浏览器需要尊重开发者在 HTML 中的顺序表达（写在哪个位置，就意味着希望在那个上下文发生）。
- 如果浏览器先跳过去解析后面的内容，再回头补发执行，会破坏脚本执行时的**上下文一致性**。

## script 阻塞的本质与执行过程 *Content-[06:06]
- **浏览器的核心顾虑**：浏览器不知道 script 具体会做什么，但它必须保证 DOM 构建是确定的，且脚本执行顺序符合开发者的书写顺序。
- **阻塞的本质**：浏览器要保证 **DOM 构建的确定性** 与 **脚本执行顺序的一致性**。
- **遇到 script 时解析器的执行过程**：
  1\. 暂停 HTML 的解析。
  2\. 如果是外链脚本，发起网络下载。
  3\. 脚本下载完成之后，立即执行脚本。
  4\. 执行结束之后，继续向下解析 HTML。
- **阻塞的两个阶段**：下载阶段和执行阶段都会让解析器停住。

## 对比：JavaScript 与 CSS 的阻塞差异 *Content-[06:42]
- **CSS 的加载**：通常**不会**阻止 HTML 继续解析。因为 CSS 不会像 JS 一样主动修改 DOM 结构，浏览器可以放心往下构建 DOM。
- **CSS 的影响**：CSS 会影响**首次渲染（首次绘制）**。虽然 DOM 可以继续生成，但在首次绘制前，浏览器需要拿到关键的 CSSOM（CSS 对象模型）才能计算出正确的样式，否则页面会出现闪烁、重排等问题。
- **核心总结**：**JavaScript 阻塞的是解析，而 CSS 阻塞的是首次绘制。**

## 为什么默认阻塞而不是默认异步？ *Content-[07:27]
- **历史兼容性原因**：在早期网页中，大量脚本依赖于 `document.write`、依赖 script 的严格执行顺序、依赖同步注入 DOM 节点。
- **避免页面崩溃**：如果浏览器默认采用异步执行，早期的网页会大规模崩溃。
- **最保守的策略**：为了正确性与兼容性，浏览器选择默认同步执行。开发者写的顺序就是执行顺序，浏览器不用去猜测，这是一种最保守、最确定的策略。默认阻塞并不是因为浏览器设计得笨，而是出于对正确性的妥协。

## AI 总结
本节课深入剖析了前端面试高频问题“script 为什么会阻塞页面”。核心要点如下：
1. **阻塞的本质**：script 阻塞的不是页面渲染，而是 **HTML 的解析过程**。
2. **两大核心原因**：一是 JavaScript 具有直接读写 DOM 的“破坏力”，暂停解析可防止 DOM 结构变得不可预测；二是脚本执行依赖 DOM 的解析顺序，暂停可保证上下文的一致性。
3. **执行流程**：遇到 script 时，浏览器会经历“暂停解析 -> 下载 -> 执行 -> 继续解析”的完整过程。
4. **与 CSS 的对比**：JS 阻塞解析，CSS 阻塞首次绘制。
5. **历史原因**：默认阻塞是为了兼容早期依赖 `document.write` 和严格顺序的网页，保证 DOM 构建的确定性。
