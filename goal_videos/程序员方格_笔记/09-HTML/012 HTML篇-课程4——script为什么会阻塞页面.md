## 1. 阻塞的具体含义：停止解析而非渲染慢 *Content-[00:19]
- **阻塞的定义**：`script` 阻塞页面并不是指页面打不开、白屏或单纯的渲染变慢。
- **核心表现**：HTML 的解析过程会停下来。浏览器从上到下读取 HTML 时，遇到 `<script>` 标签会暂停，不再往下解析后面的标签。
- **恢复条件**：只有等该 `<script>` 的下载和执行流程全部走完，浏览器才会继续向下解析。
- **关键结论**：阻塞 = 停止解析，而不是单纯的渲染慢。

## 2. HTML解析的流式特性与JS的破坏力 *Content-[01:15]
- **流式解析（Streaming）**：
  - 浏览器不是拿到整个 HTML 后再统一处理，而是一边读一边解析。
  - 解析器拿到 HTML 字节流后，读一段、解析成 token、生成节点、拼接到 DOM 树上，然后继续读下一段。
  - DOM 树不是瞬间生成的，而是一个逐步“长出来”的过程。
- **JavaScript 的破坏力**：
  - 与图片、CSS 等被动资源不同，JS 最常做的事情是直接读写 DOM。
  - **示例说明**：
    - HTML 中有一个 `<div id="app">`，后面跟着 `<script src="main.js">`，再后面是文本和 `<footer>`。
    - 在 `main.js` 中通过 `document.querySelector('#app')` 获取节点，并使用 `innerHTML` 插入新的 `<span>` 和文本节点。
    - 刷新页面后，`#app` 的内容被成功修改。
  - **核心问题**：如果 JS 在 HTML 还没解析完时，就把已经解析出来的 DOM 改掉，此时 DOM 树还是“半成品”。如果浏览器继续往下解析出 `<footer>`，而 JS 又回头把上面的节点删除、移动或替换，DOM 树的结构就会变得不可预测，解析器刚拼好的结构瞬间被脚本改写。
  - **结论**：为了保证解析顺序和脚本修改之间不会互相冲突，浏览器必须等待 JS 执行完毕。

## 3. 脚本执行顺序与DOM构建的确定性 *Content-[04:27]
- **脚本依赖后续 DOM**：
  - JS 可能依赖后面还没有解析到的 DOM 节点。
  - **示例说明**：
    - 在 `<script>` 后面定义了一个 `<button id="btn">`。
    - 在 `main.js` 中尝试通过 `querySelector` 获取该按钮并绑定 `click` 事件。
    - 如果 `<script>` 在按钮前面，获取按钮会失败并报错；将 `<script>` 移到按钮后面，事件才能正确绑定并输出 `click button` 的 log。
  - **顺序语义**：脚本的正确执行依赖它在 HTML 文本中的插入位置。浏览器需要尊重开发者的书写顺序，不能跳过后续标签解析完再回头执行脚本，否则会破坏脚本执行时的上下文一致性。
- **浏览器的核心顾虑**：
  - 浏览器不知道 `script` 具体会做什么，但必须保证 DOM 构建是确定的。
  - 必须保证脚本的执行顺序符合作者（开发者）的书写顺序。

## 4. 阻塞的本质与两个阶段 *Content-[05:52]
- **阻塞的本质**：浏览器要保证 DOM 构建的确定性与脚本执行顺序的一致性。
- **解析器遇到 `<script>` 时的处理流程**：
  1\. **暂停解析**：暂停 HTML 的解析。
  2\. **发起下载**：如果是外链脚本，发起下载。
  3\. **立即执行**：脚本下载完成后立即执行。
  4\. **继续解析**：执行结束后，继续向下解析 HTML。
- **阻塞的两个阶段**：下载阶段和执行阶段。这两个阶段都会让 HTML 解析器停住。

## 5. 对比CSS：阻塞解析与阻塞首次绘制 *Content-[06:42]
- **CSS 不阻塞 HTML 解析**：
  - CSS 不会像 JS 一样主动修改 DOM 结构，因此浏览器可以放心地继续往下构建 DOM。
- **CSS 阻塞首次渲染（绘制）**：
  - 虽然 DOM 可以继续生成，但在首次绘制（First Paint）前，浏览器需要拿到关键的 CSSOM（CSS 对象模型）才能计算出正确样式。
  - 如果缺少 CSSOM，会出现闪烁、重排等问题。
- **核心总结**：JavaScript 阻塞的是**解析**，而 CSS 阻塞的是**首次绘制**。

## 6. 为什么默认阻塞而非异步 *Content-[07:27]
- **历史兼容性原因**：
  - 早期网页中有大量脚本依赖于 `document.write`、依赖 `<script>` 的执行顺序、依赖同步注入 DOM 节点。
  - 如果浏览器默认异步执行，早期的网页会大规模崩溃。
- **保守且确定的策略**：
  - 为了正确性与兼容性，浏览器选择默认同步执行。
  - 开发者写的顺序就是执行顺序，浏览器不需要去“猜”，这是一种最保守、最确定的策略。
  - 默认阻塞不是因为浏览器笨，而是为了保障网页的正确运行。

## 7. 面试回答模板 *Content-[08:04]
- **标准回答参考**：
  > “`script` 会阻塞页面的原因是：浏览器在解析 HTML 的过程中，必须保证 DOM 构建的正确性，以及脚本执行顺序的语义一致性。JavaScript 可能读取或修改当前 DOM，甚至影响后续解析的结果。所以解析器遇到了 `<script>` 会暂停，等待脚本下载并执行完成之后，再继续解析。”

## AI 总结
- 本次课程深入剖析了前端面试高频问题“`script` 为什么会阻塞页面”。
- 核心要点在于理解“阻塞”的本质是**暂停 HTML 解析**，而非单纯的渲染变慢。
- 浏览器之所以必须等待，是因为 JavaScript 具有直接读写 DOM 的“破坏力”，且脚本执行严格依赖其在 HTML 中的书写顺序。为了保证 DOM 构建的确定性和脚本执行的上下文一致性，浏览器采用了同步阻塞的策略。
