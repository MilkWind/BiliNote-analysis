## 核心视角：浏览器的流式解析 *Content-[00:18]
- **常见误区**：很多人直觉上认为浏览器是把整个 HTML 文件下载完之后，才开始解析和渲染页面。
- **真实机制**：现代浏览器解析 HTML 的核心特点是**流式解析**（边下载边解析，边解析边建树）。HTML 文件从网络传输时是一段一段的字节流，浏览器拿到一段就开始处理，而不是等待全部下载结束。
- **重要性**：流式解析直接决定了首屏加载速度、资源提前请求、脚本阻塞页面以及 JS 获取 DOM 的时序等核心前端性能与行为问题。
- **概念纠正**：严格来说，HTML 本身没有“解析”这一动作，它不是可运行的程序，而是一份描述文档。更精准的表达是：HTML 解析器读到一个标签，就会创建对应的节点。就像边看书边做笔记，而不是看完再做。

## 浏览器解析 HTML 的流水线过程 *Content-[02:24]
浏览器内部解析 HTML 经历了一个典型的流水线过程，主要分为以下几个阶段：
1\. **字节流到字符流**：网络传输的是字节（bytes），浏览器根据指定的编码（如 UTF-8）将其解码为字符流。
2\. **字符流到 Token**：浏览器的 Tokenizer（词法分析器）会将字符流识别成一个个 Token。例如：`<div>` 是一个开始标签 Token，`hello` 是一个文本 Token，`</div>` 是一个结束标签 Token。
3\. **Token 到 DOM 节点**：浏览器的 Tree Builder（树构建器）会根据 Token 的顺序和 HTML 规则，逐渐构建出 DOM 树。
- **核心特征**：这并不是一次性的转换，而是一个循环、流式的分析过程。浏览器每拿到一点字符就能吐出一点 Token，进而生长出一些 DOM 节点。
- **三个关键词**：流式、顺序、增量。DOM 树不是一瞬间生成的，而是持续生长的。

## DOM 树的增量构建与代码示例 *Content-[03:54]
通过一个标准的 HTML 结构示例，可以清晰看到 DOM 树的机械且确定的生长过程：
- 解析器首先读到 `<!DOCTYPE html>`，确定渲染模式。
- 读到 `<html>`，创建 HTML 节点，挂在 `document` 下。
- 读到 `<head>`，创建 head 节点，成为 HTML 的子节点。
- 读到 `<title>`，创建 title 节点挂在 head 下，接着创建文本节点挂在 title 下，最后处理闭合标签。
- 读到 `<body>` 和 `<div id="app">`，创建对应节点并设置属性（`id="app"`）。
- 读到文本 `hello`，创建文本节点挂在 div 下。
- 最后依次闭合 `div`、`body` 和 `html`。
- **结论**：DOM 的生长过程非常机械和确定，解析器严格将 Token 转成节点。理解了这一点，就能解释为什么在 `head` 里写脚本无法访问 `body` 里还没出现的 DOM（因为那部分 Token 还未解析，节点尚未创建）。

## 解析过程中遇到外部资源的处理 *Content-[06:16]
既然 HTML 是流式解析的，浏览器在解析过程中遇到外部资源（如 CSS、图片）时会采取优化策略：
- **CSS 资源**：当解析器在 `head` 中读到引入 CSS 的 `<link>` 标签时，不会等待整个 HTML 结束，而是立刻将资源交给网络层请求。这有助于尽早完成布局与绘制，提升性能。
- **图片资源**：在 `body` 中遇到 `<img>` 标签时，浏览器也会尽可能早地发出图片请求。
- **Preload Scanner 机制**：HTML 解析器负责发现资源并触发请求。浏览器内部有 Preload Scanner（预加载扫描器）机制，会尽量提前扫描并预加载关键资源。流式解析的结构天然让“边解析边请求”成为可能。

## Script 标签的特殊性与阻塞机制 *Content-[07:18]
与 CSS 和 Image 等静态资源不同，`<script>` 标签在解析过程中是一个“危险而特殊”的角色：
- **谨慎处理的原因**：脚本不仅仅是资源，它是会执行的。脚本执行时可能会做两件事：
  1. 读写 DOM（如使用 `querySelector` 或 `getElementById`）。
  2. 改变解析流程（如使用 `document.write` 插入新的 HTML，解析器必须将插入的内容也解析掉）。
- **同步点机制**：为了保证脚本执行时 DOM 处于一个确定的状态（否则脚本读到的结构可能是错的），解析器通常会在遇到 `<script>` 时**暂停解析**，等待脚本加载并执行结束后，再继续往下解析。
- **核心概念**：脚本会影响 DOM，而 DOM 正在生长，因此脚本在解析过程中会被当作**同步点**，从而导致阻塞或时序差异。

## 高频面试题解析：DOM 获取的时序问题 *Content-[08:26]
- **现象**：在 `head` 中编写 JS 脚本通过 `document.querySelector('#app')` 查找节点，结果为 `null`；而将同样的脚本放到 `body` 末尾，则能正确获取到该 DOM 节点。
- **原因分析**：
  - 当 `head` 中的脚本执行时，解析器可能只解析到了 `head` 部分，`body` 里的 `div` 还没有出现，DOM 树还没生长到那个节点，因此获取不到。
  - 当脚本放在 `body` 末尾时，前面的 DOM 节点已经全部构建完成，因此可以正确获取。

## 面试总结：可复述的解析模型 *Content-[09:26]
在面试中，可以通过以下五句话构建一个清晰、专业的回答模型：
1\. 浏览器对 HTML 是**流式解析**的，不是下载完一次处理。
2\. 大体流程是：bytes 解码成字符，字符生成 Token，Token 逐步构建成 DOM。
3\. 因此 DOM 是**增量构建**的，资源请求可以提前发出。
4\. 脚本因为可以读写 DOM，会成为解析过程中的**同步点**，导致阻塞或者时序的差异。
5\. 所以 `head` 的脚本中拿不到 `body` 后面的节点，而 `body` 末尾的脚本可以拿到。
