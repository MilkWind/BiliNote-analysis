## 插件化思想与 Pinia 插件机制 *Content-[00:01]

### 插件化思想的核心意义
- **开放与繁荣**：插件化思想能够让工具变得更加开放，通过开放相关接口，让开发者能够注入自定义能力，从而繁荣整体生态。
- **避免纯黑盒**：在产品开发中，应思考如何管理产品的开放程度。纯黑盒设计往往会限制平台的发展，而相对程度的开放能让生态持续繁衍。

### Pinia 的插件化机制
- **能力扩展**：Pinia 正是基于插件化思想来扩展和增强其核心能力。
- **拦截机制**：通过拦截触发 store 的相关方法（如 action），以及拦截 store 的生命周期和周期钩子，实现对 store 的增强，并实现全局性或复用性的逻辑。
- **插件的本质**：插件本质上是一个**函数**。它接收 store 的实例作为参数，在函数内部对 store 进行增强操作，并最终返回一个对象。

## Pinia 插件的核心原则与钩子 *Content-[02:05]

### 插件的核心原则
1\. **单一职责**：每个插件应专注于一个特定的功能。例如，持久化插件和日志记录调试插件应该分开，用各自独立的插件来实现。
2\. **类型安全**：需要为插件提供完善的 TypeScript (TS) 支持，确保类型安全。
3\. **轻量无侵入**：
   - 插件不能过于笨重。
   - 避免直接修改 store 的原有逻辑。
   - 优先使用 Pinia 提供的相关钩子（如 `onAction`、`$subscribe`、`patch` 等 API）来完成处理，做到无侵入。

### Pinia 核心钩子函数
- **`onAction`**：主要用于监听 action 的调用。当触发一个 action 后，就会执行对应的回调函数。
- **`$subscribe`**：用于监听 state 的变更。当 state 发生变化时进入回调，常用于追踪 state 的变化过程（从什么值变到了什么值）。
- **`patch`**：用于批量更新当前 state，触发 state 的变更。

## 常见插件场景：状态持久化 *Content-[04:30]

### 场景痛点
- 在默认情况下，每次刷新页面，Pinia 中的状态都会被重置。
- 对于用户登录状态（如 token），如果刷新后丢失，就需要重新请求登录，这在业务场景中是不合理的。因此需要将状态进行持久化存储。

### 持久化插件的实现与使用
- **引入第三方库**：通常引入第三方库 `pinia-plugin-persistedstate` 来实现。
- **全局注册**：在 main 文件中，通过 `pinia.use()` 方法全局注册该插件。
- **Store 配置**：
  - 在 `defineStore` 中，添加 `persist` 配置对象。
  - 可以指定 `storage: localStorage` 来设置存储方式，并配置 `key`（如 'message'）作为本地存储的键名。
  - 也可以直接简写为 `persist: true`，使用默认配置。
- **效果**：配置后，更新 state 并刷新页面，数据会从 `localStorage` 中读取，状态得以保留。

### 注意事项
- 避免将敏感数据进行持久化存储。
- 在必要时，需要对持久化的数据进行加密处理。

## 常见插件场景：开发环境日志记录 *Content-[08:50]

### 日志插件的实现思路
- **自定义插件**：定义一个 `logPlugin` 函数。
- **解构钩子**：在回调中，通过解构获取 store 的相关钩子方法。
- **监听与打印**：
  - 打印当前 action 相关的 name。
  - 在 `after` 钩子中，处理修改 state 后的逻辑，打印状态变更。
  - 捕获并处理异常情况下的状态。

### 环境控制与效果演示
- **环境限制**：通过判断 `import.meta.env.DEV`，控制该日志插件仅在开发环境 (DEV) 中使用，避免在生产环境产生多余日志。
- **无侵入监听**：
  - 当 dispatch 一个 action（如 `increment`）时，插件会拦截并打印 `called with` 及传入的参数。
  - 在 action 成功执行后，打印 state 成功修改后的状态。
  - 整个过程完全通过监听 action 调用和 state 变化实现，没有修改任何原有业务逻辑，体现了无侵入特性。
