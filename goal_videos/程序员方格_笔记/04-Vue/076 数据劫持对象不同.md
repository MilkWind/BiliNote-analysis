## 面试题背景与核心考点 *Content-[00:00]
- **面试题**：Cookie 和 Token 都是存放在请求头里面，为什么数据劫持通常劫持 Cookie，而很少劫持 Token？
- **考察重点**：考察应聘者对 Cookie 和 Token 设计机制、使用方式以及安全特性的深入理解。只有理解了它们的设计初衷，才能明白为什么 Cookie 容易被劫持而 Token 相对安全。

## 原因一：发送机制的差异 *Content-[02:18]
### 1\. **Cookie 的自动发送机制**
- **机制说明**：Cookie 在设计时具备自动发送机制。在浏览器同源（同主域）策略下，Cookie 会自动附加到每个请求的请求头中。
- **开发者视角**：开发者不需要手动添加，浏览器每次请求同域资源时都会自动携带。
- **安全风险**：这种“无脑”自动附加的机制带来了巨大风险。如果攻击者通过跨站脚本（XSS）注入恶意脚本，浏览器无法分辨请求是正常发起还是恶意发起，依然会自动附带 Cookie。一旦访问恶意网站或页面被注入脚本，Cookie 就会被轻松窃取，导致整个会话被劫持。

### 2\. **Token 的主动控制机制**
- **机制说明**：Token 采用主动控制机制，不会像 Cookie 那样自动附加到请求中，而是需要开发者手动将其放入请求头。
- **存储与读取**：Token 通常存储在 `localStorage`、`sessionStorage` 或内存中。开发者需要主动编写代码读取 Token 并塞入请求头。
- **安全风险降低**：
  - 攻击者若想利用 Token 发起攻击，必须先通过额外代码读取到 Token 的值，然后再将其发送到自己的服务器，这大大增加了攻击难度。
  - 恶意网站无法伪造请求携带 Token，除非攻击者同时窃取了 Token（难度极高）。因为 Token 不会随浏览器自动发送，攻击者很难在不知情的情况下获取并构造有效请求。

## 原因二：安全设置的差异 *Content-[07:29]
### 1\. **Cookie 的安全属性及局限性**
- **HttpOnly 属性**：设计用于防止 JavaScript 直接读取 Cookie。但如果开发者忘记设置或配置不当，该属性形同虚设，无法防御 XSS 攻击。
- **SameSite 属性**：用于限制跨站发送 Cookie（防御 CSRF）。但由于部分浏览器的兼容性问题或开发者配置不当，导致该安全设计经常失效。
- **结论**：Cookie 的安全属性高度依赖开发者的正确配置，一旦疏忽，就会变成高风险对象。

### 2\. **Token 的安全设计优势**
- **灵活的过期时间**：可以灵活设置 Token 的有效期。例如使用 `sessionStorage` 存储，关闭浏览器后 Token 即失效，缩短了被攻击的窗口期。
- **无状态性**：服务器端不需要存储 Token 的状态（会话信息）。攻击者无法通过固定的会话 ID 进行劫持，因为服务端根本没有存储对应的固定会话。
- **额外的签名机制**：如 JWT (JSON Web Token) 内部包含签名机制。一旦 Token 被攻击者篡改，签名校验会立即失败，Token 瞬间失效。这使得即使 Token 被劫持，篡改后也无法使用。

## 原因三：攻击场景的对比 *Content-[11:00]
### 1\. **XSS 攻击场景对比**
- **Cookie**：如果未设置 `HttpOnly`，攻击者可以直接通过 JavaScript 读取 Cookie，并利用 `<img>` 标签等方式将 Cookie 发送到攻击者的服务器，过程非常简单。
- **Token**：攻击者需要额外编写代码去读取 `localStorage` 等存储介质。现代浏览器的内容安全策略 (CSP) 或隔离机制通常会限制这种跨域或恶意的读取行为，导致攻击者很难成功获取 Token。

### 2\. **CSRF 攻击场景对比**
- **Cookie**：由于浏览器会自动发送 Cookie，攻击者只需伪造一个请求（如插入一张 `<img>` 图片或一个恶意链接），诱导用户点击或加载，浏览器就会自动携带 Cookie 发送请求，从而完成 CSRF 攻击。
- **Token**：攻击者必须同时窃取到用户的 Token，才能构造出携带有效 Token 的伪造请求。由于 Token 不会自动携带，攻击者无法仅凭伪造 HTML 标签就完成 CSRF 攻击。

## 核心总结与面试回答要点 *Content-[13:39]
- **Token 并非绝对安全**：Token 并不是绝对不会被劫持，而是其**主动控制**和**无自动发送**的特性大幅降低了被劫持的风险。
- **Token 的自我保护**：即使被劫持，Token 自身的无状态性和签名机制也能提供一定的保护，使得篡改失效。
- **Cookie 的高风险性**：Cookie 的自动发送机制使其在未妥善配置安全属性（如 `HttpOnly`、`SameSite`）时，极易成为攻击目标。
- **面试回答建议**：在回答此题时，重点突出 Cookie 的“自动发送机制”与 Token 的“主动控制机制”的对比，并补充两者在安全属性设计（如 JWT 签名、无状态性）上的差异，即可给出满分回答。对于 Cookie，必须强调需要做好多层安全防护配置。

## AI 总结
本题核心探讨了前端身份验证中 Cookie 与 Token 在数据劫持风险上的差异。Cookie 因浏览器的“自动发送机制”及高度依赖开发者手动配置安全属性（如 `HttpOnly`、`SameSite`），在 XSS 和 CSRF 攻击中极易被劫持。相反，Token 采用“主动控制机制”，需开发者手动读取并注入请求头，增加了攻击者的窃取难度；同时 Token（如 JWT）具备无状态性、灵活过期时间及签名防篡改等自身安全设计，大幅降低了被劫持及劫持后滥用的风险。面试时应从发送机制、安全设计差异及具体攻击场景（XSS/CSRF）三个维度进行结构化回答。
