## 1. 题目难点分析 *Content-[00:29]
手写一个符合 Promise A+ 规范的 Promise 几乎是中高级前端岗位的必考题。这道题主要有四个难点（四个坎）需要跨越：
- **规范本身复杂**：Promise A+ 规范为了保证不同 Promise 实现之间的一致性，定义了大量规则。特别是 2.3 章节，专门用来处理 `then` 方法返回值的解析过程，包含大量的边界情况。
- **状态管理**：Promise 本质上是一个状态机，包含 `pending`、`fulfilled` 和 `rejected` 三种状态。这三种状态的变更是单向的，一旦从 `pending` 变成 `fulfilled` 或 `rejected`，就不能再改变，需要在代码中严格控制。
- **异步处理细节**：规范明确要求 `then` 方法注册的回调必须是异步执行的，且必须使用**微任务**（如 `queueMicrotask`），不能使用 `setTimeout` 等宏任务。
- **链式调用**：每个 `then` 方法都必须返回一个新的 Promise 实例，同时还需要正确处理值穿透问题（即当 `then` 里面不传函数时，值要能传递到下一个 `then` 方法）。

## 2. 第一步：搭建基础结构 *Content-[02:11]
任何复杂的代码都从简单的结构开始。首先定义 `MyPromise` 类，在构造函数中定义关键属性并立即执行执行器函数：
- **状态属性**：`state`（初始状态必须为 `pending`）、`value`（成功值）、`reason`（错误原因），分别用来存储状态、成功的值和错误的原因。
- **回调队列**：定义 `onFulfilledCallbacks` 和 `onRejectedCallbacks` 两个数组，用来存放在 Promise 状态还是 `pending` 时，通过 `then` 方法注册的成功和失败回调函数。
- **执行器函数**：构造函数接收一个执行器函数并立即执行。执行器函数会接收在构造函数中定义的 `resolve` 和 `reject` 两个函数作为参数，同时使用 `try...catch` 包裹以进行错误处理。

## 3. 第二步：实现状态变更 *Content-[03:32]
实现 `resolve` 和 `reject` 这两个核心方法，让状态机运转起来：
- **resolve 方法**：
  - 首先检查当前状态是否为 `pending`，这确保了状态只能被改变一次。
  - 如果是 `pending`，将 `state` 改为 `fulfilled`，并保存成功的 `value`。
  - 遍历 `onFulfilledCallbacks` 数组，把之前所有暂存的回调函数依次执行。
- **reject 方法**：
  - 逻辑与 `resolve` 几乎一模一样。先检查状态是否为 `pending`。
  - 将 `state` 改为 `rejected`，保存失败的 `reason`。
  - 遍历 `onRejectedCallbacks` 队列，执行所有暂存的失败回调。
- 通过 `if` 判断锁定状态的单向流转，通过遍历回调队列解决异步回调执行的问题，至此一个基础的 Promise 模型已经成型。

## 4. 核心概念：异步处理与微任务 *Content-[04:59]
在实现 `then` 方法之前，必须搞清楚 Promise A+ 规范中至关重要的规定：注册的回调必须是异步执行的，且不能是 `setTimeout` 这样的宏任务，而必须是**微任务**。
- **为什么必须是微任务**：
  - 直接调用是同步的，不符合规范。
  - `setTimeout` 虽然异步，但属于宏任务，执行时机太晚。
  - 正确做法是使用 `queueMicrotask`（现代浏览器专门调度微任务的 API）。在 Node.js 或旧版浏览器中，可用 `process.nextTick` 或 `MutationObserver` 模拟。
- **Event Loop 经典示例**：
  - 假设代码输出顺序为 `1, 5, 2, 3, 4`。
  - 主线程的同步代码（1 和 5）先被打印。
  - 同步脚本执行结束后，事件循环系统立即清空微任务队列，打印 2 和 3。
  - 最后才轮到宏任务队列里的 `setTimeout`，打印 4。
  - Promise 的设计就是为了保证回调在本次同步代码执行完后，以最快的速度被调用。

## 5. 第三步：实现 then 方法 *Content-[06:45]
`then` 方法接收 `onFulfilled` 和 `onRejected` 两个可选参数，实现逻辑较长，需分步拆解：
- **值穿透处理**：
  - 如果传入的不是函数，A+ 规范要求忽略并实现值穿透。
  - `onFulfilled` 的默认函数直接返回接收到的值（`v => v`）。
  - `onRejected` 的默认函数直接抛出错误（`e => { throw e }`），保证链式调用中值向下传递。
- **返回新的 Promise**：
  - 为实现链式调用，`then` 必须返回一个全新的 Promise 实例（命名为 `promise2`）。
  - `then` 内部的所有逻辑都写在 `promise2` 的执行器函数中。
- **分状态处理回调**：
  - **fulfilled 状态**：使用 `queueMicrotask` 将 `onFulfilled` 放入微任务队列。在微任务中执行回调获取返回值 `x`，需用 `try...catch` 捕获回调本身的错误。
  - **rejected 状态**：同理，使用微任务执行 `onRejected` 回调。
  - **pending 状态**：不能直接执行回调，将 `onFulfilled` 和 `onRejected` 的逻辑分别包装后，`push` 进对应的回调数组中。等待未来状态改变时，这些包装函数被执行（内部包含 `queueMicrotask` 逻辑）。

## 6. 第四步：实现 resolvePromise 解析过程 *Content-[09:38]
`resolvePromise` 函数根据 `then` 回调的返回值 `x` 来决定 `promise2` 的最终状态，是 A+ 规范 2.3 节的精髓，分为四个核心场景：
- **防止循环引用**：
  - 如果 `x` 等于 `promise2` 本身，直接抛出 `TypeError` 提示循环引用，防止死循环。
- **x 是 MyPromise 实例**：
  - 使用 `instanceof MyPromise` 判断。
  - 如果是，调用 `x.then`，将 `promise2` 的 `resolve` 和 `reject` 传入，使 `promise2` 的状态紧跟随 `x`。
  - 注意：`x.then` 成功回调拿到的值 `y` 可能也是 Promise，需要递归调用 `resolvePromise` 处理。
- **x 是 thenable 对象（最复杂）**：
  - `thenable` 对象指带有 `then` 方法的对象或函数。
  - 判断 `x` 是否为对象或函数且不为 `null`。
  - 使用 `called` 标志位防止 `resolve` 或 `reject` 被重复调用。
  - 在 `try...catch` 中尝试获取并执行 `x.then`（使用 `call` 将 `x` 作为 `this` 传递）。
  - 只认第一次调用的结果，防止第三方代码多次调用。
  - 如果 `x.then` 不是函数，则按普通对象处理，直接 `resolve(x)`。
- **x 是普通 JavaScript 值**：
  - 如果 `x` 不是 `thenable` 对象（如数字、字符串、普通对象），直接用 `x` 来 `resolve` `promise2`。

## 7. 面试满分回答思路总结 *Content-[14:24]
当面试官问及“能手写 Promise 吗”时，可以按以下四步有条不紊地进行满分回答：
1. **搭建基础结构**：定义好三个基础状态（`pending`, `fulfilled`, `rejected`）以及两个回调队列。
2. **实现状态变更**：编写 `resolve` 和 `reject` 方法，保证状态单向流转，并在变更后执行回调队列。
3. **实现核心 then 方法**：返回新的 Promise，使用微任务保证回调的异步性；对于 `pending` 状态，记得把回调存到队列里面。
4. **实现 resolvePromise 解析过程**：严格按照 A+ 规范处理 `then` 返回的各种值，重点讲解对于 `thenable` 对象的兼容处理和循环引用的检测。
