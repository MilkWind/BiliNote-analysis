## 1. 引言：面试中的请求重试问题 *Content-[00:00]
- **面试常见场景**：面试官提问“如果一个 API 请求失败了，你会怎么处理？”
- **糟糕的用户体验**：用户点击按钮 -> 界面转圈 -> 接口报错 -> 界面无反应 -> 弹出“网络错误，请稍后重试”。直接把错误抛给用户是最懒的做法。
- **优秀的解决方案**：在用户无感知的情况下，通过**请求重试（Retry）** 机制悄悄解决问题。
- **重试背后的两个核心问题**：
  1. **重试的时机**：是否所有失败都应该重试？（例如：网络抖动、503 可重试；404、401 不可重试）。
  2. **重试的策略**：决定重试后，是立即重试还是等待？等待多久？（立即重试可能会加重服务器负担）。

## 2. 第一步：判断是否应该重试 (shouldRetry) *Content-[02:01]
- **核心原则**：**只对可恢复的错误进行重试**。
- 编写 `shouldRetry` 函数进行精准判断：
  - **网络层面错误**：如 `response` 不存在（DNS 解析失败、客户端断网等），属于瞬时错误，**应该重试**。
  - **服务端错误（状态码 >= 500）**：如 500、502 Bad Gateway、503 Service Unavailable。服务器可能很快恢复，**应该重试**。
  - **限流错误（状态码 429）**：服务器因限流暂时拒绝请求，明确提示稍后再试，**应该重试**。
  - **客户端错误（如 404, 403, 401）**：接口地址错误、未登录等，重试 1 万次也无法解决，**不应该重试**（直接返回 `false` 放弃重试）。

## 3. 第二步：重试策略 - 指数退避 (Exponential Backoff) *Content-[03:15]
- **核心原则**：**千万不要立即重试**。如果服务器因压力过大返回 503，立即重试会增加服务器压力，导致问题恶化。
- **经典策略**：**递增延迟 / 指数退避**。
- **实现逻辑**：在 `for` 循环中限制最大重试次数 `maxRetry`。
- **延迟时间计算公式**：
  $$ \text{Delay} = 2^i \times 1000\text{ms} $$
  （其中 $i$ 为当前重试次数，从 0 开始）
- **效果演示**：
  - 第 1 次失败（$i=0$）：等待 $2^0 \times 1000 = 1$ 秒。
  - 第 2 次失败（$i=1$）：等待 $2^1 \times 1000 = 2$ 秒。
  - 第 3 次失败（$i=2$）：等待 $2^2 \times 1000 = 4$ 秒。
- **优势**：每次重试间隔呈指数级增长，给服务端宝贵的喘息机会，大大提高下一次请求的成功概率。

## 4. 第三步：优化策略 - 随机抖动 (Jitter) *Content-[04:49]
- **潜在问题（惊群效应）**：如果服务器发生大范围 P0 故障，成千上万的用户同时请求失败。如果都采用相同的指数退避策略，客户端会在 1秒、2秒、4秒后**同时**发起重试，形成新的流量高峰，再次压垮刚缓过气的服务器。
- **解决方案**：在延迟时间中加入**随机抖动（Jitter）**，打散并发请求。
- **随机抖动计算公式**：
  $$ \text{Jitter} = (\text{Math.random}() - 0.5) \times \text{系数} $$
  （生成一个 `-0.5` 到 `0.5` 之间的随机数，乘以系数后加到原始延迟上）
- **效果**：即使 1000 个客户端同时失败，它们的下次重试时间也会是“1秒左右”、“2秒左右”，而不是精确的 1秒、2秒。请求被均匀分散到不同时间点，进一步减轻服务器瞬时压力。
- **结论**：**指数退避 + 随机抖动** 是业内公认的最佳实践。

## 5. 代码组装：完整的请求重试机制 *Content-[06:39]
将上述逻辑封装到一个健壮的 `request` 函数中，完整流程如下：
1. **控制次数**：使用 `for` 循环控制最大重试次数，避免无限重试。
2. **捕获错误**：使用 `try...catch` 捕获 API 调用可能抛出的任何错误。
3. **错误判断**：在 `catch` 中调用 `shouldRetry`（哨兵函数），第一时间判断错误是否值得投入资源重试。
4. **计算延迟**：如果值得重试，调用 `getRetryDelay` 计算下一次重试的最佳时机（包含指数退避和随机抖动）。
5. **等待与重试**：使用 `sleep` 函数安静地等待延迟时间，然后进入下一次循环。
6. **优雅降级**：如果所有尝试都失败，将最终错误抛给上层业务逻辑处理，给用户展示最终的失败提示。

## 6. 面试满分答案总结 *Content-[07:58]
当面试官问及“如何实现请求重试”时，不要只回答“简单的 for 循环调 3 次接口”，而应展示一个完整、智能、有策略的机制：
1. **错误判断**：通过 `shouldRetry` 判断错误类型，只对可恢复的错误（网络错误、5xx、429）进行重试。
2. **递增延迟**：采用指数退避策略（Exponential Backoff），避免对服务器造成二次冲击。
3. **随机抖动**：在延迟基础上加入随机值（Jitter），打散并发重试，防止多个客户端造成服务器“惊群”压力。
4. **优雅降级**：达到最大重试次数后，将最终失败结果交给业务层处理，给用户合理的提示。
- **核心价值**：向面试官证明你不仅写过代码，还深入思考过系统的稳定性和代码的健壮性，这是高级工程师和初级工程师拉开差距的地方。

## 7. AI 总结
本视频详细讲解了前端面试中高频的场景题——“如何实现请求重试”。一个生产级别的请求重试机制绝非简单的循环调用，而是需要综合考量**重试时机**与**重试策略**。核心要点包括：通过 `shouldRetry` 过滤不可恢复的错误（如 404/401）；采用**指数退避（Exponential Backoff）** 避免立即重试压垮服务器；引入**随机抖动（Jitter）** 打散并发请求防止“惊群效应”；最终在达到最大重试次数后实现**优雅降级**。掌握这套组合拳，能够充分展现开发者对系统稳定性和健壮性的深度思考。
