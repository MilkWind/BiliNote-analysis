## 1. 引言：为什么需要请求重试 *Content-[00:00]
- **常见糟糕场景**：用户在应用中点击按钮发起 API 请求，界面开始 loading，若接口报错且界面无反应，最终只弹出一个“网络错误，请稍后重试”的提示。
- **痛点分析**：直接将失败的错误消息返回给用户是最懒的做法，用户体验极差。
- **优秀解决方案**：优秀的程序员会在用户无感知的情况下悄悄解决问题。**请求重试（Retry）** 机制就是解决此类问题最重要的武器。
- **核心挑战**：重试说起来简单，但背后需要重点考虑两个核心问题：**重试的时机**（该不该重试）和**重试的策略**（怎么重试）。

## 2. 核心问题一：重试的时机（该不该重试） *Content-[01:01]
- **核心原则**：**只对可恢复的错误进行重试**。
- **需要重试的错误类型**（通过 `shouldRetry` 函数判断）：
  - **网络层面错误**：如 DNS 解析失败、客户端断网等（通常表现为没有 `response` 对象），这类瞬时错误重试后大概率能恢复。
  - **服务端临时错误**：`response.status >= 500`（如 502 Bad Gateway、503 Service Unavailable）。这类错误说明服务端出了问题，但通常是暂时的，服务器可能很快恢复。
  - **限流错误**：`429 Too Many Requests`。服务器因限流暂时拒绝请求，明确提示“稍后再试”，因此必须进行重试处理。
- **不需要重试的错误类型**：
  - **客户端错误**：如 `404 Not Found`（接口地址错误）、`401 Unauthorized`（未登录）、`403 Forbidden`。这类错误重试 1 万次结果也不会改变，毫无意义，应直接返回 `false` 放弃重试。

## 3. 核心问题二：重试的策略（怎么重试） *Content-[03:15]
- **核心原则**：**千万不要立即重试**。如果服务器已经因为压力过大返回 503，立即重试不仅不能修复问题，反而会进一步增加服务器压力。
- **经典策略：递增延迟 / 指数退避（Exponential Backoff）**
  - 在一个 `for` 循环中尝试最多 `maxRetries` 次。
  - 当捕获到错误且决定重试时，等待时间以指数级增长，给服务端宝贵的喘息机会。
  - **延迟计算公式**：等待时间 = $2^i \times 1000\text{ms}$ （其中 $i$ 为当前重试次数，从 0 开始）。
    - 第 1 次失败（$i=0$）：等待 $2^0 \times 1000\text{ms} = 1\text{s}$
    - 第 2 次失败（$i=1$）：等待 $2^1 \times 1000\text{ms} = 2\text{s}$
    - 第 3 次失败（$i=2$）：等待 $2^2 \times 1000\text{ms} = 4\text{s}$
  - **优势**：指数级增长的间隔大大提高了下一次请求的成功概率。

## 4. 进阶策略：引入随机抖动（Jitter） *Content-[04:55]
- **问题背景（惊群效应）**：如果服务器出现大范围 P0 故障，成千上万的用户可能同时请求失败。如果所有客户端都使用完全相同的指数退避策略，他们会在 1s、2s、4s 后像约定好一样同时发起重试。这种有规律的集中重试流量会形成新的流量高峰，把刚缓过气的服务器再次压垮。
- **解决方案：随机抖动（Jitter）**
  - 在计算出的延迟时间里加入一个随机值，打散并发请求。
  - **实现逻辑**：使用 `Math.random() - 0.5` 生成一个 $[-0.5, 0.5]$ 之间的随机数，乘以一个系数得到随机抖动时间，然后将其加到原始的指数退避延迟上。
  - **效果**：即使有 1000 个客户端同时失败，他们计算出的下一次重试时间也会是“1秒左右”、“2秒左右”，而不是精确的 1s、2s。请求被均匀分散到不同的时间点上。
- **结论**：**指数退避（Exponential Backoff） + 随机抖动（Jitter）** 是业内公认的重试最佳实践，能进一步减轻服务器瞬时压力，提高系统整体恢复成功率。

## 5. 代码组装：完整的请求重试函数 *Content-[06:40]
将上述所有逻辑零件组装，封装成一个健壮的 `request` 函数：
- **循环控制**：使用 `for` 循环控制最大重试次数（`maxRetries`），避免无限重试。
- **错误捕获**：使用 `try...catch` 捕获底层请求（如 `fetch`）可能抛出的任何错误。
- **哨兵判断**：在 `catch` 中调用 `shouldRetry` 函数，第一时间判断该错误是否值得投入更多资源去重试。
- **计算延迟**：如果值得重试，调用 `getRetryDelay` 函数计算下一次重试的最佳时机（内部包含指数退避和随机抖动逻辑）。
- **等待执行**：使用 `sleep` 函数安静地等待计算出的延迟时间，然后进入下一次循环。
- **优雅降级**：如果所有尝试均失败，将最终的错误抛给上层业务逻辑处理，此时可给用户展示最终的失败提示。

## 6. 面试满分答案总结 *Content-[07:58]
当面试官询问“如何实现请求重试”时，满分答案绝不是简单的 `for` 循环调 3 次接口，而是一个完整、智能、有策略的机制。答题需涵盖以下核心流程：
1\. **错误判断**：精准判断错误类型，只对可恢复的错误（网络错误、5xx、429）进行重试。
2\. **递增延迟（指数退避）**：采用指数级增长的延迟策略，避免对服务器造成二次冲击。
3\. **随机抖动（Jitter）**：在延迟基础上加入随机值，打散并发的重试请求，防止多个客户端同时重试造成服务器雪崩。
4\. **优雅降级**：在达到最大重试次数后，将最终失败结果优雅地交给业务层处理。

**面试价值**：答出这些要点，能向面试官证明你不仅会写基础代码，而且深入思考过系统的稳定性和代码的健壮性，这是高级工程师与初级工程师拉开差距的核心所在。
