## JS 异步编程概述 *Content-[00:00]

在 JS 中，异步编程是一个核心且复杂的课题。与同步代码不同，异步代码的执行顺序并不直观。

1\. **异步代码的特点**
- 异步代码不像同步代码（如连续执行 `console.log(1)`、`console.log(2)`、`console.log(3)`）那样按顺序一目了然地输出。
- 异步代码需要加入到**事件循环机制 (Event Loop)** 当中执行。

2\. **执行流程与任务队列**
- 异步代码放入事件循环后，如果处于结果待产生（待执行）状态，会等待结果产生。
- 在快产生结果的那一刻，会将结果拿回到同步代码的调用栈中执行。
- 执行顺序还涉及**宏任务 (Macro Task)** 和**微任务 (Micro Task)** 的调度，因此控制起来比同步代码复杂得多。

3\. **发展历程**
JS 异步解决方案主要经历了四个阶段：
1. 回调函数 (Callback)
2. Promise
3. Generator (生成器)
4. async/await (目前主流)

## 阶段一：回调函数 (Callback) *Content-[01:12]

这是最基础的异步处理方式，通过传递回调函数来获取异步操作的结果。

1\. **基础场景模拟**
- **需求**：模拟计算两个数相加，假设计算过程需要 1 秒（使用 `setTimeout` 模拟）。
- **实现**：定义一个计算函数，接收参数 `a`、`b` 和一个 `callback` 回调函数。在定时器内部计算 `a + b`，1 秒后将结果传给 `callback` 并执行。
- **原因**：因为异步代码无法直接通过 `return` 返回结果给调用者（定时器不处理返回值），所以必须依赖回调函数来接收结果。

2\. **连续计算的需求**
- **需求升级**：第一次计算 `1 + 2 = 3` 完成后，需要用第一次的结果 `3` 再加上 `3` 进行第二次计算（即 `3 + 3 = 6`）。
- **实现方式**：由于必须等待第一次异步计算完成，第二次计算的调用必须写在第一次计算的**回调函数内部**。

3\. **回调地狱 (Callback Hell)**
- **问题产生**：如果需求继续增加（第三次、第四次计算），代码就需要不断在回调函数内部嵌套回调函数。
- **代码表现**：代码会形成向右倾斜的“金字塔”或“箭头”形状（即回调地狱）。
- **缺点**：
  - 代码极度冗长，可读性极差。
  - 非常不方便维护，如果中间某一步出错（例如传入了非数字导致计算错误），在深层嵌套中排查错误非常费劲。
  - 因此，回调函数并不是处理复杂异步逻辑的好选择。

## 阶段二：Promise *Content-[06:01]

为了解决回调地狱问题，ES6 引入了 Promise。

1\. **代码改造**
- 将原本传递回调函数的方式，改为函数内部 `return new Promise()`。
- 在 Promise 内部执行定时器，计算完成后调用 `resolve` 将结果传递出去。

2\. **链式调用**
- 调用该函数时，不再传入回调，而是通过 `.then()` 方法接收结果。
- 如果需要连续计算，只需在第一个 `.then()` 中 `return` 一个新的 Promise，即可继续链式调用第二个 `.then()`。
- **示例逻辑**：`calc(1, 2).then(res => calc(res, 3)).then(res => calc(res, 4))...`

3\. **优缺点分析**
- **优点**：
  - 成功解决了回调地狱问题，代码结构变得扁平化。
  - 每一步的逻辑非常清晰，如果某一步断开或报错，可以很容易地定位到具体的 `.then()` 节点。
- **缺点**：
  - 虽然比回调函数简便，但代码依然显得繁琐。
  - 需要编写大量的 `.then()` 和回调函数，代码可读性仍有提升空间。

## 阶段三：Generator (生成器) *Content-[08:40]

Generator 是 `async/await` 的底层基础，但在实际开发中较少直接使用。

1\. **基本定位**
- `async/await` 的底层原理其实就是 Generator 加上**自动执行器**。
- Generator 函数本身需要**手动调用执行**（通过不断调用 `.next()` 方法来推进状态）。

2\. **跳过原因**
- 因为实际开发中我们直接使用带有自动执行器的 `async/await`，不需要手动控制执行流程，所以在此不做重点展开，直接过渡到最终方案。

## 阶段四：async/await *Content-[09:12]

这是目前现代前端开发中最主流、最推荐的异步解决方案。

1\. **代码实现**
- 使用 `async function` 定义异步函数，内部使用 `await` 关键字等待 Promise 的结果。
- **示例逻辑**：
  ```javascript
  async function start() {
      let res1 = await calc(1, 2); // 等待1秒，得到3
      let res2 = await calc(res1, 3); // 等待1秒，得到6
      let res3 = await calc(res2, 4); // 等待1秒，得到10
  }
  start(); // 必须手动调用一次初始函数
  ```

2\. **底层原理**
- `async/await` 内部使用的依然是 Promise。
- 当代码执行到 `await` 时，会将其后面的代码（或表达式）**包装成 Promise 对象**。
- 这会强制让当前的异步代码进入**暂停状态**，并将后续的执行逻辑推入**微任务队列 (Micro Task Queue)** 中等待执行。

3\. **核心优势**
- **同步的写法，异步的逻辑**：代码看起来就像普通的同步代码一样自上而下执行，极大地改善了代码的可读性。
- **错误处理更友好**：可以方便地使用 `try...catch` 进行统一的错误捕获。
- **彻底告别繁琐**：相比 Promise 的链式调用，代码更加简洁、直观。

4\. **注意事项**
- 虽然 `async` 函数被称为“自动执行器”（遇到 `await` 会自动暂停和恢复），但**定义完 `async` 函数后，仍需手动调用一次**（如 `start()`），否则代码不会开始执行。

## 社区方案与未来展望 *Content-[11:29]

1\. **Observable (可观察对象)**
- 除了 ES 官方标准外，社区还推出了 Observable 方案（常用于 RxJS 等响应式编程库）。
- 它目前属于社区过渡方案，并非 ES 官方标准语法。

2\. **开发建议**
- 在实际业务开发中，遇到“异步变同步”的需求，**务必首选 `async/await`**。
- 掌握异步代码的发展历程，有助于深刻理解 JS 的事件循环和底层运行机制，这也是前端面试中的高频考点。
