## 核心概念与基础用法 *Content-[00:33]

`setTimeout` 和 `setInterval` 是 JavaScript 浏览器环境中用于处理异步或定时任务的基础 API。尽管它们看起来简单，但在实际开发中如果不了解其背后的机制，很容易踩坑。

### 核心定义
- **`setTimeout`**：接收一个回调函数和一个 `delay`（延迟时间，单位为毫秒）。作用是在指定的延迟时间之后**执行一次**给定的回调函数。它会返回一个数字 ID，可用于取消这次计划好的执行。
- **`setInterval`**：接收类似的回调函数和 `delay` 参数。区别在于它会**每隔指定的时间间隔重复执行**给定的回调函数。同样返回一个数字 ID，用于取消重复执行的任务。

### 为什么需要定时器？
JavaScript 是默认单线程的，同一时间只能处理一个任务。如果一个任务非常耗时，会阻塞主线程，导致页面无法响应（即“假死”）。定时器的核心目的是通过将任务放入队列中，利用事件循环（Event Loop）机制安排任务在未来某个时间点执行，从而实现异步调度，防止 UI 冻结，保持页面流畅。

### 实际用途
- 延迟显示弹窗
- 实现复杂的动画效果
- 周期性向服务器轮询数据
- 作为更高级异步模式的基础

### 基本代码示例

**`setTimeout` 示例：**
```javascript
function greet(name) {
  console.log(`Hello, ${name}`);
}

// ES5 引入的特性：第三个参数可直接作为参数传递给回调函数
const timerId = setTimeout(greet, 2000, 'World'); 

// timerId 是非零的正整数
// 可以在指定时间到来前取消执行
// clearTimeout(timerId); 
```

**`setInterval` 示例：**
```javascript
let count = 0;
const intervalId = setInterval(() => {
  count++;
  console.log(`当前次数: ${count}`);
  if (count >= 5) {
    clearInterval(intervalId); // 达到 5 次后停止任务
  }
}, 1000); // 每隔 1000ms (1秒) 执行一次
```

## 陷阱一：定时器延迟不精确 *Content-[05:16]

最容易被误解的陷阱是认为定时器的 `delay` 是一个精确的保证值。

### 延迟的真实含义
`delay` 参数指的是将回调函数添加到消息队列中的**最小延迟时间**。它决定了浏览器何时把你的函数排队，而实际的执行时间受事件循环影响。

### 影响实际执行时间的因素
1. **主线程繁忙**：如果主线程正忙于执行其他耗时任务（如复杂的同步计算或渲染大量动画），即使 `delay` 时间到了，回调函数也只能在消息队列中排队，等待主线程空闲后才被执行。因此，**实际的延迟时间总是大于或等于指定的 `delay`**。
2. **最小延迟限制**：在大多数现代浏览器中，为了避免过度消耗 CPU 资源（尤其是对于连续或嵌套的定时器调用），存在一个最小延迟限制（通常为 **4ms**）。这意味着即使你设置 `delay` 为 0，实际添加到队列的时间也不会立即发生。

## 陷阱二：setInterval 导致的任务堆积 *Content-[07:01]

这个陷阱与 `setInterval` API 紧密相关。

### 任务堆积场景
假设设置了一个 `setInterval`，`delay` 为 100ms，但回调函数本身需要 200ms 才能执行完毕：
1. 100ms 时，第一个回调任务被添加到消息队列并开始执行，持续 200ms。
2. 在这 200ms 内，第二个、第三个 100ms 时间点已经过去。
3. 浏览器会根据 `delay` 继续将第二个、第三个回调任务添加到消息队列中。

### 后果
当耗时任务执行完毕、主线程空闲时，消息队列里可能已经排了好几个相同的回调任务实例。它们会一个接一个地被拉进 Call Stack（调用栈）中执行，不再遵守最初设定的 100ms 间隔。这会导致间隔失控，如果任务持续耗时，队列越积越多，最终可能导致性能急剧下降甚至程序崩溃。

### 解决方案：使用递归的 `setTimeout`
核心思想是：当前次的 `setTimeout` 回调执行完毕后，再根据需要调用下一个 `setTimeout` 来调度下一次执行。这样无论任务本身耗时多久，下一次执行总是基于上一次完成的时间来计算延迟，保证每次执行之间有相对稳定的间隔。

```javascript
function recursiveTimeout() {
  console.log('执行任务');
  
  // 模拟耗时 200ms 的操作
  const start = Date.now();
  while (Date.now() - start < 200) {}
  
  // 任务执行完毕后，再调度下一次
  setTimeout(recursiveTimeout, 100);
}

// 启动递归定时器
setTimeout(recursiveTimeout, 100);
```
*注：即使任务本身耗时 200ms，加上设定的 100ms 延时，两次任务执行之间的实际总间隔大约是 300ms，有效防止了任务堆积。*

## 陷阱三：this 指向问题 *Content-[10:55]

在传统的 JavaScript 函数中，`this` 的值是在函数被调用时确定的，取决于函数的调用方式。

### 问题表现
当把一个对象的方法作为回调函数传递给 `setTimeout` 或 `setInterval` 时，如果在回调函数内部使用 `function` 关键字定义，回调执行时 `this` 默认会指向全局对象（在浏览器中通常是 `window`，在严格模式下是 `undefined`）。这会导致无法在定时器内部通过 `this` 访问到原始对象上的属性或方法。

```javascript
class MyClass {
  constructor() {
    this.value = 42;
  }
  
  methodWithProblem() {
    setTimeout(function() {
      console.log(this.value); // 报错或输出 undefined
    }, 1000);
  }
}
```

### 解决方案

**1. 使用箭头函数（最推荐）**
ES6 引入的箭头函数没有自己的 `this` 绑定，它会捕获被定义时所处的父级作用域的 `this` 值。
```javascript
  methodWithArrow() {
    setTimeout(() => {
      console.log(this.value); // 正确指向 MyClass 实例，输出 42
    }, 1000);
  }
```

**2. 使用 `bind` 方法**
`bind` 会创建一个新的函数，其 `this` 值会被永久绑定到指定的第一个参数上。
```javascript
  methodWithBind() {
    setTimeout(function() {
      console.log(this.value); // 正确指向 MyClass 实例
    }.bind(this), 1000);
  }
```

**3. 使用外部变量保存引用**
在外部变量中保存 `this` 的引用（如 `const self = this`），然后在回调中使用 `self`。

## 陷阱四：忘记取消定时器 *Content-[15:30]

这是一个常见但非常重要的陷阱，特别是对于 `setInterval`。

### 潜在危害
- **`setInterval`**：如果不显式调用 `clearInterval`，它会一直运行下去。即使应用状态已改变或相关 UI 已被移除，仍会持续消耗 CPU 资源。
- **`setTimeout`**：如果原计划执行的回调在实际执行前已经不必要（例如用户在延迟结束前切换了页面），未及时取消可能导致不必要的代码执行，甚至尝试操作已经不存在的 DOM 元素从而导致报错。

### 解决方案
利用 `setTimeout` 和 `setInterval` 返回的数字 ID，使用 `clearTimeout(id)` 和 `clearInterval(id)` 来取消对应的定时器。

```javascript
let intervalId = null;

function startPolling() {
  intervalId = setInterval(() => {
    console.log('轮询数据...');
  }, 1000);
}

function stopPolling() {
  if (intervalId) {
    clearInterval(intervalId);
    intervalId = null; // 清理为 null，防止重复清理
  }
}
```

### 框架中的最佳实践
在现代前端框架（如 React 或 Vue）开发组件时，必须在组件生命周期的清理阶段及时清理定时器，这是防止内存泄漏和非预期行为的最佳实践。
- **React**：在 `useEffect` 的返回函数中清理，或在类组件的 `componentWillUnmount` 中清理。
- **Vue**：在 `onUnmounted` 或 `beforeDestroy` 生命周期钩子中清理。

## 课程总结 *Content-[17:40]

本节课深入探讨了 `setTimeout` 和 `setInterval` 的四个主要陷阱及应对策略：
1. **延迟不精确**：`delay` 只是最小延迟时间，实际执行受事件循环和浏览器最小延迟限制（如 4ms）影响。需深入理解事件循环机制。
2. **任务堆积**：`setInterval` 在回调耗时过长时会导致任务堆积。对于高频或耗时任务，优先考虑使用**递归 `setTimeout`**。
3. **`this` 指向丢失**：定时器回调中的 `this` 默认指向全局。利用**箭头函数**或 **`bind` 方法**可有效解决此问题。
4. **忘记取消定时器**：会导致资源浪费和内存泄漏。始终记得在不需要时（尤其是组件销毁时）**清理定时器**。
