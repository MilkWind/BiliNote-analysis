## 1. 异步编程与 Promise 简介 *Content-[00:01]

### Promise 的核心概念
在 ES6 中，`Promise` 是一个非常核心的知识点。它的官方解释是**异步编程的解决方案**，相比于传统的回调函数和事件机制，`Promise` 提供了更合理、更强大的异步处理方式。在深入理解 `Promise` 之前，必须先了解传统回调函数解决异步编程时存在的最大弊端。

### 什么是异步编程？
异步代码（Asynchronous Code）是指不随着主线程阻塞执行的代码。它不会阻塞主线程，而是等到特定条件触发时再去执行。
常见的异步编程场景包括：
- 定时器（如 `setTimeout`）
- 事件监听（Event Listeners）
- Web Workers（多线程）
- 网络请求（Ajax/Fetch）等

### 经典面试题：同步与异步的执行顺序
视频中出现了一道经典的执行顺序面试题，用于测试对异步编程的理解：

```javascript
console.log(1);
setTimeout(() => {
    console.log(2);
}, 0);
console.log(3);
```

- **错误答案**：1, 2, 3（答错意味着基础不牢，需要重新复习）。
- **正确答案**：1, 3, 2。
- **原理解析**：
  1. 代码首先执行主线程的同步代码，因此先打印 `1`。
  2. 遇到 `setTimeout`，将其放入异步任务队列中（即使延迟时间设置为 `0`，也必须等同步代码执行完毕）。
  3. 继续执行同步代码，打印 `3`。
  4. 主线程同步代码执行完毕，去异步队列中取出任务，打印 `2`。

## 2. 回调函数在异步中的应用 *Content-[02:29]

### 异步计算求和的需求场景
假设有一个计算求和的需求，为了模拟计算耗时，使用 `setTimeout` 设置 1 秒的延迟：

```javascript
function sum(a, b, callback) {
    setTimeout(() => {
        let result = a + b;
        callback(result);
    }, 1000);
}
```

**需求**：计算完上一步的结果后，拿着上一步的结果继续加下一个数（例如：先算 1+2，再用结果加 3）。

### 直接获取返回值的误区
如果尝试直接获取返回值：
```javascript
let result = sum(1, 2); 
console.log(result + 3); // 错误：此时 result 还未计算出来
```
**错误原因**：`sum` 函数内部是异步代码，而外部的 `console.log` 是同步代码。同步代码会立即执行，此时 `result` 还没有被赋值（或者说返回的是 `undefined`），无法得到 1 秒后的计算结果。在异步函数中直接写 `return` 也是无效的，因为 `return` 返回给的是当前的同步执行上下文，而不是 1 秒后的异步回调。

### 使用回调函数（Callback）解决依赖
为了解决“等待上一步结果”的问题，传统方式是在函数中传入一个**回调函数（Callback）**。等到异步操作执行完毕，再调用这个回调函数并将结果传递出来：

```javascript
// 第一次计算
sum(1, 2, (result) => {
    console.log("第一次计算结果:", result); // 1秒后打印 3
    
    // 第二次计算，使用上一次的 result
    sum(result, 3, (result) => {
        console.log("第二次计算结果:", result); // 再1秒后打印 6
        
        // 第三次计算...
        sum(result, 4, (result) => {
            console.log("第三次计算结果:", result);
        });
    });
});
```
通过这种方式，可以确保每一步都在上一步计算完成后才执行，完美解决了异步数据依赖的问题。

## 3. 回调地狱的产生与弊端 *Content-[06:22]

### 回调地狱的代码表现
如果需求需要连续进行多次计算（例如嵌套到第 9 次），代码结构会变成如下形式：

```javascript
sum(1, 2, (result) => {
    sum(result, 3, (result) => {
        sum(result, 4, (result) => {
            sum(result, 5, (result) => {
                // ... 一直嵌套到第 9 次
            });
        });
    });
});
```

这种代码在视觉上呈现出严重的**阶梯状**，被网友们形象地调侃为 **“动感光波”**。这种回调函数嵌套过深的现象，在开发中被称为**回调地狱（Callback Hell）**。

### 回调地狱的核心弊端
回调地狱最大的问题**不在于代码格式不好看**，而在于**极不方便维护，维护成本非常高**：

1. **排错极其困难**：代码层层嵌套，小括号和大括号交错。如果中间某一行（例如第 76 行）报错，开发者需要一层一层地去匹配括号，寻找错误位置，过程非常令人崩溃。
2. **业务逻辑不清晰**：实际开发中，每一次嵌套的需求和逻辑可能都不一样，不像示例中那样规整。嵌套过深导致业务逻辑被掩盖在缩进之中。
3. **形象比喻**：老师用“冬天穿裤子”来比喻回调地狱的嵌套之深。就像里面穿秋裤，秋裤套毛裤，毛裤套棉裤，棉裤套绒裤，最外面再套裤子。如果此时腿痒了，需要先把绒裤脱了，再脱棉裤、毛裤、秋裤才能挠到痒处。这种“一层套一层”的结构导致修改和调试（“挠痒”）变得异常痛苦。

## 4. 总结与引出 Promise *Content-[09:32]

### 痛点总结
使用回调函数解决异步编程虽然可行，但当异步操作存在复杂的依赖关系时，必然会导致**回调函数嵌套过深**，从而引发**回调地狱**。这会导致代码可读性极差、维护成本极高、错误排查困难。

### 引出 ES6 Promise
正是因为传统回调函数存在上述致命缺陷，ES6 才引入了 `Promise`。`Promise` 的核心目的之一就是**解决回调地狱问题**，通过链式调用（`.then()`）的方式，将深层嵌套的回调函数扁平化，从而大幅提升异步代码的可读性和可维护性。

1. **异步编程基础**：明确了异步代码不阻塞主线程的特性，并通过 `setTimeout` 的经典示例（输出 1, 3, 2）巩固了同步与异步的执行顺序。
2. **回调函数的应用与局限**：展示了在异步操作中，为了获取上一步的计算结果，必须使用回调函数（Callback）来传递数据。
3. **回调地狱的痛点**：当多个异步操作存在依赖关系时，回调函数的层层嵌套会导致代码呈“阶梯状”（动感光波）。其最大弊端并非视觉上的不美观，而是导致代码极难维护、括号匹配困难、排错成本极高。
4. **承上启下**：正是为了解决回调函数嵌套过深带来的“回调地狱”问题，ES6 引入了 `Promise`，开启了前端异步编程的新范式。
