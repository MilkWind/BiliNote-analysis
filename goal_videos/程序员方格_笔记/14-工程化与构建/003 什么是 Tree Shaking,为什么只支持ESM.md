## 1. 引言与背景 *Content-[00:00]

- 在前端开发中，我们经常会引入大量的第三方库和模块，但很多时候只使用了其中的一小部分功能。
- 如果将所有引入的代码都打包进最终产物，无疑会大幅增大应用的体积，严重影响页面的加载性能。
- **Tree Shaking** 是前端工程化和性能优化中一个非常重要的概念，其核心目的就是剔除无用代码，为我们的应用“减负”。

## 2. Tree Shaking 的核心思想 *Content-[00:45]

- **树的比喻**：
  - **树根**：应用的入口文件（如 `main.js` 或 `app.js`）。
  - **枝干**：从入口文件开始，通过 `import` 语句引入的各种模块。
  - **枯叶**：模块文件中定义了许多函数或变量，但在应用中从未被使用过的代码。它们就像树上枯萎、没有生命力的叶子。
- **核心动作**：Tree Shaking 字面意思就是“摇晃树木”，让枯叶自行脱落，只保留真正有生命力、对应用有用的部分。
- **技术本质**：在代码的编译阶段，通过**静态分析**找到并移除那些永远不会被执行的死代码（Dead Code）。因此，它本质上是一种**死代码消除（Dead Code Elimination）** 技术。

## 3. Tree Shaking 的两个关键前提 *Content-[02:26]

Tree Shaking 的实现必须建立在以下两个关键前提之上，缺一不可：

1. **ES Module (ESM) 模块系统**：这是最根本的前提。ESM 具有非常重要的“静态”特性，使得在代码运行前就能确定模块的导入和导出。
2. **构建工具的支持**：需要像 Webpack 或 Rollup 这样的构建工具来执行分析过程。它们内部包含对代码进行分析和处理的能力，从入口文件遍历依赖图，标记出哪些是实际用到的“活代码”，哪些是未用到的“死代码”。

## 4. 为什么 ESM 的静态结构是关键 *Content-[03:45]

ESM 的静态特性是 Tree Shaking 能够生效的基石，具体体现在 `import` 和 `export` 语法的严格限制上：

- **ESM 的静态限制**：`import` 和 `export` 语句必须写在模块的**顶层作用域**，不能放在 `if` 判断或函数内部调用。
- **编译时分析**：因为这种限制，构建工具完全不需要运行代码，只需通过词法分析读取 `import` 和 `export` 关键字，就能 100% 确定模块之间的依赖关系，构建出精确完整的依赖图谱。
  - *示例*：`import { a, b } from './utils.js'`，工具在编译时一眼就能看出需要从 `utils.js` 获取 `a` 和 `b`。
- **对比 CommonJS 的动态性**：
  - CommonJS 的 `require` 是动态语句，可以写在 `if (condition) { require('./utils.js') }` 中。
  - 在编译时，工具无法知道 `condition` 的真假，因此无法确定是否会执行 `require`，也不知道具体的路径。这些信息只有在代码实际运行时才能确定。
  - 这种动态性让编译时的静态依赖分析变得几乎不可能，因此 CommonJS 无法有效支持 Tree Shaking。

## 5. 构建工具的工作流程：标记与清除 *Content-[06:09]

在 ESM 的基础上，构建工具执行 Tree Shaking 的工作流程分为两个阶段：

- **阶段一：标记 (Mark)**
  - 构建工具从入口文件开始，像侦探一样顺着 `import` 链条遍历所有模块。
  - 检查每一个被导入的模块，分析其中有哪些函数或变量被真实地调用或引用。
  - 所有被实际使用到的代码，都会被打上 **Live Code（活代码）** 的标记。
- **阶段二：清除 (Sweep)**
  - 标记结束后，代码库被分为两部分：被标记的 Live Code 和未被标记的 **Dead Code（死代码）**。
  - 在生成最终打包文件时，工具只会打包标记为 Live Code 的部分。
  - 所有未被标记的 Dead Code 都会被无情抛弃，仿佛从未存在过。

**具体示例说明**：
- 假设 `utils.js` 中定义了 `add`、`subtract`、`multiply` 三个函数。
- 入口文件 `main.js` 中仅通过 `import` 导入了 `add` 函数并进行了调用，完全没有碰另外两个函数。
- **打包结果**：构建工具在标记阶段将 `add` 标记为 Live Code，而 `subtract` 和 `multiply` 未被标记。在清除阶段，后两个函数会从最终产物中完全消失，只保留 `add` 函数及其调用逻辑，从而有效减小代码体积。

## 6. 实际开发中的阻碍：副作用 (Side Effects) *Content-[09:41]

理论上 Tree Shaking 非常完美，但在实际开发中有时会发现它未按预期工作，最常见的原因是**副作用**。

- **什么是副作用**：如果一个模块在被 `import` 时，不仅仅是提供函数或变量，还会执行一些改变外部环境的操作，那么这个模块就具有副作用。
- **典型的副作用场景**：
  - 修改全局变量或 `window` 对象。
  - 像 Polyfill 那样修改原生对象的原型。
  - 向 DOM 中添加元素。
  - 注入样式（例如：模块被导入时，创建一个 `style` 标签并插入到页面的 `head` 标签中，从而改变页面背景色）。
- **构建工具的困境**：构建工具虽然智能，但无法读取业务逻辑去判断一个副作用操作对应用是否必须。出于**安全第一**的考虑，只要检测到模块可能有副作用，哪怕你没有从该模块中 `import` 任何具体代码，工具也不敢轻易将其移除。

## 7. 解决副作用问题：sideEffects 配置 *Content-[11:59]

为了帮助构建工具做出更准确的判断，让 Tree Shaking 发挥最大威力，开发者（尤其是库作者）可以在 `package.json` 中配置 `sideEffects` 字段。

- **方案一：全局声明无副作用**
  - 配置：`"sideEffects": false`
  - 含义：向构建工具承诺该库中所有代码都是纯的，没有任何副作用。
  - 效果：工具可以放心大胆地进行 Tree Shaking，只要导出的模块没被使用，就尽管删除。这对于纯计算类或工具类库是必要的配置。
- **方案二：精确列出有副作用的文件**
  - 配置：`"sideEffects": ["./src/some-side-effect-file.js", "*.css"]`（使用数组形式）
  - 含义：明确告知构建工具，库中确实有一部分文件（如样式注入脚本、CSS 文件本身）是有副作用的，必须保留。
  - 效果：除了数组中列出的文件外，库里的其他所有静态文件依然被视为无副作用，构建工具可以继续对它们进行 Tree Shaking 优化。
  - 优势：在保证功能正确的前提下，最大化 Tree Shaking 的优化效果。

## AI 总结

Tree Shaking 是前端性能优化中用于消除死代码（Dead Code）的核心技术。它依赖于 ESM 模块的静态特性以及 Webpack/Rollup 等构建工具的依赖分析能力，通过“标记”和“清除”两个阶段，剔除未使用的代码以减小打包体积。然而，模块的“副作用”会阻碍这一过程，因为工具无法判断副作用是否必要。通过在 `package.json` 中合理配置 `sideEffects` 字段（设为 `false` 或指定具体文件数组），可以明确告知构建工具哪些代码是安全的，从而在确保功能正常的前提下，实现极致的代码体积优化。
