## 核心思想与概念 *Content-[00:45]
- **树的比喻**：将应用代码结构想象成一棵树，树根是应用的入口文件（如 `main.js`）。通过 `import` 语句引入的各种模块就像树上伸展出的枝干。
- **枯叶与落叶**：模块文件中定义了许多函数或变量，但应用中可能只用到其中一两个。那些被定义但从未使用过的代码，就像树上枯萎、没有生命力的叶子。Tree Shaking 的过程就像摇晃大树，让枯叶自行脱落，只保留真正有生命力、对应用有用的部分。
- **技术本质**：在代码的编译阶段，通过静态分析找到并移除那些永远不会被执行的 Dead Code（死代码）。其本质上就是一种死代码消除技术，目的是为应用减负，减小打包体积，提升加载性能。

## 工作原理与关键前提 *Content-[02:26]
Tree Shaking 的实现建立在两个关键前提之上，必须同时满足才能生效：
- **前提一：ES Module (ESM) 模块系统**。ESM 具有“静态”特性，这意味着在代码实际运行之前（仅仅在编译阶段），工具就能准确地知道一个模块导入和导出了什么。
- **前提二：构建工具的支持**。需要 Webpack 或 Rollup 等构建工具来执行分析和处理。这些工具会从入口文件开始遍历整个依赖图，像做记号一样标记出实际被用到的 Live Code（活代码）和没有被用到的 Dead Code（死代码）。

## ESM 静态结构的重要性 *Content-[03:45]
ESM 的静态结构是 Tree Shaking 能够可靠进行的关键点：
- **严格的语法限制**：ESM 的 `import` 和 `export` 语法必须写在模块的顶层作用域，不能放在 `if` 判断或函数内部调用。
- **编译时依赖分析**：因为上述限制，构建工具完全不需要运行代码，只需通过词法分析读出 `export` 和 `import` 关键字，就能 100% 确定模块之间的依赖关系，构建出精确完整的依赖图谱。
- **对比 CommonJS**：CommonJS 中的 `require` 是动态语句，可以写在 `if` 语句中。在编译时，工具无法知道 `if` 条件的真假，因此无法确定是否会执行 `require` 以及具体的路径。这些信息只有在代码实际运行时才能确定。因此，CommonJS 的动态性让静态分析变得几乎不可能，无法支持 Tree Shaking。

## 构建工具的操作流程 *Content-[06:09]
构建工具执行 Tree Shaking 的工作流程分为两个阶段：
- **标记阶段**：构建工具从入口文件开始，顺着 `import` 链条遍历所有模块。检查每一个被导入的模块，分析其中哪些函数或变量被真实地调用或引用。所有被实际使用到的代码都会被打上 Live Code 的标记。
- **清除阶段**：标记结束后，代码库分为被标记的 Live Code 和未标记的 Dead Code。在生成最终打包文件时，工具只打包标记为 Live Code 的部分，所有未标记的 Dead Code 都会被无情抛弃。
- **具体示例**：
  - 假设 `utils.js` 中定义了 `add`、`subtract`、`multiply` 三个函数。
  - `main.js` 入口文件中只通过 `import` 导入了 `add` 函数并进行了调用，完全没有碰过另外两个函数。
  - 构建工具分析后，将 `add` 标记为 Live Code，`subtract` 和 `multiply` 不被标记。
  - 最终打包结果中，另外两个函数完全消失，只保留了 `add` 函数及 `main.js` 中的调用逻辑，从而有效减小了代码体积。

## 副作用 Side Effects 对 Tree Shaking 的影响 *Content-[09:41]
在实际开发中，Tree Shaking 有时未按预期工作，最常见的原因是“副作用”：
- **副作用的定义**：如果一个模块在被 `import` 时，不仅提供函数或变量，还会执行一些改变外部环境的操作，则该模块具有副作用。
- **典型的副作用操作**：修改全局变量或 `window` 对象、修改原生对象的原型（如 Polyfill）、向 DOM 中添加元素等。
- **构建工具的保守策略**：构建工具无法读取业务逻辑来判断副作用操作是否必须。出于安全第一的考虑，只要检测到模块可能有副作用，它就不敢轻易移除该模块，哪怕你没有从该模块中 `import` 任何具体变量。
- **副作用示例**：一个文件没有 `export` 任何内容，唯一作用是在被 `import` 时创建 `style` 标签并插入页面的 `head` 标签中以改变背景色。这是典型的副作用模块，构建工具会保留该文件在最终打包结果中。

## 如何优化 Tree Shaking 效果 *Content-[11:59]
为了帮助构建工具做出更准确的判断，让 Tree Shaking 发挥最大威力，开发者（尤其是库作者）可以在 `package.json` 中配置 `sideEffects` 字段：
- **方案一：全局声明无副作用**。将 `sideEffects` 设置为 `false`。这相当于向构建工具承诺库中所有代码都是纯的，没有任何副作用。只要导出的模块没被使用，就可以放心删除。这对于纯计算工具类库是必要的配置。
- **方案二：精确指定副作用文件**。如果库中确实有一部分文件有副作用（如样式注入脚本或 CSS 文件），可以在 `sideEffects` 字段中提供一个数组，列出这些确实需要保留副作用的文件。除此之外的其他所有静态文件依然被视为无副作用，构建工具可对它们进行 Tree Shaking 优化。这种方式在保证功能正确的前提下，最大化了 Tree Shaking 的效果。

## AI 总结
Tree Shaking 是前端性能优化中消除死代码（Dead Code）的核心技术。它依赖于 ESM 的静态特性以及 Webpack/Rollup 等构建工具的标记与清除机制，能够在编译阶段精准剔除未使用的代码以减小打包体积。然而，模块的副作用（Side Effects）会阻碍这一过程，因为构建工具出于安全考虑会保留可能改变外部环境的代码。开发者可以通过在 `package.json` 中合理配置 `sideEffects` 字段（设为 `false` 或指定副作用文件数组），来引导构建工具安全、最大化地进行 Tree Shaking 优化。
