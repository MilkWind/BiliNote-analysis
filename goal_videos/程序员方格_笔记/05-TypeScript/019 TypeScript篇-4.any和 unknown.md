## 为什么需要处理未知类型 *Content-[00:00]

TypeScript 的核心优势在于其强大的类型系统，但在真实的软件开发中，数据的来源并不局限于我们自己编写的代码。以下是常见的需要处理未知类型的场景：

- 使用没有提供 TS 类型声明的旧版 JS 库。
- 通过后端 API 获取数据，其数据结构可能非常复杂甚至是动态变化的。
- 用户直接输入的内容（如表单提交），在数据被校验之前类型是不确定的。
- 解析 JSON 字符串或从 `localStorage` 中读取数据，这些操作在初始阶段的数据类型都是未知的。

这些场景共同引出了一个核心问题：如何在处理类型不确定的数据时，既能保证代码的灵活性，又不会放弃 TS 提供的宝贵的类型安全。`any` 和 `unknown` 就是 TS 针对这个问题给出的两种不同答案。

## any 类型的特性与缺陷 *Content-[02:15]

`any` 类型的作用非常直接，它告诉 TS 编译器不要对值进行任何类型检查，本质上是在一小块代码区域里关闭了类型系统。

**核心特性：**
1. 一个 `any` 类型的变量可以被赋值成任何类型的值（如数字、字符串、布尔值等）。
2. 可以对该变量调用任何方法、访问任何属性，即使它们根本不存在。
3. 编译器对此完全放行，不会给出任何错误或警告。

**代码示例分析：**
定义一个类型为 `any` 的 `flexible` 变量，可以随意将数字或字符串赋值给它。如果调用一个完全不存在的方法，在 TS 编译阶段是完全合法的。但在实际运行时，它会立刻抛出错误（如提示“不是一个函数”）。同样，访问不存在的属性也不会在编译时报错，但运行时可能会受到影响。`any` 提供了极大的灵活性，但代价是牺牲了编译时的安全。

## any 带来的具体问题分析 *Content-[04:09]

社区普遍建议谨慎使用 `any`，因为它会带来以下具体问题：

1\. **类型污染 (Type Pollution)**
从 API 获取数据并标记为 `any`，从中取出属性赋值给 `string` 类型的变量。因为 `data` 是 `any`，TS 编译器无法确认 `data.name` 是否为字符串，只能选择信任。此时 `username` 变量虽有 `string` 注解，但并未得到类型系统的保护。如果 API 返回的 `data.name` 恰好是数字或 `null`，后续调用 `toUpperCase()` 就会在运行时报错。`any` 的影响会从一个变量传播到另一个变量。

2\. **失去 IDE 支持，影响开发体验**
当变量是 `any` 类型时，代码编辑器无法提供有用的代码补全和类型提示。访问属性必须完全靠记忆手打，极易拼错方法或变量名。在进行代码重构（如修改属性名）时，IDE 无法自动更新所有 `any` 类型对象上的引用，非常容易遗漏。

3\. **运行时错误难追踪**
类型错误不会在数据源头被发现，而是推迟到代码的下游环节真正使用该值时才出现问题。这使得调试变得非常困难，需要回溯整个调用链才能找到问题的根源。

总而言之，`any` 会在类型系统中打开一个缺口，削弱 TS 的核心能力与价值。

## unknown 类型：安全的替代方案 *Content-[06:45]

`unknown` 是在 TS 3.0 中引入的，可以看作是 `any` 的安全对应版本。它的核心设计理念是：可以像 `any` 一样接收任何类型的值，但在对其进行任何操作之前，必须先通过类型检查来确定其具体类型。

**any 与 unknown 的直观比较：**
- **接收任何值**：两者相同，都具备灵活性。
- **直接使用**：`any` 可以直接使用，`unknown` 不行。
- **类型检查**：`any` 不需要任何类型检查，`unknown` 强制要求类型检查。
- **类型安全**：`any` 是不安全的，`unknown` 是安全的。

**代码示例分析：**
定义一个 `unknown` 变量，试图直接调用 `toUpperCase()` 方法或将其赋值给 `string` 类型的变量时，TS 编译器会报错，提示类型是 `unknown`，不能对它做任何假设。
正确的做法是使用 `if (typeof myVar === 'string')` 进行检查。在 `if` 代码块里面，TS 会将该变量的类型收窄（Narrowing）为 `string`，此时再调用 `toUpperCase()` 就是完全类型安全的。这种强制的类型检查机制是 `unknown` 带来安全性的保障。

## 类型收窄 (Type Narrowing) 的常用方法 *Content-[08:53]

在使用 `unknown` 之前必须进行类型检查，TS 中有一个专门的术语来描述这个动作，叫做“类型收窄”。以下是几种实现类型收窄的常用方法：

1\. **`typeof` 操作符**
用于检查变量是否为 JS 的基础类型（如 `string`, `number`, `boolean`, `symbol`, `bigint`, `undefined`, `function`）。在 `if` 块内将类型收窄后，可安全调用对应方法。
*缺陷*：对于对象，无法区分 `null`、数组和普通对象。

2\. **`instanceof` 操作符**
用于判断一个对象是否是某个类的实例（如检查是否为 `Date` 对象）。这是处理对象比较高效的做法，在代码块内可安全调用该对象的方法。

3\. **类型断言 (Type Assertion)**
使用 `as` 关键字（如 `as number`）显式告诉编译器相信该值就是某种类型。这是一种强制的类型转换，绕过了编译器的检查。需要非常谨慎地使用，必须 100% 确定其类型，否则会导致运行时错误。

4\. **自定义类型守卫 (Type Guards)**
对于复杂的对象验证，可以编写一个返回特殊类型（如 `value is string`）的函数。当返回 `true` 时，TS 就知道传入的 `value` 在后续的 `if` 块里是特定类型，从而封装了验证逻辑。

5\. **`in` 操作符**
用于检查一个对象上是否具有某个特定属性，从而收窄对象类型。

6\. **等值检查**
进行简单的等值检查，例如 `value === null` 或 `value === undefined`，将其收窄为 `null` 或 `undefined` 类型。

## 最佳实践与项目建议 *Content-[12:45]

基于以上讨论，以下是使用 `any` 和 `unknown` 的最佳实践：

1\. **核心原则：能用 `unknown` 就别用 `any`**
当下意识想写 `any` 时，思考是否可以用 `unknown` 配合类型收窄来更安全地实现。

2\. **将 `unknown` 作为外部不可信数据的默认选择**
处理 API 响应、用户输入、JSON 解析结果等外部数据时，默认使用 `unknown` 进行定义。

3\. **限制 `any` 的使用范围**
`any` 只应在特殊、不得已的场景下使用（如迁移大型 JS 项目时的临时标记），后期一定要将其重构改掉，否则会留下隐患。

4\. **利用 ESLint 工具进行约束**
开启相关 ESLint 规则，在本地开发环境写 `any` 时直接报错，强迫开发者必须编写类型检查。

5\. **有计划地消灭现存的 `any`**
在 Code Review 时特别注意新增的 `any`。对于历史遗留的 `any`，创建任务逐步将其重构为具体类型或 `unknown`。

遵循这些原则，可以显著提升 TS 项目的健壮性和可维护性。

## AI 总结

本视频深入探讨了 TypeScript 中处理未知类型的两种核心方式：`any` 和 `unknown`。`any` 提供了极大的灵活性，但会关闭类型检查，导致类型污染、失去 IDE 支持以及运行时错误难以追踪等严重问题。作为替代，TS 3.0 引入了 `unknown` 类型，它同样能接收任何类型的值，但强制要求在进行操作前通过类型收窄（如 `typeof`、`instanceof`、类型断言、自定义类型守卫等）来确认具体类型，从而保障了类型安全。视频最后强调了最佳实践：在处理外部不可信数据时应默认使用 `unknown`，严格限制 `any` 的使用，并借助 ESLint 和 Code Review 逐步消除项目中的历史 `any`，以提升代码的健壮性与可维护性。
