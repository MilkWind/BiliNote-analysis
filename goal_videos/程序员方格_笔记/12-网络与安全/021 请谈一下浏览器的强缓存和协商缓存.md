## 1. 缓存的基本概念与演示 *Content-[00:00]
- **演示环境**：以访问百度网站为例。
- **强制加载（无缓存状态）**：
  - 操作：右键选择“强制加载”（Empty Cache and Hard Reload），清空浏览器所有缓存。
  - 结果：页面会访问大量资源（如 JS 文件），加载时间通常在 20多毫秒甚至几秒。
  - 结论：第一次访问时本地没有缓存，所有资源完全从服务器获取。
- **刷新页面（命中缓存状态）**：
  - 操作：再次刷新页面。
  - 结果：资源加载时间极快，几乎为 0ms。
  - 状态码：返回 200。
  - 提示：开发者工具中显示“来自内存缓存”（from memory cache），说明此时命中了强缓存。

## 2. 强缓存机制详解 *Content-[00:54]
- **命中表现**：
  - HTTP 状态码为 200。
  - 加载时间极短（0ms）。
  - 资源来源提示为“来自内存缓存”或“来自磁盘缓存”。
- **控制字段**：
  - 通过 Response Header（响应头）中的 `Cache-Control` 字段进行控制。
  - 常见配置示例：`Cache-Control: max-age=300`。
  - 作用机制：告诉浏览器该资源已被强缓存，在指定的时间内（如 300 秒）不需要向服务器发起请求，直接从本地读取资源。

## 3. 协商缓存机制详解 *Content-[01:53]
- **命中表现**：
  - HTTP 状态码为 304。
  - 加载时间相对较长（如演示中的图片加载耗时 572ms）。虽然比强缓存慢，但比无缓存直接下载要快。
- **控制字段**：
  - 主要通过 `ETag` 或 `Last-Modified` 字段来决定是否命中协商缓存。
- **工作流程**：
  - 当浏览器对某个资源的请求没有命中强缓存时，会发送请求到服务器验证协商缓存。
  - **命中协商缓存**：服务器返回 HTTP 状态码 304，响应不携带实体数据。浏览器确认本地文件可用后，直接从本地读取。
  - **未命中协商缓存**：服务器返回 HTTP 状态码 200，并携带资源的完整实体数据。浏览器接收数据并重新加载新资源。

## 4. 强缓存与协商缓存的区别与对比 *Content-[02:40]
### 4.1 强缓存的控制字段
- **Expires**：
  - HTTP/1.0 引入的缓存方案。
  - 服务端返回一个绝对的过期时间（如 `Expires: Wed, 21 Oct 2025 07:28:00 GMT`）。
  - 在时间范围内，浏览器直接从本地获取资源，不访问服务端。
- **Cache-Control**：
  - HTTP/1.1 引入，优先级高于 `Expires`，是目前项目中最常用的强缓存控制字段。
  - 常见指令：
    - `max-age=<seconds>`：设置相对缓存时间（如 `max-age=300` 表示缓存 300 秒，即 5 分钟）。
    - `no-store`：禁止缓存，每次都必须从服务器获取完整资源。
    - `no-cache`：不使用强缓存，但可以使用协商缓存。
    - `public`：表示响应可以被任何对象（包括客户端、代理服务器等）缓存。
    - `private`：表示响应只能被单个用户（浏览器）缓存，不能被代理服务器缓存。

### 4.2 协商缓存的工作机制
- 如果后台没有设置 `Cache-Control` 或 `Expires` 等强缓存 Header，请求会直接走协商缓存。
- **优势场景**：对于大文件（如大图片），协商缓存可以先向服务器询问文件是否过期。如果未过期（命中），则直接使用本地文件，避免重新下载大文件；如果过期，则返回 200 重新下载。这相当于用一次轻量级的网络请求换取了可能的全量下载。

## 5. 协商缓存的判断字段与对比 *Content-[06:21]
协商缓存主要通过以下两组字段进行判断，两者在精度和性能上各有侧重：
### 5.1 Last-Modified / If-Modified-Since
- **引入版本**：HTTP/1.0 引入（较老的方案）。
- **工作原理**：基于文件的最后修改日期进行对比。服务器返回 `Last-Modified`，浏览器后续请求带上 `If-Modified-Since`。如果服务器端文件的修改日期与请求头中的日期一致，则命中缓存。
- **优点**：性能较好，只需对比时间字符串。
- **缺点**：精度只能到秒。如果文件在 1 秒内被频繁修改，该方案无法准确判断文件内容是否发生了变化。

### 5.2 ETag / If-None-Match
- **引入版本**：HTTP/1.1 引入（较新的方案）。
- **工作原理**：基于文件内容生成指纹。服务器对文件内容进行哈希算法（Hash）计算，生成一段哈希值作为 `ETag`。浏览器后续请求带上 `If-None-Match`。如果服务器端重新计算的哈希值与请求头中的一致，说明文件内容无变化，命中缓存。
- **优点**：更精细，能够准确判断文件内容是否发生改变，彻底解决了 `Last-Modified` 精度不足的问题。
- **缺点**：性能不如 `Last-Modified`，因为每次文件变更都需要服务器重新计算哈希值，消耗一定的计算资源。
- **选择建议**：需要根据项目实际情况和文件改动频率综合选择。对于改动频繁且需要精确判断的文件，推荐使用 `ETag`。

## AI 总结 *Content-[07:54]
浏览器的缓存机制主要分为强缓存和协商缓存。强缓存通过 `Cache-Control`（HTTP/1.1）和 `Expires`（HTTP/1.0）控制，在缓存有效期内直接使用本地资源，状态码为 200，性能最高。当强缓存失效或未设置时，浏览器会发起协商缓存请求，通过 `ETag` 或 `Last-Modified` 向服务器验证资源是否更新。若未更新则返回 304 使用本地缓存，若已更新则返回 200 并下载新资源。`ETag` 基于内容哈希，精度更高；`Last-Modified` 基于修改时间，性能更好。在实际开发中，通常结合使用强缓存和协商缓存，以达到最优的加载性能与资源更新准确性。
