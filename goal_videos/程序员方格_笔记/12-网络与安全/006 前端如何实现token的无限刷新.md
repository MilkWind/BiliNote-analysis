## 核心思路 *Content-[00:00]
在 B 端管理系统的开发中，Token 的无感刷新是一个非常常见且重要的场景。在面试中回答此类场景题时，首先需要阐述清楚核心的解决思路。

- **核心目标**：在用户无感知的情况下，当访问令牌（Access Token）过期时，系统能够自动进行刷新，从而确保用户的操作不会被中断。
- **痛点分析**：如果没有实现无感刷新，当 Token 过期时，用户会被迫主动刷新页面或重新登录，然后再回溯到之前的操作页面，这会带来极差的用户体验。
- **理想流程**：系统在前端拦截到 Token 过期后，自动在后台完成刷新操作，刷新完成后继续调用用户之前想要发起的请求，使整个流程对用户透明且合理。
- **核心机制**：主要依赖于**双 Token 机制**来实现这一目标。

## 实现方案：双 Token 机制 *Content-[02:18]
基于上述核心思路，具体的实现方案依赖于双 Token 机制，即将 Token 分为短期和长期两种：

- **Access Token（访问令牌）**：
  - **有效期**：短期有效，通常设置为 15 到 30 分钟。
  - **作用**：用于与后端进行鉴权的标识，即作为 API 请求的认证凭证。
- **Refresh Token（刷新令牌）**：
  - **有效期**：长期有效，例如设置为 7 天。
  - **作用**：专门用于在 Access Token 过期时，向服务端请求获取新的 Access Token。

## 建立核心能力：TokenService *Content-[04:05]
在实际代码实现中，通常使用 Axios 作为请求库，因为它同时兼容 Node 端和浏览器端。为了实现无感刷新，需要封装一个核心的 `TokenService` 类，并在构造函数（`constructor`）中初始化以下关键能力：

- **`isRefreshing` 标识**：
  - 用于控制避免重复请求 Refresh Token。
  - 当发起刷新请求时，将其设为 `true`；后续并发请求发现该标识为 `true` 时，无需再次触发刷新逻辑，避免多次重复请求刷新接口。
- **`requests` 请求队列（Queue）**：
  - 用于暂存因 Token 过期而挂起的请求。
  - 当多个请求同时发现 Token 过期时，第一个请求触发刷新，后续请求则被包裹成 Promise 存入队列。
  - 待获取到最新 Token 后，重新执行队列中的请求，避免请求被抛弃或遗漏，保证请求的完整性。

## Axios 实例与请求拦截器 *Content-[06:10]
在 `TokenService` 中，首先需要初始化 Axios 实例，并配置 `baseURL`、`timeout` 等基础参数。随后，通过**请求拦截器**（Request Interceptor）来统一处理 Token 的注入：

- **获取 Token**：在每次请求发出前，从本地存储（Storage）中读取 Token。
- **注入 Header**：如果 Token 存在，则将其追加到请求的 `header` 中（例如通过 `Authorization` 字段）。
- **作用**：由于前后端交互通常是无状态的，通过 Header 传递 Token 可以让服务端识别当前请求的用户身份，避免每次请求都进行登录鉴权，开发者也无需在每个具体的请求中手动追加 Token。

## 响应拦截器与 Token 过期处理 *Content-[09:52]
**响应拦截器**（Response Interceptor）是处理无感刷新的核心部分，主要着重处理 Error 场景下的 Token 过期逻辑：

- **约定过期状态**：与后端约定 Token 过期的状态码（例如 HTTP 状态码 401，或业务状态码 4001，以及 `response.data.code` 为 `token_expired`）。
- **排除刷新接口**：必须排除刷新 Token 接口本身的报错。如果是刷新接口返回错误，说明 Refresh Token 也失效了，此时应直接清除本地 Token 并走登出逻辑，避免陷入死循环。
- **请求入队**：对于普通的业务接口报错（Token 过期），将当前失败的请求配置（`config`）包裹在一个 Promise 中，并存入之前定义的请求队列中暂存。

## 处理请求队列与刷新逻辑 *Content-[14:22]
当请求被暂存后，需要调用核心方法（如 `processQueue`）来处理刷新和重试逻辑：

- **状态检查**：如果 `isRefreshing` 为 `true` 或队列为空，则直接返回，避免重复处理。
- **获取新 Token**：
  - 设置 `isRefreshing = true`。
  - 从 Storage 中获取当前的 Refresh Token，若不存在则抛出异常。
  - 调用后端的刷新接口，传入 Refresh Token，获取最新的 Access Token 和 Refresh Token。
- **更新本地存储**：将获取到的新 Token 重新更新并存储到 Storage 中。
- **重试队列请求**：
  - 遍历请求队列中的每一个挂起请求。
  - 修改其 `config` 中的 `header`，注入最新的 Access Token。
  - 重新调用 Axios 实例发起请求。
- **重置状态**：请求重试完成后，清空队列，并将 `isRefreshing` 重置为 `false`。

## 异常处理与流程总结 *Content-[19:46]
- **异常处理**：如果在刷新 Token 的过程中发生异常（例如 Refresh Token 过期），则需要调用 `clearToken` 方法清除本地存储的所有 Token 信息，并引导用户跳转到登录页面重新登录。
- **整体流程回顾**：
  1. 通过响应拦截器捕获 Token 过期异常。
  2. 排除刷新接口自身的错误，将当前业务请求暂存至队列。
  3. 利用 `isRefreshing` 标识控制并发，调用刷新接口获取新 Token。
  4. 更新本地 Storage 中的 Token 数据。
  5. 遍历请求队列，使用新 Token 重新发起之前挂起的请求，实现真正的“无感”体验。

本视频详细讲解了前端面试中高频的场景题——“如何实现 Token 的无感刷新”。核心解决方案是采用**双 Token 机制**（短期 Access Token + 长期 Refresh Token）。在工程实现上，通过封装 Axios 拦截器，在请求拦截器中统一注入 Token，在响应拦截器中捕获过期错误。利用 `isRefreshing` 状态锁防止并发刷新，并借助请求队列（Queue）暂存过期期间的并发请求。待新 Token 获取成功后，更新本地存储并自动重试队列中的请求，从而在不打断用户操作的前提下，实现了平滑、无感的 Token 刷新体验。
