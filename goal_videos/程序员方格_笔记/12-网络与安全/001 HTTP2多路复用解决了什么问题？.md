## 2. HTTP 1.1 时代的痛点：队头阻塞与多连接 *Content-[00:57]
### 2.1 顺序处理与队头阻塞 (Head-of-Line Blocking)
- HTTP/1.1 规定在一个 TCP 连接上，所有请求必须按顺序处理。
- 发出请求 A 后，必须等 A 的响应完全返回，才能处理请求 B。
- **队头阻塞**：如果一个请求（如请求 A）处理很慢，它会像“路霸”一样堵住整条路，导致后续所有请求（B、C 等）必须排队等待。

### 2.2 浏览器的变通方案：多连接
- 为了避免请求干等，浏览器采用变通方法：既然一个连接会排队，就多开几个连接。
- 现代浏览器通常对同一个域名最多建立 **6 个并行的 TCP 连接**，以此提高并发度。

### 2.3 多连接方案的弊端
- 多连接并非完美方案，会带来新的开销：
  - 每次建立连接需经历 TCP 三次握手。
  - 若开启 HTTPS，还需经历 TLS 握手。
  - 维持多个连接会在服务端造成更多资源浪费。
- **结论**：HTTP/1.1 的核心问题在于协议层面的顺序处理机制，多连接只是缓解问题的无奈之举，不够高效。

### 2.4 队头阻塞的具体场景
- 假设在同一个 TCP 连接中发送了 A、B、C 三个请求。
- 服务器处理 A 时很慢（slow request），必须等待 A 的响应完整发送给浏览器。
- 在此期间，即使服务器已处理完 B 和 C，它们的响应也只能等待 A 发送完毕。B 等 A，C 等 B。
- 这种一个缓慢请求阻塞后续所有就绪请求的现象，对追求极致加载速度的网页应用是无法接受的，这也是驱动 HTTP 协议演进的核心动力。

## 3. HTTP/2 的核心突破：多路复用与二进制分帧 *Content-[05:26]
### 3.1 多路复用 (Multiplexing) 机制
- **核心思想**：在单一的 TCP 连接上虚拟出多个通道，称为**流 (Stream)**。
- 每个流代表一个请求和响应的来回（例如请求 `a.css` 是一个流，请求 `b.js` 是另一个流）。
- **Stream ID**：浏览器和服务器通过独一无二的 `stream id` 区分不同流的数据包，相当于给每个请求/响应对话打上标签。

### 3.2 二进制分帧 (Binary Framing)
- HTTP/2 不再将响应报文作为整体传输，而是将其打碎成许多带有类型和 `stream id` 的**二进制帧 (Frame)**。
- 来自不同流的帧可以完全无序、交错地在同一个 TCP 连接中传输。
- 接收端收到乱序的帧后，根据 `stream id` 重新拼装成对应流的完整数据。
- 常见帧类型：
  - `HEADERS` 帧：专门承载头部信息。
  - `DATA` 帧：专门承载实体数据。
- 二进制格式对机器而言，解析效率远高于纯文本，且更加稳定。

### 3.3 多路复用的显著收益
1. **单链接并发请求**：彻底解决了 HTTP/1.1 应用层的队头阻塞问题。
2. **关键资源优先传输**：当页面同时请求大图片和小 CSS 文件时，CSS 的 `DATA` 帧无需排在图片后面，可交错传输，使关键 CSS 更快到达浏览器，加速页面渲染。
3. **节省连接开销**：无需浏览器强行开启 6 个 TCP 连接，节省了大量建立连接时的握手开销。

## 4. HTTP/2 的头部压缩：HPACK 算法 *Content-[10:24]
### 4.1 头部冗余问题
- 多路复用使并行请求变得廉价，可能导致页面发起几十上百个请求。
- 在 HTTP/1.1 中，像 `Host`、`User-Agent`、`Cookie` 等头部字段在同一页面的多个请求中几乎完全相同。
- 重复发送这些头部数据会造成严重的带宽浪费，尤其是当 Cookie 很大时。

### 4.2 HPACK 头部压缩算法
- HTTP/2 引入 **HPACK** 算法专门解决头部冗余问题。
- **核心思想**：客户端和服务端共同维护一个字典。对于重复发送的头部字段，无需发送完整字符串，只需发送对应的**索引编号**。
- 极大减少了每个请求的字节数，使得在多路复用带来的大量小请求场景下，固定开销变得非常低。

## 5. HTTP/2 的隐患：TCP 层的队头阻塞与工程启示 *Content-[12:31]
### 5.1 TCP 层的队头阻塞
- 虽然 HTTP/2 解决了应用层的队头阻塞，但在更底层的 TCP 层暴露了新的问题。
- HTTP/2 建立在 TCP 协议之上，TCP 的核心特性是保证字节流的有序和可靠。
- **触发场景**：当网络抖动导致 TCP 数据包丢失（如 `pack1` 丢失，`pack2` 和 `pack3` 到达）时，TCP 层不能将已收到的 2 和 3 直接交给上层 HTTP/2 处理。
- 必须原地等待发送方重传 `pack1`，凑齐 1、2、3 的有序序列后，才会一次性交给上层。
- **致命影响**：在 HTTP/2 的单一连接中，所有流的数据帧混合在一个 TCP 字节流中。一旦该连接因丢包阻塞，**所有的流都会同时被卡住**，导致全局性暂停。

### 5.2 HTTP/1.1 与 HTTP/2 抗风险能力对比
- **HTTP/1.1 (多连接)**：虽然应用层有队头阻塞，但 6 个并行连接分散了风险。若其中一个连接因丢包阻塞，其余 5 个连接不受影响，可继续下载资源，避免页面雪崩。
- **HTTP/2 (单连接)**：所有鸡蛋放在一个篮子里。一旦连接因丢包阻塞，页面上所有资源请求同时暂停，负面影响被放大。

### 5.3 前端工程决策启示
- 在高速光纤等理想网络下，HTTP/2 单连接效率极高。
- 在真实物理世界（网络不稳定、丢包常见）中，若将资源拆得过碎（发起几十上百个请求），会增加 TCP 队头阻塞发生的概率，且一旦发生会导致整个页面加载出问题。
- **结论**：“有了 HTTP/2 就不用合并资源”的说法在网络不稳定场景下是不成立的，资源合并策略仍需慎重评估。

## 6. HTTP/3 与 QUIC 协议：彻底解决队头阻塞 *Content-[17:48]
### 6.1 QUIC 协议的引入
- 为了解决 TCP 层的队头阻塞，HTTP/3 进行了激进改变：不再基于 TCP，而是基于全新的 **QUIC** 协议。
- QUIC 构建在 **UDP** 之上。UDP 本身不保证有序和可靠，QUIC 在 UDP 基础上重新实现了一套可靠的传输、多路复用和流量控制机制。

### 6.2 QUIC 解决队头阻塞的原理
- TCP 只认整体有序的字节流，一个包丢失整个流等待。
- QUIC 从协议层面内置了流的概念，不同流之间的数据在逻辑上**完全独立**。
- 若一个流的数据包丢失，QUIC 只会阻塞该特定的流，其他流的数据只要收到即可立即交付给 HTTP/3 处理。

### 6.3 HTTP/3 的优势与工程影响
- 在网络丢包环境下，HTTP/3 提供更稳定流畅的用户体验（例如大图片下载丢包，不会影响关键资源加载）。
- HTTP/3 和 QUIC 协议从底层彻底解决了困扰多年的队头阻塞问题。
- **工程影响**：进入 HTTP/3 时代后，资源合并的必要性会被进一步大幅削弱。
