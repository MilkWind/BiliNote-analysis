## 面试背景与核心考点 *Content-[00:00]

在实际的应用开发或项目落地中，由于开发者代码水平或编码习惯的差异，项目上线后往往会暴露出许多安全漏洞。
- **面试考察目的**：企业在面试前端或后端开发人员时，重点考察安全漏洞相关知识，旨在筛选出能够在编码阶段提前识别并规避安全风险的候选人。
- **核心考点**：前后端均可能涉及的安全漏洞中，最核心且高频的考点是 **SQL 注入** 和 **XSS 漏洞**。
  - **SQL 注入**：与前后端均有关系，前端输入不规范或后端处理不当都会导致此问题。
  - **XSS 漏洞**：主要是恶意脚本注入，与后端关系不大，完全是前端开发时需要重点关注的防御点。

## SQL 注入 (SQL Injection) *Content-[03:27]

### 1\. 什么是 SQL 注入
SQL 注入是一种通过在用户输入中插入恶意 SQL 代码（该代码遵循 SQL 语法，能被数据库识别）的攻击方式。
- **原理**：攻击者利用应用程序对用户输入未做充分过滤的漏洞，篡改正常的数据库查询格式和方式，从而操纵数据库，导致数据泄露、篡改甚至被删除（如直接删库或使数据库瘫痪）。
- **成因**：前端输入不够严谨，同时后端 SQL 写法过于依赖前端传入的数据，直接进行字符串拼接。

### 2\. 常见场景与攻击示例
- **常见场景**：
  - 用户登录表单（输入用户名和密码进行查询）。
  - URL 参数直接拼接 SQL 查询（如通过修改 URL 中的 key 值来拼接恶意 SQL）。
- **攻击示例（登录表单）**：
  - **正常 SQL 逻辑**：`SELECT * FROM users WHERE username = '输入的用户名' AND password = '输入的密码'`
  - **恶意输入**：攻击者在用户名处输入 `admin' --`，密码随意填写。
  - **执行结果**：SQL 语句变为 `SELECT * FROM users WHERE username = 'admin' --' AND password = '...'`。
  - **危害**：`--` 是 SQL 中的注释符号，导致后面的密码验证代码被注释掉而不被执行。攻击者无需密码即可直接以 `admin` 身份登录，从而暴露所有用户数据。

### 3\. 如何防范 SQL 注入
防范 SQL 注入需要前后端协同配合，但**后端的防御更为核心和重要**。
- **前端防范**：
  - 限制输入格式：例如只允许输入字母和数字，禁止输入 `--` 等特殊字符。
  - 规范 API 调用和输入验证，减少传递给后端的风险数据。
- **后端防范（核心）**：
  - **避免直接拼接 SQL**：绝不能将前端传来的参数直接拼接到 SQL 语句中。
  - **参数化查询**：对传入的参数进行严格过滤和预编译处理。
  - **使用 ORM 框架或存储过程**：通过成熟的框架或数据库存储过程来执行查询，从根本上杜绝拼接漏洞。

## XSS 漏洞 (Cross-Site Scripting) *Content-[09:21]

### 1\. 什么是 XSS
XSS 全称为 Cross-Site Scripting（跨站脚本攻击）。
- **原理**：攻击者通过在网页中注入恶意的脚本代码（如 JavaScript），当其他用户访问该页面时，恶意脚本会在用户的浏览器中自动执行。
- **危害**：从而窃取用户的敏感数据（如 Cookie）、劫持用户会话或篡改页面内容。

### 2\. XSS 的三种主要类型
- **存储型 XSS**：攻击者将恶意脚本提交并保存在后端数据库中（如评论区）。当其他用户访问并加载该页面时，脚本会自动执行。
- **反射型 XSS**：恶意脚本通过 URL 等途径传入，服务端将其反射到页面上并触发执行。
- **DOM 型 XSS**：纯前端漏洞。攻击者通过修改页面的 DOM 结构来触发并执行恶意脚本，与后端交互关系较小。

### 3\. XSS 攻击示例
- **场景**：一个搜索页面，未对用户的搜索内容进行过滤。
- **攻击过程**：
  1. 攻击者在搜索框中输入一段恶意的 `<script>` 标签代码（例如用于发送请求窃取数据的脚本）。
  2. 由于未做过滤，该恶意代码被当作正常内容保存到数据库，并显示在搜索结果页面上。
  3. 当其他用户访问该页面时，浏览器解析到 `<script>` 标签并自动执行其中的 JavaScript 代码。
  4. 恶意脚本在后台发送请求，将当前用户浏览器中的 `cookie` 值发送给攻击者的服务器。
  5. 攻击者获取 `cookie` 后，即可模拟该用户的身份进行登录和操作。

### 4\. 如何防范 XSS
XSS 的防范主要依赖前端和浏览器的安全机制。
- **输入过滤与转义**：在用户输入时，对特殊字符（如 `<`、`>`）进行转义，将其替换为 HTML 实体（如 `&lt;`、`&gt;`），使其失去脚本执行能力。
- **输出编码**：在将数据渲染到页面时，根据上下文使用 HTML 编码，确保数据仅作为纯文本显示。
- **内容安全策略 (CSP, Content Security Policy)**：
  - 限制脚本加载的来源，禁止页面加载非预期的外部脚本。
  - 确保页面内容仅作为纯文本显示，防止恶意脚本被当作可执行代码加载。

## SQL 注入与 XSS 的核心区别总结 *Content-[14:15]

| 维度 | SQL 注入 (SQL Injection) | XSS 漏洞 (Cross-Site Scripting) |
| :--- | :--- | :--- |
| **攻击目标** | 后端数据库 | 前端用户（浏览器） |
| **利用方式** | 篡改 SQL 查询语句 | 注入并执行恶意脚本（如 JavaScript） |
| **防范重点** | 后端：参数化查询、ORM<br>前端：输入验证与格式限制 | 前端：输入过滤、输出编码、CSP 策略 |
| **常见场景** | 登录表单、URL 参数拼接查询 | 评论区、搜索框、富文本展示 |

## AI 总结

本视频详细解析了前端面试中高频考察的两大安全漏洞：**SQL 注入**与 **XSS 漏洞**。
- **SQL 注入**主要针对后端数据库，攻击者通过构造恶意输入篡改 SQL 语句。防范的核心在于后端必须使用**参数化查询**或 **ORM 框架**，杜绝直接拼接 SQL，同时前端需做好输入格式限制。
- **XSS（跨站脚本攻击）**主要针对前端用户，攻击者通过注入恶意脚本窃取 Cookie 等敏感信息。防范的核心在于前端必须对输入进行**转义过滤**，对输出进行**编码**，并合理配置 **CSP（内容安全策略）**。
掌握这两种漏洞的原理、攻击场景及防御手段，是前端开发者保障系统安全、顺利通过大厂面试的必备技能。
