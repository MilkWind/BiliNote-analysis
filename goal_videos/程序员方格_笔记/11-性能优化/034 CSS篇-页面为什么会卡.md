## 页面为什么会卡：核心结论 *Content-[00:27]
页面卡顿的本质原因并不是浏览器运行慢，而是因为代码让浏览器不得不重复执行非常昂贵的渲染工作。这些昂贵的工作主要分为两类：
1\. **重排（Layout / Reflow）**：负责重新计算页面的几何信息（如宽高、位置、换行等）。
2\. **重绘（Paint / Repaint）**：负责重新绘制像素（如颜色、背景、阴影等）。

**面试常见误区**：
很多开发者只会死记硬背“少改样式，用 `transform`，别用 `top/left`”的口诀。但在面试中，面试官往往会深入追问底层机制，例如：
- 修改 `color` 会触发什么？
- 读取 `offsetWidth` 为什么会导致卡顿？
- `transform` 为什么不卡？
因此，必须彻底理解浏览器内部的渲染机制，而不是仅仅背诵结论。

## 浏览器渲染流水线复习 *Content-[01:15]
在深入探讨卡顿原因前，需要快速复习浏览器的渲染流水线：
1. HTML 解析生成 DOM 树，CSS 解析生成 CSSOM 树。
2. 将 DOM 和 CSSOM 合成为 Render Tree（渲染树）。
3. 进入真正绘制页面的阶段，核心包含三个步骤：
   - **Layout（布局）**：计算元素的几何信息。
   - **Paint（绘制）**：绘制元素的像素。
   - **Composite（合成）**：将图层合成为最终画面。

**卡顿的本质**：触发了 Layout 或 Paint，且触发频率过高。更严重的情况是在循环中反复触发 Layout，导致主线程被完全堵死，页面“卡成 PPT”。

## 重排（Reflow / Layout）详解 *Content-[02:24]
**核心概念**：几何信息变了，布局就必须重新计算。几何信息包括宽高、位置、是否换行、元素挤压关系以及父子尺寸传递等。

**代码演示与陷阱**：
- **写操作触发重排**：通过 `box.style.width` 修改元素宽度（如每次增加 20px），必然触发重排。因为宽度的改变可能影响文本换行、挤开相邻元素或撑高父元素。
- **读操作的性能陷阱**：`box.offsetWidth` 看似只是一个简单的读取操作，没有成本。但实际上，浏览器为了返回一个准确的 `offsetWidth`，必须保证当前的布局是最新的。如果前面有写操作导致布局“变脏”（失效），此时的读取操作就会触发**强制同步布局（Forced Synchronous Layout）**。
- **机制总结**：写样式会让布局变脏，而读布局会逼迫浏览器立刻把脏的部分计算干净。这会将原本可以合并处理的布局计算，硬生生变成一堆同步的阻塞操作。

**常见触发重排的操作**：
任何影响盒子几何或文档流参与方式的 CSS/DOM 改动都可能触发重排，包括：
- 样式属性：宽度、高度、padding、margin、display、position、font-size、line-height 等。
- DOM 操作：节点的插入、删除、改变顺序，或者修改 class 触发一系列影响布局的 CSS 规则。

## 重绘（Repaint / Paint）详解 *Content-[04:38]
**核心概念**：布局（几何）没有改变，但外观（长相）变了，因此需要重新绘制像素。例如改变颜色、背景、阴影、描边等，元素依然在原位置且大小不变。

**代码演示**：
通过按钮改变 box 的背景颜色和阴影，这种操作只会触发重绘，不会触发重排。

**核心对比结论**：
- **重排一定会导致重绘**：因为几何位置变了，像素自然需要重新绘制。
- **重绘不一定会导致重排**：因为像素变了，不代表几何位置发生了改变。

**渲染成本对比**：
重排成本 **远大于** 重绘成本 **远大于** 合成（Composite）成本。
- **为什么重排最贵？** 因为重排往往是“牵一发而动全身”。例如一个容器宽度改变，可能导致内部 inline 文本重新换行，整段高度发生变化，浏览器必须依赖这些变化把所有相关部分重新计算一遍。

## 布局抖动（Layout Thrashing）与性能杀手 *Content-[06:09]
**核心概念**：布局抖动是线上最常见的性能杀手。它的特点不是只触发了一次重排，而是在极短时间内触发了成百上千次重排，瞬间塞满主线程。

**经典错误写法**：
在循环中交替进行“读布局”和“写布局”操作。
- **Demo 演示**：在 `for` 循环中，先读取 `offsetWidth`，然后给 `style.width` 加 1。
- **性能表现**：
  - 循环 1万次：耗时约 150ms，卡顿不明显。
  - 循环 10万次：耗时超过 1秒，出现明显卡顿。
  - 循环 100万次：耗时超过 10秒，页面完全卡死，box 宽度甚至无法正常更新。
- **原理**：读操作要求布局最新，写操作让布局立刻失效（挂上脏标记）。交替进行彻底打碎了浏览器将多次写操作合并到下一帧统一计算的机会。
- **常见线上场景**：滚动时计算元素高度同时写 style；做瀑布流时一边测量一边插入 DOM。

**正确做法：读写分离**
- **Demo 修复**：使用变量（如 `size`）只读取一次宽度，在 `for` 循环中只进行纯 JS 数学计算，不触发布局。
- **性能表现**：即使循环 100万次，也仅需 3ms。
- **面试高分话术**：“浏览器可以把多次写操作合并到下一帧统一计算，但如果在循环里读布局，就会把这个合并的机会打碎。”

## 为什么 transform 动画更流畅 *Content-[09:12]
**核心原理**：
- `top` / `left`：改变的是元素的布局坐标（几何位置），意味着元素位置变了，必须重新计算布局，触发 Layout 和 Paint（重排和重绘）。
- `transform`：绕过了 Layout 和 Paint，直接走到 Composite（合成）阶段。它更像是把已经画好的图层当做一张图片进行挪动。在合成阶段完成位移，不需要重新 Layout 和 Paint。

**代码演示**：
给 box 添加 `transform` 动画，在 900ms 内做横向移动。由于只动了图层不动几何，动画效果非常流畅。

## 课程核心总结 *Content-[10:18]
1\. **最贵的操作是 Layout（重排）**：尽量避免频繁修改影响几何的样式。
2\. **重排一定带来重绘**：理解两者的包含与触发关系。
3\. **动画优先使用 `transform`**：利用合成层特性，避免触发重排和重绘。
4\. **避免布局抖动**：坚持“读写分离”原则，批量读取和批量写入。

本页笔记深度解析了前端面试高频考点“页面为什么会卡”的底层机制。页面卡顿的本质是代码频繁触发了浏览器昂贵的渲染操作，即重排（Layout）和重绘（Paint）。笔记详细梳理了浏览器渲染流水线，通过代码实例直观展示了修改样式、读取布局属性（如 `offsetWidth`）以及交替读写引发的“布局抖动”灾难。同时，对比了 `top/left` 与 `transform` 在动画性能上的差异，强调了“读写分离”和“优先使用 `transform`”的核心优化原则，帮助开发者从浏览器底层机制出发，彻底掌握前端性能优化的实战技巧。
