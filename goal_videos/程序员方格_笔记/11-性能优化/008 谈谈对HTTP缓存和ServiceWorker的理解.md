## 1. HTTP缓存机制的核心痛点与基本流程 *Content-[00:00]
- **核心痛点**：HTTP 缓存机制主要为了解决**复用资源**、**减少延迟**和**节省带宽**三大痛点。避免用户每次访问都重新下载图片、CSS、JS 等文件，从而提升网络加载速度和用户体验。
- **基本交互流程**：
  - 浏览器请求资源时，首先检查本地存储空间是否已缓存该资源。
  - 缓存是否有效的决策依据，来自服务器在返回资源时通过 HTTP 响应头附加的指令（如 `Cache-Control`、`ETag`）。
- **两大核心分类**：
  - **强缓存**：缓存明确有效，浏览器直接复用本地资源，**不发起网络请求**。
  - **协商缓存**：强缓存失效，但浏览器不确定资源是否更新，向服务器发起**轻量级验证请求**进行协商。

## 2. 强缓存机制详解：Cache-Control 与 Expires *Content-[06:05]
- **强缓存定义**：命中规则时，浏览器直接从本地内存或磁盘读取资源，完全不向服务器发起请求。在 Chrome DevTools 中通常标记为 `from disk cache` 或 `from memory`。
- **控制字段对比**：
  - **`Cache-Control`**（HTTP/1.1）：现代主流方案，功能强大且灵活。
  - **`Expires`**（HTTP/1.0）：已过时的方案，指定绝对的 GMT 过期时间。其致命缺陷是依赖客户端本地系统时间，若用户时间不准会导致缓存判定偏差。
  - **优先级**：当两者同时存在时，`Cache-Control` 优先级高于 `Expires`。现代开发中基本只需关注 `Cache-Control`。
- **`Cache-Control` 常用指令**：
  - **`max-age=<seconds>`**：指定资源的保质期（相对时间），例如 `max-age=31536000` 表示一年内有效。
  - **`public`**：允许最终用户的浏览器及中间代理服务器（如 CDN）缓存，提升分发效率。
  - **`private`**：仅允许用户浏览器缓存，禁止中间代理服务器缓存（适用于包含个人信息的页面）。
  - **`no-cache`**：**并非不缓存**，而是允许缓存，但在使用缓存副本前必须向服务器验证其有效性（跳过强缓存，直接进入协商缓存）。
  - **`no-store`**：**真正意义上的禁止缓存**，任何中间缓存和本地都不会存储，每次必须重新从服务器请求。
  - **`immutable`**：强暗示资源内容永远不会变化。即使用户刷新页面，浏览器也优先使用本地资源，不发起任何请求。非常适合文件名包含哈希值或版本号的静态资源（如 `app.v1.js`）。

## 3. 协商缓存机制详解：Last-Modified 与 ETag *Content-[12:35]
- **协商缓存定义**：当强缓存失效或设置为 `no-cache` 时触发。浏览器向服务器发起验证请求，目的是询问“本地版本是否还能用”。此阶段**一定会发生网络请求**。
- **服务器响应结果**：
  - **`304 Not Modified`**：文件未修改，浏览器直接使用本地旧版本。
  - **`200 OK`**：文件已更新，服务器返回全新资源，浏览器替换本地缓存并更新策略。
- **实现方式一：基于最后修改时间**
  - **字段**：`Last-Modified`（服务器响应），`If-Modified-Since`（浏览器请求）。
  - **流程**：服务器返回文件及最后修改时间 -> 浏览器缓存 -> 再次请求时携带 `If-Modified-Since` -> 服务器比对时间，一致返回 304，不一致返回 200。
  - **缺点**：时间戳精度仅到秒，一秒内多次修改无法感知；仅修改文件元数据未改内容也会导致时间戳更新，造成不必要的重新下载。
- **实现方式二：基于内容指纹（ETag）**
  - **字段**：`ETag`（服务器响应），`If-None-Match`（浏览器请求）。
  - **流程**：服务器生成代表资源内容哈希值的 `ETag` -> 浏览器缓存 -> 再次请求时携带 `If-None-Match` -> 服务器比对 `ETag`，一致返回 304，不一致返回 200 及新 `ETag`。
  - **优点**：完全基于内容生成，精度极高，彻底解决 `Last-Modified` 的缺陷。
  - **优先级**：现代服务器中 `ETag` 优先级高于 `Last-Modified`。若浏览器同时发送两个验证字段，服务器优先使用 `ETag` 校验。

## 4. Service Worker：可编程的缓存方案 *Content-[19:07]
- **背景**：传统 HTTP 缓存是声明式的（由 HTTP Header 定义），无法实现离线缓存、网络优先、先返回缓存再后台更新等复杂策略。
- **本质与能力**：`Service Worker` 是独立于主线程、在后台运行的 JS 脚本。其最强大的能力是**拦截和处理**受控页面发出的所有网络请求。
- **自定义响应**：拦截请求后，开发者可编写代码决定如何响应（从缓存读取、从网络获取或动态生成响应）。
- **常见缓存策略**：
  - **Network First**：优先保证网络请求，网络失败时回退到缓存。
  - **Cache First**：优先读取缓存，缓存未命中时才请求网络。
  - **SWR (Stale-While-Revalidate)**：立即返回缓存中的内容，同时在后台发起网络请求更新数据，供下次使用。
- **核心价值**：将缓存控制权从声明式的 HTTP 头部交还给前端开发者，为构建功能强大的网络应用提供全新思路。

## 5. 实际项目中的缓存策略组合应用 *Content-[21:07]
- **带哈希值/版本号的静态资源**（如 CSS/JS/图片）：
  - **策略**：最激进的强缓存。
  - **配置**：长 `max-age` + `immutable`。因为 URL 与文件内容强绑定，内容不变则永久缓存，无需验证。
- **主入口文件**（如 `index.html`）：
  - **策略**：强制协商缓存。
  - **配置**：`no-cache`。确保浏览器每次都与服务器协商，通过 `ETag` 或 `Last-Modified` 验证文件是否更新，保证用户始终加载最新的 HTML 及其引用的新资源。
- **动态 API 请求数据**：
  - **要求绝对实时**：使用 `no-store` 完全禁用缓存。
  - **可接受短暂延迟**：设置较短的 `max-age`，降低服务器短时间内的请求压力。
- **复杂场景**：当传统 HTTP 缓存策略无法满足需求时，使用 `Service Worker` 实现自定义的精细缓存逻辑。
