## 为什么页面动画会卡顿？ *Content-[00:21]
- **现象**：在项目中编写动画时，有的动画非常顺滑，几乎没有性能压力；而有的动画只是让元素移动了一下位置，页面却明显开始掉帧。
- **常见误区**：很多人第一反应是怀疑 JavaScript 执行过慢。
- **真实原因**：通过浏览器的性能分析可以发现，大多数时候 JavaScript 并不是瓶颈。真正决定动画是否流畅的，是**浏览器为了这次变化走了哪一条渲染路径**。
- **核心问题**：当修改元素样式时，浏览器是否一定会重新开始布局（重排）并重新绘制页面（重绘）？
- **结论**：浏览器内部存在一种更便宜的处理方式，即 **Composite（合成）**。理解这一机制是解决动画卡顿的关键。

## 浏览器渲染流程与 Composite 阶段 *Content-[01:38]
- **宏观渲染过程**：
  - HTML 解析成 DOM，CSS 解析成 CSSOM。
  - 两者合并生成 Render Tree（渲染树）。
  - 依次进行 Layout（布局）、Paint（绘制）和 Composite（合成）。
- **性能差异分析**：
  - **Layout 和 Paint**：属于 CPU 密集型工作，需要大量的计算遍历和内存操作。
  - **Composite**：是整个流程的最后一步。此阶段浏览器不关心布局，也不重新绘制像素，只负责将已经画好的图层按照新的规则拼合在一起。
- **GPU 加速优势**：Composite 阶段通常由 GPU 来完成。GPU 非常擅长处理平移、缩放、旋转和透明度混合等操作。
- **优化思路**：如果一次样式变化只涉及上述 GPU 擅长的操作，浏览器就完全没有必要回到 Layout 和 Paint（即重排和重绘），只需将变化限制在 Composite 阶段，页面性能就会非常稳定。

## 合成层（Composite Layer）与触发属性 *Content-[02:51]
- **合成层概念**：浏览器内部并不会把整个页面当作一张图来处理，而是将页面拆分成很多层。其中只有一部分元素会被提升为**合成层**。
- **核心优势**：一旦元素成为合成层，其在视觉上的变化就可以直接交由 GPU 处理。
- **触发合成层的常见 CSS 属性**：
  - `transform`：开发动画相关组件或效果时最常用的属性。
  - `opacity`：用于描述元素的透明度。
  - `position` 和 `will-change`：也可以将当前元素提升为合成层。
- **共同特征**：这些属性**不会改变元素在文档流中的占位关系**。无论元素怎么动，父元素、兄弟元素的尺寸和位置都不会改变。
- **底层逻辑**：只要布局是稳定的，浏览器就可以放心地跳过 Layout 和 Paint，直接将变化交给 Composite 阶段处理。

## CSS 属性的性能分类 *Content-[04:26]
CSS 属性之间真正的差别不在于视觉效果，而在于它们**是否会影响布局模型**。根据性能代价，可分为以下三类：

1\. **只触发 Composite（不触发 Layout 和 Paint）**
- **代表属性**：`transform`、`opacity`。
- **原理**：当这两个属性发生变化时，元素在文档流中的位置没有改变，浏览器不需要重新计算任何布局变化，直接停在 Composite 阶段由 GPU 完成。几乎所有的高性能动画方案最终都落脚在这两个属性上。

2\. **触发 Paint，但不触发 Layout**
- **代表属性**：`background-color`、`box-shadow`、`border-radius`。
- **原理**：这些属性不影响元素的几何结构，但需要重新绘制像素。

3\. **既触发 Layout，又触发 Paint（性能代价最高）**
- **代表属性**：`width`、`height`（改变宽高），`margin`、`padding`（盒模型相关），`left`、`top`、`display`（改变位置和展示状态）。
- **原理**：这些属性一旦变化，浏览器无法确定影响范围，只能从 Layout 开始，把整个渲染流程重新走一遍（即经历重排和重绘）。

## 经典对比：left 与 transform 的底层差异 *Content-[06:01]
通过实现一个元素向右偏移 100px 的 hover 动画，对比两种写法的底层逻辑：

- **使用 `left` 属性**：
  - **代码实现**：设置 `left: 0` 到 `left: 100px`，配合 `transition`。
  - **底层逻辑**：`left` 发生变化时，元素的布局坐标被修改。浏览器必须确认该元素的位置是否影响了其他元素。
  - **渲染路径**：浏览器会选择最安全的路径，即从 Layout（重排） -> Paint（重绘） -> Composite。这是最昂贵的一条路径。

- **使用 `transform` 属性**：
  - **代码实现**：设置 `transform: translateX(0)` 到 `transform: translateX(100px)`，配合 `transition: transform 0.3s`。
  - **底层逻辑**：发生变化的只是图层的位置，原有的布局结果完全可以复用。
  - **渲染路径**：浏览器直接跳到 Composite 阶段，完全跳过了昂贵的重排和重绘。
- **结论**：两者视觉效果一致，但底层实现和性能表现存在本质差异。

## will-change 属性的使用与优化 *Content-[08:27]
- **作用机制**：给元素加上 `will-change` CSS 属性，可以提前告诉浏览器该元素接下来会发生变化，促使浏览器提前创建合成层，从而避免动画开始时的额外开销。
- **注意事项**：每一个合成层都会占用 GPU 资源。如果合成层过多，反而会增加整体的性能成本。
- **最佳实践**：需要节制使用，并在动画结束后释放提示。例如，在动画结束后给元素添加一个类（如 `animation-end`），将 `will-change` 的值改回 `auto` 以释放资源。

## 课程总结 *Content-[09:11]
- **流畅的关键**：页面是否流畅，关键不在 JavaScript，而在于**渲染的路径**。
- **属性选择**：`transform` 和 `opacity` 可以把变化限制在 Composite 阶段；`position` 和 `will-change` 也能达到类似效果，但 `will-change` 必须节制使用。
- **优化本质**：真正的性能优化就是让浏览器**尽量少做事情**。只有理解了浏览器的底层原理，才能知道如何让它少做事，只做它应该做的事情。
- **一句话总结**：**性能优化 = 让变化停在 Composite，尽量少触发 Layout 和 Paint**。
