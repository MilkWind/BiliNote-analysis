## 核心 Web 指标概述 *Content-[00:00]

*   **背景**：过去衡量网页体验多凭用户的主观感觉，或者使用一些对开发者友好但对用户不够直观的传统技术指标。
*   **提出**：Google 推出了一套名为**核心 Web 指标（Core Web Vitals）** 的体系。
*   **核心目的**：尝试去量化用户的真实体验，将主观感受转换成可以量化和优化的数据。
*   **关注焦点**：不再仅仅关注技术层面的加载优化，而是重点关注用户实际感受到网页“快不快”、“稳不稳”以及“流不流畅”。

## 核心 Web 指标概览 *Content-[01:14]

核心 Web 指标从三个维度覆盖了用户与网页交互的核心体验：

1\. **加载性能**：通过 **LCP**（最大内容绘制）衡量，回答用户最关心的问题——“页面最主要的内容什么时候才能显现出来”。
2\. **视觉稳定性**：通过 **CLS**（累积布局偏移）衡量，量化页面元素突然跳动导致的误触或中断，将偏移量用指标衡量出来。
3\. **交互响应性**：通过 **INP**（交互到下次绘制的时间）衡量，关注用户点击按钮或进行其他操作时，页面能否立刻给出反馈。

## LCP：最大内容绘制 (加载性能) *Content-[03:02]

*   **定义**：衡量从页面开始加载到视口内**最大的可见**图片或者文本块被完全渲染出来所花费的时间。
*   **核心关注**：“最大”和“可见”。它关注的是用户第一眼就能看到的最主要目标，而不是整个页面的所有元素。
*   **优势**：相对于传统的 `load` 事件，LCP 更贴近用户感知，直接反映用户主观感受到的页面加载速度，更能代表页面的可用性。
*   **优秀标准**：Google 给出的优秀标准是 LCP 时间应该 **≤ 2.5秒**。
*   **加载流程**：用户发起请求 -> 浏览器向服务器请求资源（HTML/CSS/JS） -> 解析和渲染 -> 最大内容被绘制到屏幕上（此时 LCP 计时结束，通常代表用户认为页面主体已加载出来）。

## CLS：累积布局偏移 (视觉稳定性) *Content-[05:07]

*   **痛点场景**：阅读文章时图片加载把文字推下；准备点击按钮时突然弹出广告导致误触。
*   **定义**：衡量页面在整个生命周期中，所有**非用户预期**的布局偏移的总和。
*   **计算方式**：CLS 不是一个时间值，而是一个**分数**。通过计算移动元素的尺寸和移动距离得出。分数越低，代表布局稳定性越高，用户体验越好。
*   **优秀标准**：Google 建议优秀的网页 CLS 分数应该 **< 0.1**，代表页面几乎没有发生过令人困惑的布局跳动。
*   **优化建议**：在开发时给图片、广告等异步加载的内容预留好对应的空间，保证布局相对稳定。

## INP：交互到下次绘制的时间 (交互响应性) *Content-[06:57]

*   **背景**：INP 在 2024年3月正式取代旧指标 **FID**（首次输入延迟），成为新的核心指标。
*   **FID 的局限性**：只测量用户与页面的第一次交互延迟。对于复杂的单页应用（如复杂表单、在线编辑器），首次交互可能很快，但后续大量交互时主线程被阻塞导致变卡，FID 无法捕获这种后续的性能问题。
*   **INP 的优势与测量方式**：
    *   监控用户在页面上的**所有交互**（包括点击、键盘输入等）。
    *   记录每一次交互的延迟时间，选取**最慢的那一次**或接近最慢的高百分位值作为 INP 代表值。
    *   能够捕捉到哪怕只有一次交互卡顿的“最差瞬间”，提供更真实的用户体验画像。
*   **完整响应链路**：用户点击按钮 -> 浏览器处理事件 -> 相关计算和渲染逻辑执行 -> 页面视图更新。INP 关注的是这整个链路的完整响应时间。

## 性能数据的测量方式：实验室数据与现场数据 *Content-[11:38]

测量核心 Web 指标的数据主要分为两大类，两者是互补关系：

*   **实验室数据 (Lab Data)**：
    *   **来源**：使用 Lighthouse 等工具在开发机器或受控服务器上运行。
    *   **优点**：环境可控（可设置固定的网络速度、CPU性能），结果稳定可复现，适合开发和调试阶段快速定位问题。
    *   **缺点**：模拟环境不等于用户的真实环境，无法涵盖用户设备性能、网络状况或浏览器插件等变量。
*   **现场数据 (Field Data)**：
    *   **来源**：真实网站用户的实际体验数据（如 Google CRUX 报告，或网页集成 `web-vitals` 库收集）。
    *   **优点**：绝对真实，反映用户在各种不可控环境下的真实体验，是优化的最终目标。
    *   **缺点**：当报告问题时难以复现，因为无法确切知道用户当时的具体环境。
*   **结论**：开发阶段用实验室数据保证基础质量，线上用现场数据监测真实的用户体验。

## 常用性能检测工具与代码实践 *Content-[14:36]

### 获取实验室数据的工具
1\. **Lighthouse**：内置于 Chrome DevTools。可对当前页面做整体性能评估，给出 LCP、CLS 及与 INP 强相关的 TBT（总阻塞时间）等分数和优化建议，是开发自测首选。
2\. **PageSpeed Insights**：Google 提供的在线服务。输入网址后，不仅运行 Lighthouse 测试，还能拉取过去一个月的现场数据（需网站流量足够大），提供双维度数据展示。

### 获取现场数据的工具
1\. **Google Search Console**：在“体验”板块下的“核心网页指标”报告，基于海量真实用户数据，宏观展示哪些 URL 指标良好或需要改进。
2\. **web-vitals (JavaScript 库)**：Google 官方推出的轻量级库。集成到网站代码中，可在用户浏览器实时测量 LCP、CLS、INP，并将数据发送到自定义分析后台进行深度分析。

### web-vitals 代码实践示例
*   导入 `onLCP`, `onCLS`, `onINP` 回调函数。
*   定义 `sendToAnalytics` 函数，用于收集性能指标数据并处理后发送到后端分析服务，实现定制化分析。
*   调用上述回调函数并传入 `sendToAnalytics` 进行数据上报，从而在项目中建立性能监控。

## 课程总结与回顾 *Content-[18:29]

*   **LCP**：核心目标是让页面最主要内容尽快对用户可见，直接关系到用户对加载速度的感知。
*   **CLS**：要求在加载过程中保持页面布局稳定，避免元素跳动给用户带来干扰和误操作。
*   **INP**：衡量页面的整体响应能力，确保用户在进行点击、输入等操作时能够得到及时、流畅的视觉反馈。
*   **工具体系**：通过 Lighthouse、Search Console 和 `web-vitals` 库获取实验室数据和现场数据，为产品建立一套完善的自动化性能监测体系。
