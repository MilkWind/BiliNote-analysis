## 引言与问题现象 *Content-[00:00]
- **问题现象**：在前端开发中，我们经常会遇到一个“玄学”问题——明明给元素设置了 `z-index: 9999`，但该元素依然被其他元素（例如 `z-index: 10` 的遮罩层）挡住。即使将 `z-index` 改为 `99999`，现象依然存在。
- **核心结论**：`z-index` 从来没有失效。真正的问题在于“我们在用一个世界的数字，去和另一个世界的元素比高低”。这涉及到了前端 CSS 中的核心概念——**层叠上下文（Stacking Context）**。

## 核心概念：层叠上下文 Stacking Context *Content-[03:11]
- **浏览器的真实模型**：页面并不是一张平面的纸，所有元素也不在同一个平面上排队。浏览器会把页面切成很多个“独立舞台”，每个舞台内部进行排序，而舞台和舞台之间也有排序。
- **比较规则**：我们只能在同一个舞台（即同一个层叠上下文）里比较 `z-index` 的大小。
- **层叠上下文的定义**：它是一个独立的层叠空间。在这个空间内，子元素的 `z-index` 只与同一上下文的兄弟元素进行比较，**不会跨越上下文进行比较**。
- **通俗比喻**：创建了层叠上下文就等于创建了一个“新的世界”。世界内部怎么排序都可以，但对外只能派出“世界代表”去比较。例如，子元素 `child` 在父元素 `parent` 的世界里 `z-index` 是 `9999`，但 `parent` 世界整体对外比较时，只看 `parent` 自己的 `z-index`。就像在班级里考了第一名，不能直接拿去和年级第一名比，要看班级整体的年级排名。

## 创建层叠上下文的常见条件 *Content-[04:03]
在面试中，我们需要熟记以下会创建层叠上下文的高频条件（凡是可能触发合成层、独立渲染层的属性，都要警惕其带来的层叠上下文）：

1\. **定位 + z-index**：`z-index` 不为 `auto`，且 `position` 为 `relative`、`absolute`、`fixed` 或 `sticky`。注意：单独写 `position: relative` 不一定创建层叠上下文，关键是 `z-index` 参与了层叠（不能是 `auto`）。
2\. **透明度 (opacity)**：`opacity` 小于 `1` 时会创建一个层叠上下文。
3\. **变换 (transform)**：`transform` 不等于 `none`。例如，很多开发者为了开启 GPU 加速会写 `transform: translateZ(0)`，这同样会开启层叠上下文。
4\. **3D 相关属性**：如 `perspective` 等 3D 变换相关属性。
5\. **隔离 (isolation)**：设置了 `isolation: isolate`。
6\. **will-change**：指定了 `will-change` 属性。
7\. **滤镜 (filter)**：使用了 `filter` 属性。

- **记忆口诀**：“位（定位）+ 透（opacity）+ 变（transform）+ 滤（filter）+ 隔（isolation）”。在面试时说出这几个高频项，足以证明对底层原理有深刻理解。

## Demo 案例分析与验证 *Content-[05:51]
- **场景结构**：根节点 `root` 下包含 `parent` 和 `mask`，`parent` 内部包含子元素 `child`。
- **样式设置**：
  - `child`：`z-index: 9999`
  - `parent`：`position: relative; z-index: 1;`（创建了层叠上下文）
  - `mask`：`z-index: 10;`（也创建了层叠上下文）
- **现象分析**：
  - `child` 在 `parent` 舞台中排名第一，但 `parent` 舞台整体排不过 `mask` 所在的舞台。
  - 因为 `parent` 的 `z-index` 是 `1`，而 `mask` 是 `10`，`parent` 输了，导致其内部所有元素（包括 `z-index: 9999` 的 `child`）都被 `mask` 遮挡。
- **验证实验**：
  - **提升父级层级**：将 `parent` 的 `z-index` 改为 `100`，`parent` 赢得比较，`child` 立刻能盖住 `mask`。这证明 `child` 自身的 `9999` 并不关键，关键是它所在的舞台（`parent`）要先赢。
  - **移除父级上下文**：将 `parent` 的 `z-index` 删除或改为 `auto`，`parent` 无法创建层叠上下文。此时 `child` 回到根上下文与 `mask` 比较，因为 `9999 > 10`，`child` 会正常显示在 `mask` 上方。
- **排查思路**：看到 `z-index` 失效时，先不要看子元素的值写了多少，**首要检查其祖先元素是否创建了层叠上下文**，以及祖先元素的层叠上下文是否被其他元素压住了。

## 工程实践中的解决方案 *Content-[07:42]
在工程层面，通常有以下三种方案来解决 `z-index` 层级覆盖问题：

1\. **把弹窗类组件挂载到 `body` 上（最推荐/标准做法）**
   - **原因**：弹窗（如 `toast`、`dropdown`、`tooltip`）本质上是全局覆层。如果将其放在某个业务组件内部，极易被祖先上下文（如祖先写了 `transform`、`overflow` 或 `opacity`）限制，从而陷入无尽的 `z-index` 调参过程。
   - **实现**：原生写法可使用 `Portal` 将弹窗渲染到 `body` 下的指定节点；在框架中，React 提供 `Portal`，Vue 提供 `Teleport`，本质都是将浮层放到更高的层级世界里，从结构上避免业务容器的层叠上下文干扰。

2\. **提升创建上下文的父元素的层级**
   - **做法**：直接提高父元素（如上述 Demo 中的 `parent`）的 `z-index`，让它赢得和其他舞台的比较。
   - **缺点**：会引入新的维护成本，因为抬高一个舞台的层级可能会意外影响其他舞台或模块的显示。

3\. **避免创建没有意义的上下文**
   - **场景**：通常发生在动画实现上。例如给动画的 `container` 加了 `transform` 以为能开启 GPU 优化，却意外创建了新的层叠上下文，导致内部浮层覆盖出问题。
   - **正确做法**：将 `transform` 放到更内层的元素上，或者只在真正需要动画的元素上添加，切勿盲目加到大的外层容器上。

## 面试回答模板 *Content-[09:37]
当面试官提问：“`z-index` 为什么会失效？”时，可以直接使用以下模板回答：

> “`z-index` 本身并不会失效，通常是因为元素处在不同的**层叠上下文（Stacking Context）** 里。`z-index` 只能在一个 Stacking Context 内部比较大小，不能跨上下文比较。
> 
> 在实际工程开发中，为了解决这类层级覆盖问题，我们通常采取以下三种方案：
> 1. 最标准的做法是把浮层类组件（如弹窗）通过 `Portal` 或 `Teleport` 挂载到 `body` 上，脱离业务组件的上下文限制。
> 2. 提高父级层叠上下文的 `z-index`，让父级舞台赢得层级比较。
> 3. 审查代码，避免创建无意义的层叠上下文，比如在不需要 3D 变换的大容器上滥用 `transform`。”
