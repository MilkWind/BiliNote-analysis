## 1. 问题引入与核心结论 *Content-[00:21]

在前端开发中，我们经常遇到一个典型的“玄学”问题：**明明给元素设置了 `z-index: 9999`，但元素依然被其他元素遮挡。**

面对这种情况，开发者通常会怀疑是浏览器 Bug、CSS 写错，或者认为 `z-index` 不支持某些特定元素。

**核心结论**：
`z-index` 从来没有失效。真正的问题在于**我们在用一个世界的数字，去和另一个世界的元素比高低**。这就引出了今天讲解的核心概念——**层叠上下文（Stacking Context）**。

## 2. Demo 演示与“舞台模型” *Content-[00:59]

为了直观理解，我们通过一个 Demo 来演示这个现象：

- **DOM 结构**：
  - 一个 `parent` 容器，内部包含一个 `child` 元素（黄色弹窗）。
  - 在 `parent` 的同级，有一个 `mask` 遮罩层（黑色 div）。
- **样式设置**：
  - `child` 的 `z-index` 设置为 `9999`。
  - `mask` 的 `z-index` 设置为 `10`。
- **现象**：
  - 黑色的 `mask` 遮罩层盖住了黄色的 `child` 弹窗。
  - 即使将 `child` 的 `z-index` 改为 `99999`，现象依然不变，依然被 `mask` 遮挡。

**本质原因**：
不是 `z-index` 数字不够大，而是**比较关系压根不成立**。

**浏览器的真实模型（舞台模型）**：
- **错误认知**：页面像一张纸，所有元素在一个平面上排队，`z-index` 像票号，数字越大排得越靠前。
- **真实模型**：浏览器会把页面切成多个**独立舞台**（即层叠上下文）。每个舞台内部做排序，舞台和舞台之间也有排序。**我们只能在同一个舞台里比较 `z-index` 的大小**。
- **通俗比喻**：`child` 在 `parent` 舞台里排名第一（相当于班级第一），但 `parent` 舞台整体排不过 `mask` 所在的舞台（相当于年级排名不是第一）。你不能拿班级第一去压年级第一。
- **Demo 解析**：`child` 在 `parent` 舞台中，`parent` 的 `z-index` 是 `1`，而 `mask` 的 `z-index` 是 `10`。`parent` 整体输给 `mask`，导致 `parent` 内部的所有元素（包括 `z-index: 9999` 的 `child`）都被 `mask` 遮挡。

## 3. 层叠上下文 (Stacking Context) 详解 *Content-[03:11]

**定义**：
层叠上下文是一个独立的层叠空间。在这个空间内，子元素的 `z-index` 只与同一上下文的兄弟元素比较，**不会跨越上下文进行比较**。创建了层叠上下文，就等于创建了一个新的世界。世界内部怎么排序都可以，但对外只能派出“世界代表”去比较。

**创建层叠上下文的常见条件（面试高频清单）**：

1\. **定位 + z-index**：`z-index` 不为 `auto`，且 `position` 为 `relative`、`absolute`、`fixed` 或 `sticky`。（注意：单独写 `position: relative` 不一定创建，关键是 `z-index` 参与了层叠且不为 `auto`）。
2\. **透明度 (opacity)**：`opacity` 小于 `1` 时，会创建一个层叠上下文。
3\. **变换 (transform)**：`transform` 不等于 `none`。例如为了开启 GPU 加速写的 `transform: translateZ(0)` 也会创建层叠上下文。
4\. **其他触发合成层/独立渲染层的属性**：
   - `perspective` 或 3D 相关属性。
   - `isolation: isolate`。
   - `will-change`。
   - `filter`（滤镜）。

**记忆口诀**：“位”（定位）+ “透”（opacity）+ “变”（transform）+ “滤”（filter）+ “隔”（isolation）。凡是可能触发合成层的属性，都要警惕其带来的层叠上下文。

## 4. 案例原理解析与验证 *Content-[05:52]

**层级关系图解**：
- 根舞台（Root）包含 `parent` 舞台和 `mask` 舞台。
- `parent` 舞台内部包含 `child` 元素。
- `parent` 因为设置了 `position: relative` 且 `z-index: 1`，成为了一个独立舞台。

**验证实验 1：提升父元素层级**
- 将 `parent` 的 `z-index` 从 `1` 改为 `100`。
- **结果**：`parent` 赢得了与 `mask` 的比较，`child` 立刻盖住了 `mask`。
- **结论**：`child` 自己的 `9999` 并不关键，关键是让它所在的舞台（`parent`）先赢。

**验证实验 2：移除父元素的层叠上下文**
- 将 `parent` 的 `z-index` 删除或改为 `auto`。
- **结果**：`child` 又被 `mask` 遮挡。因为此时 `parent` 无法创建层叠上下文，导致层级比较规则发生变化。

**排查思路**：
看到 `z-index` 失效时，先不要看子元素的值写了多少，**先看它的祖先元素有没有创建层叠上下文**，以及祖先元素的层叠上下文是否被压住了。

## 5. 工程层面的解决方案 *Content-[07:45]

在实际工程中，我们通常有以下三种方案来解决 `z-index` 失效或层级混乱的问题：

1\. **把弹窗类的组件挂载到 `body` 上（最推荐/工程标准）**
   - **原因**：弹窗（Toast、Dropdown、Tooltip）本质上是全局覆层。如果放在业务组件内，容易被祖先上下文（如 `transform`、`overflow`、`opacity`）限制，陷入无尽的调参过程。
   - **实现**：
     - 原生写法：使用 Portal 将弹窗渲染到 `body` 下的 `div`（如 `port-root`）。
     - 框架写法：React 使用 `Portal`，Vue 使用 `Teleport`。本质都是把浮层放到更高的层级世界，从结构上避免业务容器的层叠上下文影响。

2\. **提升创建上下文的父元素层级**
   - **做法**：提高父元素（如 `parent`）的 `z-index`，让它在舞台比较中获胜。
   - **缺点**：引入新的维护成本，抬高一个舞台可能影响其他舞台或模块。

3\. **避免创建没有意义的上下文**
   - **场景**：通常发生在动画上。给动画容器加 `transform` 以为能优化，却意外创建了新的层叠上下文，导致浮层覆盖问题。
   - **正确做法**：把 `transform` 放到更内层元素上，或只在需要动画的元素上添加，不要加到大的容器上。

## 6. 面试回答模板 *Content-[09:40]

当面试官问：“`z-index` 为什么会失效？”时，可以按照以下模板回答：

1. `z-index` 本身不会失效，通常是因为元素处在不同的**层叠上下文（Stacking Context）** 里。
2. `z-index` 只能在一个 Stacking Context 里比较大小，不能跨上下文比较。
3. 在工程上解决这个问题，通常有三种方式：
   - 把浮层挂载到 `body` 上（如使用 React Portal / Vue Teleport）。
   - 提高父级层叠上下文的 `z-index`。
   - 避免创建无意义的层叠上下文（如滥用 `transform`）。

## AI 总结 *Content-[10:07]

`z-index` 失效的本质并非属性本身不起作用，而是由于**层叠上下文（Stacking Context）** 的隔离机制导致跨上下文比较无效。浏览器通过“舞台模型”将页面划分为多个独立的层叠空间，子元素的层级只能在其所属的父级上下文内进行比拼。在工程实践中，解决此类问题的最优解是利用 `Portal` 或 `Teleport` 将全局浮层直接挂载至 `body`，从而彻底规避复杂业务组件中因 `transform`、`opacity` 等属性意外创建的层叠上下文所带来的层级覆盖问题。
