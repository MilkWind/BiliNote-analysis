## 问题引入：z-index 失效的“玄学”现象 *Content-[00:21]

在前端开发中，我们经常会遇到一个典型的“玄学”问题：**z-index 为什么会失效？**

- **常见现象**：明明给元素写了 `z-index: 9999`，甚至改到 `99999`，元素还是被其他元素挡住。此时开发者往往会怀疑是浏览器 bug、CSS 写错了，或者认为 z-index 不支持某些元素。
- **核心结论**：`z-index` 从来没有失效。真正的问题在于，我们在用一个世界的数字去和另一个世界的元素比高低。这就引出了今天要讲的核心概念：**层叠上下文 (Stacking Context)**。

## 核心概念：层叠上下文与舞台模型 *Content-[02:04]

要理解 z-index 失效的原因，首先需要纠正对浏览器渲染模型的错误认知。

- **错误认知**：认为页面像一张纸，所有元素都在一个平面上排队，z-index 就像一个票号，数字越大排得越靠前。
- **真实模型（舞台模型）**：浏览器会把页面切成很多个**独立舞台**。每个舞台内部再做排序，而舞台和舞台之间也有排序。
- **核心规则**：我们**只能在同一个舞台（层叠上下文）里**比较 z-index 的大小。
- **生动比喻**：就像你在班级里考了第一名（子元素 z-index 很大），但是年级排名可能并不是第一（父元素舞台层级低）。你不能拿班级第一去压年级第一，比较关系压根不成立。

## 层叠上下文的定义与触发条件 *Content-[03:11]

### 什么是层叠上下文？
层叠上下文是一个**独立的层叠空间**。在这个空间内，子元素的 z-index 只与同一上下文的兄弟元素比较，不会跨越上下文进行比较。也就是说，创建了层叠上下文，就等于创建了一个新的世界。世界内部怎么排都可以，但对外只能派出“世界代表”（父元素）去比。

### 哪些 CSS 属性会创建层叠上下文？
在面试中，不需要背诵所有条件，但必须熟记以下高频触发条件：

1\. **定位 + z-index**：`z-index` 不能是 `auto`，且 `position` 的条件可以是 `relative`、`absolute`、`fixed` 或者是 `sticky`。
*注意：单独写 `position: relative` 不一定能创建层叠上下文，关键是 `z-index` 也参与了层叠（即 z-index 不能是 auto）。*

2\. **透明度 (opacity)**：`opacity` 小于 1 的时候会创建一个层叠上下文。

3\. **变形 (transform)**：`transform` 不等于 `none`。很多时候为了开启 GPU 加速会写 `transform: translateZ(0)`，这同样会触发层叠上下文。

4\. **其他常见属性**：
- `perspective` 或 3D 相关属性
- `isolation: isolate`
- `will-change`

**记忆口诀**：**“位”**（定位）+ **“透”**（opacity）+ **“变”**（transform）+ **“滤”**（filter）+ **“隔”**（isolation）。
*经验法则：凡是可能触发合成层（独立渲染层）的属性，都要警惕它带来的层叠上下文。*

## Demo 演示与排查思路 *Content-[05:51]

### Demo 场景还原
- **结构**：一个 `parent` 容器包含一个 `child` 元素，同级还有一个 `mask` 遮罩层。
- **样式**：`child` 设置了 `z-index: 9999`，`mask` 设置了 `z-index: 10`。`parent` 设置了 `position: relative` 和 `z-index: 1`。
- **现象**：黑色的 `mask` 把黄色的 `child` 盖住了。

### 现象解析
- 为什么 `child` 的 9999 比不过 `mask` 的 10？
- 因为 `parent` 满足“定位 + z-index”条件，创建了一个独立的层叠上下文（舞台）。
- 在根舞台（root）的比较中，`parent` (z-index: 1) 输给了 `mask` (z-index: 10)。
- `parent` 输了，它里面的所有东西（包括 z-index 为 9999 的 `child`）整体都会输给 `mask`，从而被遮挡。

### 验证与排查思路
- **验证 1**：把 `parent` 的 `z-index` 从 1 改成 100。此时 `parent` 赢得了和 `mask` 的比较，`child` 立刻就能盖住 `mask`。这证明 `child` 自己的 9999 并不关键，关键是让它所在的舞台先赢。
- **验证 2**：把 `parent` 的 `z-index` 删除或改成 `auto`。此时 `parent` 无法创建层叠上下文，`child` 直接和 `mask` 比较，9999 > 10，`child` 成功盖住 `mask`。
- **排查思路**：看到 z-index 失效时，**先不要看子元素的 z-index 具体值**，而是要先看它的**祖先元素**有没有创建层叠上下文，以及祖先元素的层叠上下文是否被压住了。

## 工程层面的三大解决方案 *Content-[07:44]

在真实工程开发中，如何解决 z-index 层级被覆盖的问题？推荐以下三种方案：

### 方案一：将弹窗类组件挂载到 body 上（最推荐/标准做法）
- **原因**：弹窗、Toast、Dropdown、Tooltip 等本质上是一个全局覆层。如果把它放在某个业务组件里，就可能会被祖先上下文限制（例如某个祖先写了 `transform`、`overflow` 或 `opacity`），从而陷入无尽的 z-index 调参过程中。
- **实现方式**：
  - 原生写法：直接通过 DOM 操作将弹窗挂载到 `body` 下。
  - React：使用 `Portal`。
  - Vue：使用 `Teleport`。
  - 本质都是把浮层放到更高的层级世界里，从结构上避免大部分业务容器的层叠上下文干扰。

### 方案二：提升创建上下文的父元素的层级
- **做法**：就像 Demo 中把 `parent` 的 z-index 提上去，让它在与其他舞台比较时获胜。
- **缺点**：会引入新的维护成本。在上下文里抬高了一个舞台，就可能影响其他的舞台或模块，导致“牵一发而动全身”。

### 方案三：避免创建没有意义的上下文
- **场景**：这种问题通常发生在动画上。比如给一个动画的 container 加了一个 `transform`，以为是为了性能优化，但它其实意外创建了新的层叠上下文，导致了内部浮层的覆盖问题。
- **正确做法**：把 `transform` 放到更内层元素上，或者只在需要动画的元素上加，不要加到大的容器上。

## 面试标准回答模板 *Content-[09:39]

当面试官问“z-index 为什么会失效”时，可以直接使用以下模板回答：

> “z-index 本身不会失效，通常是因为元素处在不同的层叠上下文里。z-index 只能在一个 Stacking Context 里比较大小。
> 
> 如果要在工程上解决这个问题，通常有三种方式：
> 1. 把浮层挂到 body 上（例如使用 React 的 Portal 或 Vue 的 Teleport）；
> 2. 提高父层叠上下文的 z-index；
> 3. 避免创建无意义的层叠上下文（例如在不需要的大容器上滥用 transform）。”

## AI 总结

视频深入剖析了前端开发中常见的“z-index 失效”问题。其本质并非 z-index 属性失效，而是由于**层叠上下文 (Stacking Context)** 的隔离机制，导致子元素的层级比较无法跨越父级创建的独立“舞台”。

理解该问题的核心在于掌握触发层叠上下文的 CSS 属性（如定位+z-index、opacity、transform 等）。在工程实践中，解决此类层级覆盖问题的最佳方案是通过 Portal/Teleport 将全局浮层直接挂载到 body，从而脱离业务组件的上下文限制；同时需规范动画属性的使用，避免意外创建层叠上下文。掌握这一机制，能够帮助开发者在面试中展现对 CSS 渲染原理的深刻理解，并在实际项目中快速定位和解决复杂的层级 Bug。
