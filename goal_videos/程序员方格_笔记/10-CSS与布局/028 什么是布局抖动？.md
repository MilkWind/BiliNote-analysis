## 引言：什么是布局抖动 *Content-[00:00]
- **常见现象**：页面滚动时感觉卡顿、动画播放不流畅、操作复杂列表时页面变得非常迟钝。
- **背后原因**：这些现象的背后很可能是**布局抖动（Layout Thrashing）** 在作祟。
- **学习目标**：系统理解布局抖动，学会如何发现它，并通过简单的原则进行优化，写出更加流畅的代码。

## 布局抖动的本质：强制同步布局 *Content-[00:52]
- **别名**：布局抖动的另一个名字叫做**强制同步布局（Forced Synchronous Layout）**，这个名字更直观地揭示了其本质。
- **典型特征**：在极短的时间内（通常是一帧画面的时间里），代码在“写入”和“读取”两件事之间反复交替进行。
  - **写入操作**：修改 DOM 元素的样式，特别是影响几何布局的属性（如 `width`、`height`、`margin`、`padding` 等）。
  - **读取操作**：从 DOM 中查询某个元素的几何属性（如 `offsetWidth`、`clientWidth`、`clientHeight`、`scrollTop` 等）。
- **产生后果**：
  - 当写入和读取操作交织并反复发生时，浏览器在渲染同一帧画面的过程中，被迫进行多次重复的布局计算和重绘。
  - 导致 CPU 使用率飙升，应用帧率急剧下降。
  - 用户感知到页面卡顿、掉帧，滚动和点击等交互因主线程被长时间占用而出现明显延迟。

## 浏览器理想的渲染流程 *Content-[02:39]
- **性能目标**：达到每秒 60 帧（60fps）的流畅体验，这意味着浏览器必须在 **16.6ms** 内完成一帧的所有渲染工作。
- **内置优化策略**：浏览器为了追求性能，天生会尝试**延迟和批量处理**耗费性能的布局工作。
- **标准渲染流程**：
  1. **收集变更**：收集 JS 中对 DOM 做出的所有写操作变更。
  2. **等待时机**：不会每改一个就重新渲染一次，而是等到当前宏任务执行完毕、准备绘制下一帧时统一处理。
  3. **计算样式**：重新计算受影响元素的样式。
  4. **计算布局（Reflow）**：确定每个元素在屏幕上的位置和大小。
  5. **绘制（Paint）**：将元素的像素信息填充到内存中。
  6. **合成（Composite）**：将不同图层合并到一起，最终显示在屏幕上。
- **核心思想**：在理想情况下，浏览器希望在一帧内只做**一次**布局计算和**一次**绘制。

## 触发强制同步布局的原因与错误示例 *Content-[05:10]
- **触发过程**：
  1. JS 执行写入操作（如修改元素宽度），使浏览器内部缓存的布局信息变成过期状态。
  2. 在浏览器有机会执行批量更新流程之前，代码立刻执行了一次读取操作（如获取 `offsetWidth`）。
  3. 浏览器发现布局信息已过期，但为了返回精确的最新值，被迫停下当前工作，立刻同步执行一整套渲染流程（重新计算样式、布局，甚至重绘）。
- **错误示例分析**：
  - 场景：在 `for` 循环中获取所有 `p` 标签，将它们的宽度设置为类名为 `.box` 的元素的宽度。
  - 问题：每次循环先执行写入（设置 `p` 标签宽度），使布局信息过期；接着为了获取写入的值，又去读取 `.box` 的 `offsetWidth`。
  - 结果：每次循环都迫使浏览器重新计算整个页面的布局。如果列表有成百上千个元素，将引发严重的性能灾难。

## 核心优化原则：读写分离 *Content-[08:48]
- **修复方案**：遵循**读写分离**原则。
- **优化示例**：在进入循环前，一次性读取 `.box` 的 `offsetWidth` 并缓存到变量中（Read 阶段）；在循环中仅使用缓存的变量去设置每个 `p` 标签的宽度（Write 阶段）。循环中没有任何读取布局属性的行为。
- **两大核心原则**：
  1. **先读后写，批量进行**：在代码逻辑开始前，一次性读取所有需要的布局信息（尺寸、位置等）并缓存到变量中，然后利用缓存变量批量更新 DOM。
  2. **避免读写交织**：在一个宏任务或一帧的生命周期里，刻意避免频繁的读写交替。保持“所有读在前面，所有写在后面”的清晰结构。
- **优化效果**：将优化的权力交还给浏览器，使其只需为大量变更做一次布局计算，大幅降低 CPU 消耗和渲染时间。

## 避免布局抖动的其他实践技巧 *Content-[11:09]
- **批量更新 DOM**：
  - 添加多个元素时，不要逐个使用 `appendChild`，应使用 `DocumentFragment` 收集所有节点后一次性插入真实 DOM。
  - 一次性设置 `innerHTML` 通常也比多次操作 DOM 子节点更高效。
- **利用样式类**：
  - 改变元素多个样式时，不要在 JS 中逐行设置 `style.width`、`style.height` 等。
  - 更好的做法是在 CSS 文件中预定义一个包含所有目标样式的类，在 JS 中只需执行一次 DOM 写入操作（修改 `className`）。
- **小心处理动画**：
  - 动画是布局抖动的高发区。尽可能使用不触发布局计算的 CSS 属性（如 `transform` 和 `opacity`）制作动画，它们可被 GPU 加速。
  - 若动画确实需要读取几何尺寸，应在动画开始前缓存好，或在节流（throttle）函数的回调中处理，避免在每一帧中去读取。
- **使用 `requestAnimationFrame` (RAF)**：
  - 在 RAF 回调的开头，集中执行所有需要“读”的操作。
  - 把所有“写”的操作放到一个嵌套的 RAF 回调里面。
  - 这样可以更好地与浏览器的渲染节奏对齐，确保读操作总是在写操作之前完成。

## 现代前端框架中的布局抖动问题 *Content-[13:54]
- **框架的局限性**：React 或 Vue 等现代前端框架虽然抽象了底层的 DOM 操作，但并不能自动规避所有导致布局抖动的逻辑，最终执行的仍然是浏览器的 DOM 操作。
- **典型踩坑场景**：
  - 在 `useEffect` 或 `componentDidMount` 中，先测量 DOM 节点尺寸（读），然后用该尺寸更新组件的 `state`（写/触发渲染）。
  - 如果在 `useLayoutEffect` 中这样做情况会更糟，因为它在浏览器绘制之前同步执行，读写交织极易触发强制同步布局。
- **解决思路**：
  - 与原生 JS 原则一致，尽量在同一个 `effect` 中完成计算和写入的闭环。
  - 避免多个不同的 `effect` 或 `hook` 之间来回传递布局信息。

## 课程总结 *Content-[15:43]
- **核心认知**：掌握布局抖动的核心在于理解浏览器的底层渲染机制，并建立起**读写分离**的意识。
- **问题本质**：在极短时间内交替读写 DOM 几何属性，迫使浏览器在渲染单帧画面时进行多次昂贵的同步布局计算。
- **发生原因**：浏览器为了保证 API 返回值的准确性，在布局信息因写入操作而过期时，必须打破自身的批量优化策略去进行同步计算。
- **规避方法**：严格遵循“先读后写、批量修改”的原则。先集中完成所有必要的 DOM 测量并缓存结果，再利用缓存结果统一更新 DOM。
