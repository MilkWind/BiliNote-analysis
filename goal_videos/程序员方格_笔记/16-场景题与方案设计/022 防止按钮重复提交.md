## 1. 面试题背景与考察点 *Content-[00:00]
- **面试题核心**：如何在前端防止表单重复提交，并确保用户只能提交一次。
- **业务痛点**：
  - 表单重复提交会在后端产生大量垃圾数据。
  - 存在用户恶意或故意频繁点击提交按钮的情况，给系统带来不必要的负担。
- **考察能力**：
  - 考察应聘者对表单交互技巧的处理能力。
  - 验证候选人是否真正参与过真实项目的开发，具备解决实际业务需求和边界问题的经验。

## 2. 方案一：禁用提交按钮 *Content-[02:24]
- **核心思路**：在用户点击提交后，立即禁用提交按钮，使其在请求完成前不可再次点击。
- **实现细节**：
  - 监听表单的 `submit` 事件。
  - 阻止默认的表单提交行为（使用 `preventDefault`）。
  - 将提交按钮的 `disabled` 属性设置为 `true`，使其变为不可用状态。
  - 发起 Ajax 请求提交数据。
  - 在请求成功的回调函数中，将按钮的 `disabled` 属性恢复为 `false`。
- **优点**：实现简单直观，能有效防止正常网络情况下的重复点击。
- **缺点与局限性**：
  - 如果提交时发生网络断开或请求失败，按钮将保持禁用状态，无法自动恢复。
  - 用户必须手动刷新页面才能再次操作，用户体验较差。

## 3. 方案二：使用 Token 值配合后端校验 *Content-[05:05]
- **核心思路**：前端生成唯一标识（Token），后端通过校验该标识来防止重复处理数据。
- **实现细节**：
  - 前端在提交时，生成一个唯一的 Token（例如基于时间戳生成），并随表单数据一起提交给后端。
  - 后端接收到请求后，校验该 Token 是否已存在。
  - 若数据库中已存在该 Token，说明是重复提交（如用户刷新页面或重复点击），后端直接拒绝执行写入、查询、增加、删除等操作。
  - 若 Token 不存在，则正常处理业务逻辑，并将该 Token 保存到数据库中。
- **优点**：从后端数据层面彻底杜绝重复提交，安全性与可靠性高。
- **缺点与局限性**：
  - 需要前后端紧密配合，后端需要增加额外的字段和校验逻辑。
  - 在实际开发中，后端开发人员可能会因为增加工作量而不愿配合修改。

## 4. 方案三：前端存储提交记录 *Content-[07:58]
- **核心思路**：利用前端本地存储（如 `sessionStorage`）记录提交状态，在提交前进行逻辑拦截。
- **实现细节**：
  - 监听 `submit` 事件并阻止默认行为。
  - 在提交前，检查 `sessionStorage` 中是否存在已提交的标识（例如存储一个布尔值 `true`）。
  - 如果检测到已提交，则弹出提示（如“请不要再重复提交”）并中断后续操作。
  - 如果未提交，则正常发起请求，并在成功后将 `sessionStorage` 中的标识设置为 `true`。
- **进阶处理（针对多条数据场景）**：
  - 如果业务允许提交多条不同的数据，需要在存储的 Key 中加入数据的唯一标识（如 `ID`）。
  - 这样既能防止同一条数据（同一个 `ID`）被重复提交，又不会阻碍不同数据的正常提交。
- **优点**：纯前端实现，无需后端配合，灵活性高，能有效防止页面刷新导致的重复请求。

## 5. 总结与最佳实践 *Content-[11:13]
- **综合应用原则**：前端代码相对不够严谨，为了确保业务逻辑的绝对正确，实际开发中通常会将多种方案结合使用。
- **推荐组合方案**：
  - **方案一（禁用按钮） + 方案三（前端存储记录）**：这种组合既能优化用户体验（按钮状态反馈），又能有效防止重复点击和页面刷新导致的重复请求，是前端最常用的最佳实践。
- **方案二的适用场景**：虽然需要跨端协调，但在对数据一致性要求极高的核心业务中，配合后端 Token 校验是最稳妥的兜底方案。
- **面试建议**：在面试时能够全面阐述这三种方案及其优缺点，并能结合实际场景给出组合使用的建议，能够充分证明你具备扎实的项目经验和解决复杂问题的能力。
