## 大文件上传背景与痛点 *Content-[00:06]

- **常见业务场景**：
  - 上传短视频或大视频文件。
  - 处理超大型 Excel 数据文件。
  - AI 场景下上传 AI 模型文件（通常高达几百 MB 甚至上 GB）。
- **传统上传方式（`input type="file"` + `FormData`）的痛点**：
  - **上传时间长**：文件体积大导致传输耗时久。
  - **极易中断且无法恢复**：网络波动、刷新浏览器、切换 Tab/应用、电脑熄屏或合盖等异常情况都会导致上传中断，且必须从头重新上传，用户体验极差。
  - **超时被 Kill**：前端请求库（如 axios）和后端服务器（如 Nginx）都有请求超时限制，大文件长时间传输极易被取消或强制断开。
  - **缺乏交互控制**：无法实现暂停上传、恢复上传，也无法精准显示上传进度。

## 核心解决方案：切片、哈希与秒传 *Content-[02:34]

- **文件切片（File Slicing）**：
  - 使用原生 `File.slice()` 方法将大文件切割成多个小块（例如每片 5MB）。
  - 切块后，单片文件体积小，在当前平均网速下仅需一两秒即可传完，大幅降低单次请求失败的风险。
- **哈希计算与文件指纹**：
  - 使用 `spark-md5` 库对文件内容计算哈希值，生成唯一的“文件指纹”。
  - **原理**：相同内容的文件会生成完全相同的哈希值。
  - **秒传实现**：前端将哈希值发送给后端，后端校验数据库中是否已存在该哈希。若存在，则直接返回“已存在”状态，前端无需再次上传，直接将状态置为“上传完成”，从而实现**秒传**功能。

## 性能优化：Web Worker 与并发控制 *Content-[04:07]

- **Web Worker 异步计算哈希**：
  - 大文件的哈希计算属于 **CPU 密集型任务**，非常耗时。
  - 若在主线程计算，会严重阻塞页面渲染和用户交互操作。
  - **解决方案**：引入 `Web Worker` 创建异步线程，将哈希计算放入 Worker 中执行。计算完成后，通过线程通信将结果交还给主线程，确保页面流畅。
- **并发控制上传**：
  - 当切片数量较多时，采用并发控制机制（如同时上传 3~4 个分片）代替串行逐个上传。
  - **优势**：大幅提升整体上传速度，显著缩短总上传时间。

## 断点续传与分片校验 *Content-[05:19]

- **分片校验（Track）**：
  - 在正式上传分片前，前端向服务端发起校验请求，判断当前文件是否处于“断点续传”状态。
  - 后端根据文件哈希查询已上传成功的分片列表（状态为 ready），并返回给前端。
- **断点续传实现**：
  - 前端接收到已上传分片的状态列表后，过滤掉这些已完成的分片。
  - 仅对剩余未上传的分片发起上传请求，从而实现**断点续传**，避免重复传输。
- **合并文件**：
  - 所有分片上传完成后，前端通知后端合并所有切片，还原为完整文件。

## 核心流程与细节优化 *Content-[06:14]

- **整体流程回顾**：
  1. 用户选择或拖拽文件。
  2. 判断文件大小：小文件直接上传；大文件（如 300MB~1GB+）进入分片上传流程。
  3. `Web Worker` 异步计算文件及各分片的哈希值。
  4. 校验哈希实现秒传，或进行分片校验实现断点续传。
  5. 并发上传剩余分片，完成后通知后端合并。
- **文件大小展示优化（面试细节亮点）**：
  - **常规做法**：通过 1024 的指数幂进行 `if-else` 判断（如 `> 1024` 为 KB，`> 1024*1024` 为 MB），然后拼接对应的单位文案（B, KB, MB, GB）。
  - **优化做法（数学公式）**：利用对数运算直接计算文件所处的数量级。
    - 计算公式：$\frac{\log(\text{fileSize})}{\log(1024)}$
    - 通过该公式计算出的值向下取整，即可直接得出文件是 KB、MB 还是 GB 级别，代码更加简洁优雅，是面试中的极佳加分项。

## 完整交互流程详解 *Content-[09:54]

1. **秒传检测**：前端计算整体文件哈希并传给后端。后端查库，若存在则直接返回成功，前端展示秒传完成。
2. **分片校验与续传准备**：若文件不存在，前端进行分片。请求后端查询该哈希下已上传的分片状态。前端过滤掉已上传分片，准备上传剩余部分。
3. **并发上传与失败重试**：
   - 设置合理的并发数量（如 3~4 个）。因为浏览器对同域名的并发请求数有限制（如 Chrome 通常为 6~8 个），合理控制并发既能提速，又不会阻塞页面其他核心网络请求。
   - **重试机制**：若某个分片上传失败，触发重试机制（如重试 3 次）。若多次重试仍失败，才将其标记为真正的上传失败。
4. **后端合并与回显**：所有分片上传成功后，通知服务端合并分片。服务端将完整文件移动至目标目录或上传至 OSS（对象存储），并返回文件具体路径，前端接收路径后进行 UI 回显，完成整个上传流程。
