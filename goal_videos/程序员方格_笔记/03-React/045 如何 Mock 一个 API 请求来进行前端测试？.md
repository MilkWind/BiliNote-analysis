## 为什么需要 Mock API 请求？ *Content-[00:01]

在前端开发中，测试是保证代码质量的关键一环，而几乎所有的前端应用都需要和后端 API 打交道。在进行自动化测试时，如果直接在测试中调用真实的 API，会面临以下严重痛点：

- **速度非常慢**：每个测试用例都需要走一遍网络请求，几十上百个用例跑下来可能需要几分钟，完全违背了自动化测试追求“快”的原则。
- **极其不稳定（误报）**：如果后端服务宕机或出现网络抖动，测试就会失败。这种失败通常与前端代码质量毫无关系，被称为“误报”。
- **产生副作用（脏数据）**：测试代码可能会执行创建用户等操作，导致数据库中产生脏数据，日积月累会给开发和维护带来巨大麻烦。
- **成本高昂**：如果调用的是按次计费的第三方 API 服务，运行完整的测试套件会产生大量的额外开销。

## Mock API 的定义与核心价值 *Content-[01:28]

为了解决上述问题，**API Mocking** 应运而生。

- **定义**：在测试期间，我们自己伪造一个完全可控的假接口，来替换掉真实的 API 接口。组件以为它在和服务端通信，实际上它只是在和 Mock 数据进行交互。
- **核心价值**：
  - **速度飞快**：所有数据都在本地瞬间返回，无需等待网络 I/O。
  - **极其稳定**：假接口的行为完全由开发者定义，100% 可预测，杜绝了网络和环境带来的不确定性。
  - **实现隔离**：让前端测试可以完全专注于验证前端组件本身的逻辑，无需担心后端服务的状态。
  - **全面覆盖边界情况**：可以轻松手动模拟网络错误、异常数据格式等，验证组件是否能正确处理这些边界情况。

## 方案一：Jest 内置的 Mock 功能 *Content-[04:02]

目前主流的方案主要分为两个派系，第一种是利用测试框架本身提供的能力，例如 **Jest** 自带的 Mock 功能。

- **核心思想**：在代码层面找到发起请求的函数（例如 `axios.get` 或原生的 `fetch`），然后把它替换成一个指定的假函数。这种方式非常直接，特别适合在单元测试中验证模块内部的逻辑。
- **代码实现示例（以原生 `fetch` 为例）**：
  1. 使用 `jest.spyOn` 监视全局对象上的 `fetch` 方法，相当于给该函数安装了一个监控探头。
  2. 调用 `mockResolvedValue`，告诉 Jest 下次当 `fetch` 被调用时，不要真的发请求，直接假装请求成功，并返回提供的对象。
  3. 因为 `fetch` 的返回值需要调用 `.json()` 方法来获取数据，所以返回的对象中必须提供一个假的 `json` 方法，让它返回最终想要的假数据（例如 `{ name: 'mock value' }`）。
- **缺点**：需要在测试代码中编写大量与 Mock 相关的设置代码，导致测试代码“变脏”，Mock 逻辑与测试断言逻辑混杂在一起，可读性较差。

## 方案二：MSW (Mock Service Worker) *Content-[06:20]

第二种方案是使用专门的库在网络层面做文章，这里的明星代表是 **MSW (Mock Service Worker)**。

- **核心思想**：完全不侵入业务代码，而是在网络层面工作。它利用浏览器或 Node.js 的 Service Worker 技术，去拦截真实发出的网络请求，然后返回假的响应。对于应用程序来说，它完全不知道自己被 Mock 了，一切就像真实发生的一样。
- **工作原理**：
  - 当应用发起请求时，请求在到达真正的网络之前，会被 MSW 的 Service Worker 捕获。
  - Service Worker 会检查请求的地址和方法。
  - 如果匹配到了预定义的 Mock 规则，就会直接返回伪造的响应数据，请求到此结束。
  - 如果没有匹配到，可以选择放行，让请求继续去获取真实数据。
- **代码组织**：
  - 通常会有一个专门的文件（如 `handlers.js`）来定义所有的 Mock 规则。
  - 写法非常直观，就像在写一个迷你的后端路由。例如，针对一个 GET 请求，当被拦截时返回一个包含动态生成用户名的 JSON 对象。
- **优势**：
  - 测试文件变得非常干净，完全没有 `jest.spyOn` 或 `mockResolvedValue` 的痕迹。
  - 可以直接渲染组件，然后像真实环境一样去断言数据加载后应该出现的内容（如使用 RTL 提供的 `findByText`），代码可读性和维护性大大提高。

## Jest Mock 与 MSW 的对比总结 *Content-[10:58]

| 对比维度 | Jest Mock | MSW (Mock Service Worker) |
| :--- | :--- | :--- |
| **工作层级** | 应用层（代码层面替换函数） | 网络层（拦截网络请求） |
| **侵入性** | 高（Mock 代码与测试逻辑混杂） | 低（测试代码纯粹，逻辑分离） |
| **真实性（保真度）**| 一般（仅模拟函数返回值） | 极高（模拟真实的网络环境和请求流程） |
| **适用范围** | 适合小范围的单元测试 | 可覆盖单元测试、集成测试到端到端测试（E2E）的所有场景 |

## 面试回答思路与技巧 *Content-[12:05]

当面试官询问：“在前端测试中，你是如何处理 API 请求的？能不能比较一下不同方法的优缺点？”时，建议按照以下结构优雅地组织回答：

1. **说明 Mock 的必要性**：首先点出直接请求真实 API 的几大痛点（速度慢、不稳定、有副作用、成本高），体现你对测试工程化有深入的思考。
2. **介绍 Jest Mock**：说明它的原理（在应用层替换函数）和适用场景（基础的单元测试），展示你扎实的基础知识。
3. **重点介绍 MSW**：强调它是目前更先进、更推荐的方案。解释它在网络层拦截的优势，特别是无侵入性和高保真度。
4. **给出明确总结**：表达你在实际项目中更倾向于使用 MSW，因为它能带来更可靠、更高质量的测试体验。

## 核心知识点回顾 *Content-[13:06]

1. **API Mocking** 是前端自动化测试中绕不开的一环，是前端开发者的必备技能。
2. **Jest Mock** 作为测试框架的内置功能，简单快捷，适用于基础的单元测试。
3. **MSW** 作为网络层的拦截方案，提供了无侵入、高保真的 Mock 能力，是前端项目中保障接口测试质量的首选工具。
