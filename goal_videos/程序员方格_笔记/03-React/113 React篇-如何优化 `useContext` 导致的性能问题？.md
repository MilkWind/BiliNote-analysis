## 引言与背景 *Content-[00:02]
- **场景痛点**：在日常开发和面试中，`useContext` 的性能问题几乎是一个绕不开的话题。常见场景是：明明只是在 Context 中更新了一个很小的数据片段，结果发现整个相关的组件树都跟着重新渲染，甚至引发了页面的卡顿。
- **核心原因**：这背后很可能是 `useContext` 在悄悄影响着应用的性能。
- **视频思路**：本视频将遵循“理解 -> 表达 -> 应用”的思路，从根源上理解 `useContext` 为什么会引发不必要的渲染，探讨如何在面试中清晰表达对该问题的理解，最后介绍两种基础的优化方案以改善应用性能。

## useContext 基础回顾与性能隐患根源 *Content-[01:25]
### 基础用法回顾
- **定义 Context**：使用 React 提供的 API `const MyContext = createContext(initialValue)` 创建一个 Context，可传入初始值。
- **提供数据**：在父组件中使用 `<MyContext.Provider value={{ a, b }}>` 包裹子组件树。
- **消费数据**：在子组件中使用 `const myContext = useContext(MyContext)` 获取数据，通过 `myContext.a` 直接访问属性。
- **核心作用**：`useContext` 能够让我们在组件树中跨层级共享状态，有效避免了 **Props Drilling**（属性透传）问题，无需一层一层将 Props 传递下去。

### 性能隐患的根源
- **关键特性**：当 Provider 的 `value` 发生变化时，**所有**消费了该 Context 的组件都会被强制重新渲染。
- **缺陷分析**：即使组件本身并没有用到那部分变化的数据，也会被重渲染。这是因为 `useContext` 在底层设计上**没有内置精密的过滤器或选择器**，它默认订阅的是**整个 Context 的值**。只要这个值（通常是引用）发生任何变化，所有订阅者都会被通知并触发更新。

## 面试表达：如何清晰描述 useContext 性能问题 *Content-[04:52]
当面试官提问“Context API 有哪些潜在的性能问题？如何优化？”时，建议按照以下结构组织回答，以体现逻辑性和深度：

1. **点明问题核心**：
   - `useContext` 的性能问题主要在于：当 Provider 提供的 `value` 更新时，所有通过 `useContext` 订阅该 Context 的组件都会触发重新渲染。
   - 这种重渲染是默认发生的，即便组件依赖的数据在此次更新中并没有实际改变。

2. **解释背后原因**：
   - `useContext` 本身订阅的是整个 Context 对象。React 通过比较 Provider 提供的 `value` 的**引用地址**来判断是否发生了变化。
   - 如果 `value` 是一个对象或数组，只要它的引用地址发生了改变（即使内容完全一样），React 就会认为 Context 发生了更新，从而通知所有消费者组件进行重新渲染。

3. **对比状态管理库**：
   - 它不像 Redux 中的 `useSelector`。`useSelector` 允许我们只订阅 Context 中关心的那一部分数据，或者进行更细致的比较，而 `useContext` 缺乏这种细粒度的控制能力。

## 优化策略一：拆分 Context *Content-[06:42]
- **适用场景**：应用中存在一个包含全局状态的“包罗万象”的 Context（例如同时包含用户认证信息、主题皮肤配置、应用程序设置等）。此时，任何一项信息的微小变动（如用户仅切换了应用皮肤主题），都会导致只关心用户认证的组件也跟着重新渲染，造成不必要的性能开销。
- **核心思想**：将大而全的 Context 拆分成更小、更专注、职责更单一的 Context。
- **具体实践**：
  - 将庞大的 Context 拆分为：`AuthContext`（只关心用户认证）、`ThemeContext`（只关心主题设置）、`SettingContext`（关心应用设置）等。
  - **按需订阅**：组件只订阅它们真正关心的上下文。例如，用户头像组件只订阅 `AuthContext`，主题切换组件只订阅 `ThemeContext`。
- **优势**：让组件订阅所需的最小信息集合，从而减少不相关更新带来的影响。这是最直接且非常有效的优化方案。

## 优化策略二：使用 useMemo / useCallback 稳定 Value *Content-[08:42]
- **问题场景**：Context Provider 自身可能会因为父组件的重新渲染或内部管理的其他状态发生变化而重新渲染。如果在 Provider 每次渲染时，都重新创建一个新的对象或数组作为 `value` 传递下去，即使新对象的内容完全一样，由于**引用地址不同**，React 也会认为 Context 发生了更新，导致所有消费者组件不必要地重渲染。
- **核心思想**：在 Context Provider 内部，使用 `useMemo` 或 `useCallback` 来确保传递给 Provider 的 `value` 属性具有**稳定的引用**。
- **具体实践**：
  - 将状态和函数（如 `user`、`count`、`increaseCount`）组成一个 `contextValue` 对象。
  - 使用 `useMemo` 创建该 `value` 对象，并将其依赖项数组设置为 `[user, count, increaseCount]`。这意味着只有当这三项真正发生变化时，`useMemo` 才会重新计算并返回新的 `value`。
  - **特别注意**：对于函数（如 `increaseCount`），必须使用 `useCallback` 进行包裹，返回函数的 memoized 版本，以保证函数引用的稳定性。
- **优化效果**：当 Provider 因其他原因（如父组件重渲染）而重新渲染时，只要依赖项没变，`value` 的引用就保持不变，从而避免了消费者组件的不必要重渲染。
- **重要原则**：当 Context Provider 传递的 `value` 是一个对象或者数组的时候，**一定要**使用 `useMemo` 或 `useCallback` 来保证它们引用的稳定性。

## 总结 *Content-[11:57]
- 深入理解了 `useContext` 可能带来的性能瓶颈：主要是由于其对整个 Context 值的订阅机制，导致引用变化时引发全局不必要的重渲染。
- 掌握了在面试中描述该问题的标准话术，能够清晰指出问题并解释底层引用比较机制。
- 掌握了两个基础且实用的优化技巧：
  1. **拆分 Context**：实现组件的按需订阅。
  2. **稳定 Value 引用**：使用 `useMemo` 或 `useCallback` 避免对象/函数引用频繁变化。
