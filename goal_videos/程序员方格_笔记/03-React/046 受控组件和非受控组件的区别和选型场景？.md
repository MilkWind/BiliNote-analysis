## 引言：表单处理的核心问题 *Content-[00:01]

在 React 的世界里，表单处理一直是一个绕不开的话题，其中**受控组件**和**非受控组件**更是面试中的高频考点。

本集的核心围绕一个“灵魂拷问”展开：**组件的状态究竟是谁说了算？** 
通过深入剖析这两种组件的内部机制，最终聚焦于实战，明确在真实项目中应该如何进行技术选型。

## 受控组件 (Controlled Components) *Content-[00:54]

### 核心概念
在受控组件中，表单里的所有数据有且只有一个管理者，那就是 **React 的 `state`**。
因此，回答“谁说了算”：在受控组件里，是 **React 的 `state`** 说了算，它就是组件的唯一数据源。

### 数据流闭环
受控组件的数据流动是一个非常清晰的闭环：
1. 输入框里显示的内容（`value`）由 `state` 决定。
2. 用户在输入框打字，触发 `onChange` 事件。
3. 在 `onChange` 的事件处理函数中更新 `state`。
4. `state` 一旦更新，就会触发组件的重新渲染（re-render），从而让输入框显示最新的内容。
这就是一个从 `state` 到视图，再从用户操作回到 `state` 的完整闭环。

### 代码实现逻辑
1. 使用 `useState` 定义一个 `state` 变量（如 `value`）来存储输入框的值。
2. 定义 `handleChange` 事件处理函数，在输入时被调用，通过 `setValue` 更新 `state`。
   - *进阶操作*：可以在这里对输入值进行处理，例如强制转换为大写。
3. 将 `state` 的 `value` 属性和 `handleChange` 处理器绑定到 `input` 元素上。
4. 因为数据都存储在 `state` 中，可以非常方便地在任何地方实时展示该数据。

## 非受控组件 (Uncontrolled Components) *Content-[04:03]

### 核心概念
非受控组件的核心与受控组件恰好相反：表单的数据是由 **DOM 节点自己来管理**的，React 不需要去控制它。
因此，回答“谁说了算”：是 **DOM** 说了算。React 只是一个读取者，在需要的时候才去 DOM 那里把数据拿过来。

### 数据读取机制
React 通过 **`useRef`** 来读取 DOM 中的数据，流程如下：
1. 使用 `useRef` 创建一个引用（ref），就像一个标记。
2. 把这个 `ref` 贴到想要读取的 DOM 元素上（例如 `input`）。
3. 在需要数据的时候（例如点击提交按钮），通过 `ref.current.value` 直接拿到 DOM 元素当时的实时值。

### 代码实现逻辑
1. 使用 `useRef` 创建一个 ref，例如命名为 `inputRef`。
2. 将 `ref` 属性直接传给 `input` 组件，完成挂载。这样 React 就知道这个 ref 指向的是该 input DOM 节点。
3. 当需要数据时（例如触发 `handleSubmit` 提交函数），直接通过 `inputRef.current.value` 读取输入框当前的值。

**关键特点**：从头到尾没有使用 `state`，也没有 `onChange`。组件**不会**因为用户的每一次输入而重新渲染。

## 核心区别对比 *Content-[06:30]

| 对比维度 | 受控组件 (Controlled) | 非受控组件 (Uncontrolled) |
| :--- | :--- | :--- |
| **数据源** | React `state` | DOM 本身 |
| **数据流** | 清晰的单向数据流 | React 层面没有数据流，数据存在 DOM 里 |
| **值的获取** | 可以实时获取（因为值就在 `state` 里） | 只有主动去问时，通过 `ref` 才能拿到 |
| **实现方式** | 依赖 `useState` + `onChange` | 依赖 `useRef` |

## 实战选型场景 *Content-[07:37]

在面试和实际开发中，到底应该用哪一个？这不存在绝对的答案，完全取决于**业务场景**。

### 优先使用受控组件的场景
1. **实时验证表单**：用户每输入一个字符，就需要判断格式是否正确。
2. **动态控制 UI**：根据输入框的内容动态启用或禁用提交按钮（如内容为空时按钮置灰）。
3. **强制限制输入格式**：例如强制输入大写，或者自动添加信用卡号的空格。
4. **状态共享**：输入框的状态需要被其他多个组件共享和使用时，必须使用受控组件，通过**状态提升**来管理，这是最佳实践。

### 适合使用非受控组件的场景
1. **简单的一次性表单**：如搜索框或简单的登录表单，用户填完点提交即可，使用非受控可以减少模板代码。
2. **集成非 React 库**：当需要集成一些老旧的、直接操作 DOM 的第三方库（如 jQuery 插件）时，非受控组件是绝佳的桥梁。
3. **性能优化**：如果表单非常复杂且输入极其频繁，使用受控组件可能会因为频繁的 re-render 带来性能开销，此时非受控可以避免这点。
4. **文件上传**：`<input type="file">` 元素的 `value` 是一个只读属性，只能通过 `ref` 去读取，因此它天生就适合用非受控组件来处理。

## 面试回答技巧与话术 *Content-[09:58]

当面试官询问：“谈谈你在 React 中对受控组件和非受控组件的理解？区别是什么？项目中如何选型？”时，建议按照以下四个步骤回答，确保逻辑清晰：

1\. **定义先行**
先用一句话点出最核心的区别。
*话术参考*：“面试官您好，受控和非受控组件最核心的区别在于**数据源不同**。前者的数据源是 React `state`，后者是 DOM 本身。”

2\. **细节展开**
在定义之后，展开讲解数据流和实现方式的对比。
*话术参考*：“在数据流和实现上，受控组件依赖 `useState` 和 `onChange` 形成单向数据流；而非受控组件则依赖 `useRef` 在需要时直接读取 DOM 数据。”

3\. **场景驱动（关键）**
结合具体的项目经历举例，展示实战经验。
*话术参考*：“在我之前做的一个用户注册功能中，因为需要实时校验用户名是否被占用，所以我选择了**受控组件**；而在另一个文件上传的功能里，我使用了**非受控组件**和 `ref` 来获取文件对象。”

4\. **总结升华**
表明对技术的辩证思考，展现高级开发者的素养。
*话术参考*：“总的来说，两者没有绝对的好坏。我会根据具体的业务需求，比如是否需要实时控制输入的过程、是否涉及复杂表单的性能考量，来选择最合适的技术方案。”

## 课程总结 *Content-[12:00]

1. **受控组件**：React `state` 是唯一的数据源，适合需要实时控制的精细化场景。
2. **非受控组件**：DOM 是数据源，通过 `useRef` 来读取，更适合简单、一次性的场景。
3. **选型关键**：做选择的核心在于**你是否需要关心和响应用户输入的过程**。
