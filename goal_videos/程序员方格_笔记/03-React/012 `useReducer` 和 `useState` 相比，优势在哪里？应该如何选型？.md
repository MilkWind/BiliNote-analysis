## 引言：何时使用 useReducer *Content-[00:02]

在日常开发中，`useState` 是开发者最熟悉的状态管理 Hook，几乎出现在每个函数组件中。然而，何时应该考虑使用其“兄弟” `useReducer`，是面试官考察开发者对 React 状态管理理解深度的常见问题。

很多开发者存在一个误区，认为 `useReducer` 类似 Redux，非常复杂，且只有在大型项目中才会用到。实际上并非如此。本笔记将从三个层面深入探讨：
1\. **核心优势**：`useReducer` 相比 `useState` 解决了什么问题。
2\. **面试表达**：如何清晰、有条理地阐述两者的区别与选型。
3\. **实际选型**：在应用开发中，基于哪些考量来决定使用哪一个。

## 回顾 useState 与 useReducer 基础 *Content-[01:43]

### useState 的局限性
`useState` 非常直观，一行代码即可完成状态的声明和更新，是处理独立、简单状态（如开关切换、输入框值）的最佳选择。但当组件逻辑变得复杂时，它会暴露出以下问题：
- **状态相互依赖**：组件内存在多个关联状态，下一个状态严重依赖前一个状态。虽然 `useState` 支持函数式更新，但依赖逻辑复杂时，代码阅读起来非常费劲。
- **更新逻辑分散**：状态更新逻辑散落在各个事件处理函数中（如按钮点击改变状态 A 和 B，输入框变化改变状态 B 和 C），追踪和维护困难。
- **Props 冗长**：将多个状态更新函数传递给子组件时，会导致 props 变得非常臃肿。

### useReducer 的基本语法
`useReducer` 的基本语法如下：
```javascript
const [state, dispatch] = useReducer(reducer, initialState);
```
- **reducer 函数**：接收 `currentState` 和 `action`，返回 `newState`。
- **action 对象**：描述发生了什么的对象，通常包含 `type` 字段（表示操作类型）和可选的 `payload` 字段（表示携带的数据）。

`useReducer` 借鉴了 Redux 的核心思想，但它是一个内置 Hook，主要用于**组件内部**的复杂状态管理。

## useReducer 的四大核心优势 *Content-[04:56]

1\. **复杂状态的集中管理**
当状态是一个包含多个子值的复杂对象，或更新逻辑依赖多个条件判断时，`reducer` 提供了一个集中的处理位置。所有状态转换规则都清晰定义在 `reducer` 内部，通过不同的 `action type` 区分，极大增强了代码的可读性和可维护性。
*示例*：在具有联动关系的复杂表单中，使用 `useReducer` 可以清晰定义 `update field`、`validate phone` 等 action，避免代码混乱。

2\. **稳定的 dispatch 函数与性能优化**
当需要将状态更新能力传递给深层嵌套的子组件时，使用 `useState` 需要传递多个 `setState` 函数，而 `useReducer` 只需传递一个 `dispatch`。
更重要的是，React 保证 `dispatch` 函数的引用是**稳定**的（在多次渲染间不会改变）。这对于使用 `React.memo` 优化的子组件非常友好，能有效避免因回调函数引用变化导致的不必要重渲染。

3\. **极佳的单元测试性**
`reducer` 是一个**纯函数**（相同输入总是返回相同输出，无副作用）。这使得核心的状态逻辑非常容易进行独立的单元测试，开发者只需传入不同的 `state` 和 `action` 组合验证结果，无需关心 React 组件的渲染过程。

4\. **更清晰的 action 流**
通过 `dispatch` 触发状态更新，使得每次更新的意图非常清晰。`action` 明确描述了要做什么以及需要什么数据。这不仅有助于理解复杂状态的流转，配合类似 Redux DevTools 的调试思路，也能清晰追踪是哪个 action 触发了状态改变。

## 面试指南：如何回答两者的区别与选型 *Content-[09:03]

面试官通常希望考察你对 API 的深入理解、根据场景做技术选型的能力，以及对可维护性、可测试性和性能的考量。

### 建议的回答结构
- **定位差异**：`useState` 是处理简单独立状态的基础 Hook，非常便捷；当状态逻辑变复杂（多子值、依赖前置状态、逻辑分散）时，应倾向使用 `useReducer`。
- **useReducer 的三大好处**：
  1. 代码结构更清晰，状态转换规则集中在一处，易于维护。
  2. 传递稳定的 `dispatch` 给子组件，配合 `React.memo` 可有效避免不必要的重渲染。
  3. `reducer` 是纯函数，无副作用，极易进行单元测试。
- **useState 的适用场景**：如果组件只有一两个状态且更新逻辑简单直接，使用 `useState` 更加简洁明了。
- **核心结论**：选型的关键在于评估状态管理的复杂性和可维护性。

### 面试避坑指南
- **不要绝对化性能**：不要断言 `useReducer` 性能一定比 `useState` 好。`useReducer` 带来了额外的抽象层，对于极简状态，`useState` 的开销其实更小。性能考量必须结合具体场景。
- **区分 useReducer 与 Redux**：`useReducer` 提供了类似 Redux 的状态管理模式，但其作用域通常是组件级别，或通过 Context API 实现有限的跨组件共享。它**不是**全局状态管理的完整解决方案，也**不是** Redux 的替代品。

## 实际项目中的选型考量与决策流程 *Content-[13:33]

在实际项目中，可以通过以下四个考量点来辅助决策：

### 1. 状态的复杂度
- **简单状态**：单个布尔值、数字、字符串或结构简单且逻辑清晰的对象/数组，`useState` 足够。
- **复杂状态**：嵌套较深的对象、包含多个关联子属性，且更新逻辑复杂（如更新 A 需基于条件更新 B）。*经典示例*：带有加、减、重置、按步长增加等多种操作的计数器，此时 `useReducer` 优势明显。

### 2. 状态更新逻辑的分布
- 如果更新逻辑简单且仅在一两处触发，`useState` 的内联函数更方便。
- 如果多个用户交互或事件以不同方式影响同一组状态，导致逻辑分散在各个事件处理器中，使用 `useReducer` 将所有更新逻辑收敛到一处，通过 `action type` 区分，会使逻辑更集中。

### 3. 是否需要将状态逻辑传递给子组件
- 如果需要将多个 `setState` 函数逐层传递给深层子组件，不仅繁琐，还易导致不必要的重渲染。
- 使用 `useReducer` 只需传递一个 `dispatch`，既清爽又有助于性能优化，且可完美配合 Context API 使用。

### 4. 对状态逻辑可测试性的高要求
- 如果组件中包含关键且复杂的业务逻辑（体现在状态转换上），将其抽离到纯函数 `reducer` 中，可以非常方便地进行单元测试，保证逻辑正确性。

### 经验法则与决策流程
- **默认起步**：对于新组件或新功能，默认从 `useState` 开始，它是最快最直接的选择。
- **重构时机**：在开发中如果发现需要写多个 `useState`、一个操作需更新多个状态、更新逻辑难以一眼看明白，或需要把一堆 `setState` 往下传好几层，就应认真考虑重构为 `useReducer`。
- **前瞻性决策**：如果在需求分析阶段就预见到组件未来的状态管理必然非常复杂，一开始就选择 `useReducer` 可避免后续重构。

### 何时不需要 useReducer？
- **全局状态管理**：对于应用级别的全局状态管理（特别是大型应用），应选择 Redux Toolkit (RTK)、Zustand、Jotai 等专业工具，它们提供了更完善的中间件和性能优化方案。
- **避免过度设计**：如果组件状态真的很简单，硬用 `useReducer` 会增加不必要的代码和心智负担，此时 `useState` 就是最优解。

## 总结回顾 *Content-[19:13]

- `useState` 适用于简单、独立的状态；`useReducer` 更擅长处理相关联、具有复杂更新逻辑的状态集合。
- `useReducer` 的核心优势在于：通过集中的 `reducer` 函数管理状态使逻辑更清晰；提供稳定的 `dispatch` 函数优化子组件渲染性能；纯函数特性让单元测试更简单。
- 选型的关键在于评估当前状态的复杂度、更新逻辑的分布情况，以及对可维护性和可测试性的要求。没有绝对的优劣，只有最适合当前场景的选择。
