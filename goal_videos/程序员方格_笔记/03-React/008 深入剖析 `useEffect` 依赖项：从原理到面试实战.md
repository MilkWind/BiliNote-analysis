## useEffect 基础与无依赖项情况 *Content-[01:43]
- **useEffect 的核心作用**：允许在函数组件中执行副作用操作（如数据获取、设置订阅、手动更改 DOM）。这些操作通常在 React 完成 DOM 更新后异步执行。
- **依赖项数组的作用**：告诉 React 在什么时候需要重新执行定义的副作用函数。
- **情况一：不传递依赖项数组**
  - **行为**：副作用函数在每一次组件渲染完成后（包括首次渲染和之后的每一次更新）都会执行。
  - **风险**：如果组件频繁更新，或者副作用内部触发了组件更新（例如执行 `setCount`），会导致严重的性能问题，甚至造成无限循环。
  - **建议**：除非明确知道每次渲染都需要执行该回调函数，否则极不推荐这种写法。

## 传递空数组的情况 *Content-[04:37]
- **情况二：传递空数组 `[]`**
  - **行为**：副作用函数仅在组件首次渲染（Mount）时执行一次。如果函数返回了一个清理函数，则该清理函数会在组件卸载（Unmount）时执行一次。后续的组件更新不会触发该 Effect。
  - **适用场景**：非常适合那些只需要执行一次的设置类操作。
    - 获取初始数据。
    - 设置定时器或订阅。
    - 添加全局事件监听器。

## 传递包含依赖项的数组与 Object.is 机制 *Content-[06:31]
- **情况三：传递包含依赖项的数组（最常用）**
  - **行为**：首次渲染时执行。在后续每一次渲染完成时，React 会检查数组中的每一个依赖项，与上次渲染时的值进行比较。只要至少有一个依赖项发生变化，副作用函数就会被重新执行。
- **React 的比较机制：`Object.is`**
  - React 使用原生方法 `Object.is` 来判断两个值是否相等。
  - **原始类型**：行为与严格相等 `===` 基本一致，但有两个特殊情况：
    - `Object.is(NaN, NaN)` 返回 `true`（而 `NaN === NaN` 为 `false`）。
    - `Object.is(+0, -0)` 返回 `false`（而 `+0 === -0` 为 `true`）。
  - **引用类型**：比较的是内存中的**引用地址**。
    - 即使两个对象或数组的内容完全一模一样，只要它们的实例（内存地址）不同，React 就会认为它们发生了变化。这是理解依赖项问题的核心重点。

## 经典问题：过时闭包 (Stale Closure) *Content-[09:42]
- **问题描述**：如果 Effect 函数内部使用了组件作用域中的变量（如 `count`），但没有将其添加到依赖项数组中，就会产生“过时闭包”问题。
- **具体表现**：Effect 函数会记住它首次执行时拿到的变量旧值（例如 `count` 初始为 0）。即便后续通过 `setCount` 不断更新 `count`，Effect 内部拿到的依然是旧值。
- **正确做法**：将 `count` 添加到依赖项数组中。当 `count` 改变时，旧的定时器（如 `setInterval`）会被清除，新的定时器会带着新的 `count` 值被重新创建。
- **补充优化**：对于定时器场景，更好的做法是使用函数式更新（如 `setCount(prev => prev + 1)`）来避免频繁清除和设置定时器的问题。

## 面试实战：如何回答依赖项数组的理解 *Content-[11:46]
当面试官提问“谈谈你对 `useEffect` 依赖项数组的理解”时，建议按以下结构组织回答：

1\. **开门见山，点明核心作用**
   - 依赖项数组的目的是精确控制副作用函数的执行时机。
   - 它告诉 React 在哪些数据发生变化时才需要重新运行 Effect，从而优化性能，避免不必要的计算或 API 调用，并确保 Effect 内部能访问到最新的 `props` 和 `state`。

2\. **分类讨论行为差异**
   - **不提供依赖项**：每次渲染（含首次和更新）都执行。需警惕性能和无限循环问题。
   - **提供空数组**：仅在首次挂载时执行一次。适合一次性设置（初始数据获取、全局事件监听）。
   - **提供包含依赖项的数组**：首次挂载及后续依赖项变化时执行。React 使用 `Object.is` 比较每一项。

3\. **强调关键概念**
   - **`Object.is` 比较机制**：原始类型比较值，引用类型比较地址。若依赖项每次渲染都重新创建（如函数、对象），即使内容不变也会触发重新执行。
   - **过时闭包 (Stale Closure)**：Effect 内部使用了外部响应式数据但未声明在依赖项中，导致变量保持首次执行时的旧值。原则：Effect 用到的所有外部响应式数据都应列入依赖项。
   - **官方插件**：强烈建议开启 `eslint-plugin-react-hooks`，它会自动检测并提示遗漏的依赖项，避免难以察觉的 Bug。

4\. **面试加分项（优化手段）**
   - 依赖项是函数时：配合 `useCallback` 确保函数引用稳定。
   - 依赖项是复杂对象/数组且创建耗时时：配合 `useMemo` 获取记忆化版本。
   - `setState` 或 `useReducer` 返回的 `dispatch` 函数：React 保证其引用永久稳定，可安全放入依赖项，不会导致不必要的重复执行。

## 实际场景一：依赖项是函数 *Content-[17:14]
- **场景描述**：搜索框输入变化时，需要调用组件内部定义的 `fetchResult` 方法。
- **错误写法**：直接在组件内定义 `fetchResult` 并放入 `useEffect` 的依赖项。
  - **问题**：组件每次重新渲染时，`fetchResult` 都会是一个全新的实例（引用改变），导致 `useEffect` 在每次渲染后都重新执行，即使搜索关键字 `query` 没有变化。
- **解决方案**：
  1\. **使用 `useCallback`**：用 `useCallback` 包裹 `fetchResult`。若函数内部依赖 `userId`，则将 `userId` 作为 `useCallback` 的依赖项。这样可保证函数引用的稳定性，避免 Effect 重复执行。（面试中答出此方案即可拿高分）。
  2\. **将函数移入 Effect 内部**：直接在 `useEffect` 内部定义该函数（如 `const localFetch = ...`），这样它就不需要作为依赖项，也能解决重复依赖的问题。

## 实际场景二：依赖项是对象或数组 *Content-[21:04]
- **场景描述**：依赖项是通过 `props` 传入的配置项 `options`。父组件每次渲染都会创建一个新的 `options` 对象，导致子组件的 `useEffect` 频繁重新执行。
- **解决方案**：
  1\. **使用 `useMemo`**：在父组件中使用 `useMemo` 包裹 `options` 对象，保证其引用的不变性。
  2\. **解构对象属性**：在子组件中解构出关心的具体属性（如 `const { type } = options`），然后只将 `type` 放入依赖项。只要 `type` 不变，即使 `options` 是新对象，Effect 也不会执行。
  3\. **深度比较（不推荐）**：理论上可通过 `JSON.stringify(options)` 序列化后作为依赖项。但由于序列化复杂对象性能较差，且无法处理函数等特殊值，通常不推荐，应优先考虑 `useMemo` 或解构。
