## 核心渲染机制与引用类型问题 *Content-[00:58]

在深入探讨 `useMemo` 和 `useCallback` 之前，需要先回顾 React 的核心渲染机制与 JavaScript 的引用类型特性。

- **React 核心渲染机制**：当一个父组件重新渲染时，默认情况下它的所有子组件也会跟着重新渲染。
- **优化手段 `React.memo`**：为了避免不必要的渲染，React 提供了 `React.memo`。它会对子组件的 `props` 进行浅比较，只有当 `props` 发生变化时，子组件才会重新渲染。
- **JavaScript 引用类型陷阱**：在 JavaScript 中，函数、对象和数组都是引用类型。这意味着即使一个函数或对象的内容看起来一模一样，但如果它们在不同的渲染周期中被创建，它们的引用地址就是不同的。
- **问题产生**：如果给一个被 `React.memo` 包裹的子组件传递在父组件中定义的函数或对象作为 `prop`，当父组件因为任何原因重新渲染时，这个函数或对象就会被重新创建。即便它的逻辑或内容没有丝毫改变，其引用也改变了。`React.memo` 在进行浅比较时会认为 `prop` 改变，从而导致子组件依然重新渲染。
- **解决方案**：为了解决引用地址频繁变化导致 `React.memo` 失效的问题，`useMemo` 和 `useCallback` 应运而生。

## useMemo 的核心作用与使用场景 *Content-[02:47]

### 核心作用与工作原理
`useMemo` 的核心作用是**记住（缓存）一个计算结果的值**。

它接收两个参数：
1. **创建函数**：执行实际的计算并返回结果。
2. **依赖数组**：包含该计算所依赖的值。

**工作机制**：只有当依赖数组中至少一个值发生变化时，`useMemo` 才会重新执行创建函数以获取新结果；否则，它会直接返回上一次缓存的结果。

### 典型使用场景
1. **昂贵的计算**：例如对非常大的列表进行排序、过滤或转换。避免每次组件渲染时都重新执行复杂计算，防止不必要的性能浪费。
2. **缓存对象或数组的引用**：当需要传递一个引用稳定的对象或数组给 `React.memo` 包裹的子组件时，使用 `useMemo` 缓存该对象或数组实例，防止子组件因父组件不必要的 `prop` 引用变化而重新渲染。

### 代码示例解析
- **场景 1（昂贵计算）**：根据传入的 `items` 数组和 `filterText` 计算过滤后的列表。只有当 `items` 或 `filterText` 变化时，过滤函数才重新执行。如果组件因其他不相关的 `state` 更新而重新渲染，`visibleItems` 会直接使用上次缓存的结果。
- **场景 2（缓存对象引用）**：父组件 `App` 创建 `dataOptions` 对象传递给 `React.memo` 包裹的 `ChartComponent`。如果不使用 `useMemo`，每次 `App` 渲染都会创建新对象（即使 `trackColor` 和 `trackType` 值相同），导致子组件不必要地重渲染。使用 `useMemo` 后，只有当 `trackColor` 和 `trackType` 真正发生变化时，`dataOptions` 的引用才会改变，子组件才进行重渲染。

### 面试回答话术
> “`useMemo` 是 React 提供的一个性能优化 Hook，主要作用是缓存计算结果。它接收一个回调函数和一个依赖数组，只有当依赖数组中的项发生变化时，它才会重新执行函数并返回新值；否则，它会返回上一次缓存的值。”

## useCallback 的核心作用与使用场景 *Content-[07:40]

### 核心作用与工作原理
`useMemo` 缓存的是计算结果的值，而 `useCallback` 缓存的是**函数本身（即函数的引用）**。

由于 JavaScript 中的函数也是对象，在组件内部定义的函数每次渲染时都会被重新创建，引用地址随之改变。`useCallback` 用于解决由此引发的子组件不必要重渲染问题。

它同样接收两个参数：
1. **想缓存的回调函数**。
2. **依赖项数组**。

**工作机制**：只有当依赖项数组中的某个值发生变化时，`useCallback` 才返回一个新的函数实例；否则返回上一次缓存的实例。

### 典型使用场景
1. **传递给优化的子组件**：将回调函数传递给经过 `React.memo` 优化的子组件，依赖 `props` 的引用相等性来防止不必要的重新渲染。
2. **作为其他 Hook 的依赖项**：当回调函数本身是另一个 Hook（如 `useEffect`、`useMemo`）的依赖项时，使用 `useCallback` 可以确保该函数依赖项的稳定性，避免其他 Hook 因函数引用变化而不必要地重复执行。

### 代码示例解析
- `handleIncrement` 使用了 `useCallback` 并传入空依赖数组 `[]`。这意味着该函数的引用在整个组件生命周期中保持不变。即使父组件因 `userId` 变化而重新渲染，传递给子组件的函数引用依然稳定，子组件不会因此重渲染。
- `handleUserChange` 依赖 `userId`，只有当 `userId` 发生变化时，才会返回新的函数实例。

### 与 useMemo 的关系
`useCallback(fn, deps)` 在功能上等价于 `useMemo(() => fn, deps)`。`useCallback` 本质上是一个语法糖，React 团队提供它主要是为了在语义上更清晰地区分：你是在缓存一个计算结果，还是在缓存一个函数。

### 面试回答话术
> “`useCallback` 也是 React 的一个性能优化 Hook，主要用来缓存函数实例。它接收一个内联回调函数和一个依赖项数组，会返回该回调函数的 memoized 版本。这个回调函数只有在某个依赖项变化时，才会更新它的引用。”

## 滥用 useMemo 与 useCallback 的后果 *Content-[12:18]

“过早优化是万恶之源”，`useMemo` 和 `useCallback` 并非没有成本，滥用它们会带来以下负面后果：

1. **自身的性能开销**：
   - 这两个 Hook 本身也需要执行，包括比较依赖数组中的每一项，以及存储和管理内部缓存的值或函数。
   - 如果被优化的计算或函数本身开销非常小，或者依赖项非常复杂且频繁变化，那么使用它们的成本可能会超过带来的性能收益，甚至可能导致轻微的性能下降。
2. **增加代码复杂度与降低可维护性**：
   - 过度使用会让代码充斥着各种优化逻辑，降低代码的直观性和可读性。
   - 到处使用 `useMemo` 和 `useCallback` 包裹，会使得组件逻辑的维护变得不直观，大幅增加开发者的维护成本和心智负担。

## 谨慎使用的场景与性能判断法则 *Content-[15:47]

### 何时不用或谨慎使用
1. **开销本身很小的函数或值**：例如返回一个常量或一个简单的 JSX 对象，重新计算它们的成本基本可以忽略不计。
2. **仅在组件内部使用**：如果函数或值只在当前组件内部使用，没有作为 `prop` 传递给 `React.memo` 子组件，也没有作为其他 Hook（如 `useEffect`）的依赖项，通常不需要优化其引用性，因为引用变化不会引起连锁的性能问题。
3. **依赖项数组过于复杂或频繁变化**：如果依赖项非常多或频繁变化，每次比较这些依赖项的开销可能抵消了缓存优化带来的好处。

### 如何判断是否使用（性能分析是王道）
在怀疑有性能问题时，应首先使用 **React DevTools** 或 **Profiler** 工具去定位性能瓶颈，找到那些耗时的或频繁不必要重新渲染的组件。

**经验法则**：
- 当你发现一个子组件因为 `props`（特别是对象或函数类型的引用）频繁变化而产生大量不必要的重新渲染时，检查父组件是否可以对这些 `props` 使用 `useMemo` 或 `useCallback`。
- 当你有一个 `useEffect` 因为其依赖项中的函数引用频繁变化而导致不必要的重复执行时，考虑使用 `useCallback`。
- 当你有一个计算逻辑确实非常耗时（例如几十毫秒以上）并且它的输入不常变化时，可以考虑使用 `useMemo`。

**核心原则**：不要为了优化而优化。优化的前提是你已经证实了项目存在性能问题，应优先保证代码的可读性和可维护性。

本视频深入剖析了 React 中 `useMemo` 和 `useCallback` 这两个核心性能优化 Hook。`useMemo` 用于缓存昂贵的计算结果或稳定的对象/数组引用，而 `useCallback` 用于缓存函数实例，两者均通过稳定引用来配合 `React.memo` 避免子组件的不必要重渲染。视频强调，虽然它们是优化利器，但自身存在比较依赖和执行缓存的开销。盲目滥用不仅可能拖慢性能，还会严重降低代码的可读性与可维护性。正确的做法是遵循“不要为了优化而优化”的原则，借助 React DevTools 等工具精准定位性能瓶颈，仅在确实存在引用变化导致连锁重渲染或计算耗时等场景下有针对性地使用。
