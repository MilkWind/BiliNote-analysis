## 2. 基础概念回顾：组合与继承 *Content-[02:20]
- **继承（Inheritance）**：
  - 描述的是 **“is-a”** 关系（例如：拉布拉多 is a dog）。
  - 在面向对象编程中，子类自动获得父类的属性和方法，形成层级结构，实现代码直接复用。
  - **缺点**：类之间耦合紧密，容易导致“脆弱基类”问题（一个小改动可能导致所有子类受影响）。
- **组合（Composition）**：
  - 描述的是 **“has-a”** 关系（例如：汽车 has a 引擎）。
  - 通过将简单或功能单一的对象/组件封装起来，形成更复杂、功能更强大的整体。
  - **优点**：更加灵活，组件之间耦合度更低。在 React 中，组件就非常像这些简单的对象。

## 3. React 推崇组合模式的核心优势 *Content-[04:01]
- **高度的灵活性和可维护性**：
  - 能够轻易替换组件中的某部分功能或修改行为，而不必担心对继承链上的其他部分产生不可预期的影响。
  - 就像“搭积木”，换掉一块积木比修改一个固化成型的玩具简单得多，避免了继承导致的脆弱基类问题。
- **清晰的关注点分离**：
  - 每个 React 组件专注自身核心职责（如按钮只管展示和点击，输入框只管输入）。
  - 将职责单一的组件组合成复杂 UI，代码逻辑更清晰，易于测试。
- **props 的强大驱动**：
  - React 的 `props` 机制（尤其是 `props.children`）简直是为组合量身定做的。
  - 可以方便地通过 `props` 将组件注入到另一个组件中，或传递任意内容给子组件渲染。
- **避免不必要的耦合**：
  - 继承在父子类间建立强联系，子类高度依赖父类实现。
  - 组合允许组件保持相对独立，通过明确接口（`props`）通信，耦合度更低。

## 4. 在 React 中使用继承面临的挑战 *Content-[06:09]
- **层级与数据流模糊**：
  - React 核心思想是构建可复用的 UI 单元（组件）。使用继承可能创建出概念上不直观的组件层级。
  - `props` 和 `state` 在继承链中的传递和来源难以追踪，这与 React 推崇的**单向数据流**和清晰的组件边界相冲突。
- **逻辑复用的困境**：
  - 在 React 组件中复用逻辑行为时，继承往往不如专门设计的模式（如自定义 Hook 或高阶组件 HOC）清晰和灵活。
  - 这些专门模式可以在不改变组件层级的前提下共享和注入逻辑。
- **React 官方明确立场**：
  - 官方文档指出：没有发现在组件间复用代码时，继承能解决而组合解决不了的问题。
  - 组合通常能提供更清晰、更安全的方式，是官方推荐的做法。

## 5. React 中实践组合的具体方式 *Content-[08:11]
- **通过 props 传递特定内容或行为**：
  - 将组件实例作为 `props` 传递给另一个组件（如 `PageLayout` 接收 `sidebar` 和 `mainContent`）。
  - 传递配置对象或更灵活的渲染组件，让父组件决定如何渲染某些部分。
- **万能的 `props.children`**：
  - React 组合模式中的明星，最常见且直观。
  - 在 JSX 中，外层父组件标签内部的所有内容都是它的 `children`。
  - 非常适合创建通用容器组件（如 Card、Dialog、Layout），内部包裹的内容可以是任意形式。
- **高阶组件（HOC）**：
  - 本质是一个函数，接受一个组件作为参数，返回一个功能增强的新组件。
  - 常用于复用**横切关注点**的逻辑（如用户认证、状态检查、数据订阅、日志记录）。
- **自定义 Hook**：
  - 目前 React 中非常流行的方式。
  - 将组件中的状态、逻辑和副作用提取出来。
  - 相比 HOC 更简洁、易理解，且能避免过多的包裹层（嵌套地狱）问题。

## 6. 代码演示：Card 组件的组合应用 *Content-[10:54]
- **场景**：构建一个通用的 Card 组件，包含可选的标题、底部内容和灵活填充的中间主要内容区域。
- **组件定义**：
  - 接收 `props.title`（显示可选标题）。
  - 接收 `props.footer`（显示可选底部内容）。
  - 接收 `props.children`（允许像 HTML 标签一样在组件内部插入任意内容）。
- **使用方式演示**：
  - **场景一**：传入 `title`，内部直接写文本和链接作为 `children`。
  - **场景二**：传入 `title`，并通过 `footer` prop 传递一段 JSX 代码（如自定义的 `UserProfile` 组件）作为底部。
  - **场景三**：不传 `title` 和 `footer`，仅传入图片和文本描述作为 `children`。
- **核心魅力**：Card 组件本身只关注提供通用的卡片容器结构，通过组合方式变得极其灵活，可根据需求自由定制各个区域。

## 7. 面试实战：如何清晰回答该问题 *Content-[14:05]
- **明确核心观点**：组合是实现代码复用和构建灵活组件结构的首选策略，这是由 React 的设计哲学决定的。
- **解释深层原因**：
  - React 函数组件行为接近纯函数，`props` 像函数参数，组合像函数调用和嵌套，完美契合**声明式编程**理念。
- **强调灵活性与可维护性**：组合有效降低组件间耦合，容易替换或修改局部，不用担心破坏复杂的继承体系。
- **对比传统类继承的缺陷**：在 UI 场景下，传统继承会导致层级过深难管理、方法覆盖引入混乱、脆弱基类等问题。
- **结合实际例子说明**：
  - 举例 `props.children` 构建通用容器（如 Modal、Sidebar）。
  - 提及高阶组件或自定义 Hook 复用非 UI 逻辑（如数据获取、权限校验），这也是组合思想的体现。
- **易错点提醒**：强调组合优势时，**不要完全否定继承在 JavaScript 面向对象编程中的价值**。要表达出细微区别：在 React 组件复用这个特定语境下，组合是更优选择。

## 8. 深度探讨：继承在 React 中是否完全无用 *Content-[17:40]
- **官方观点**：React 官方认为在构建 React 组件时，没有必须通过继承类组件才能解决的问题，组合总能提供更好的方案。
- **思维转换**：如果想通过类继承实现 React 组件代码复用，应停下来思考是否有更好的组合方式（如 Hook、HOC、`props.children`）。
- **React 组件模型本质**：强调封装 UI 和行为，通过 `props` 通信。组件间是**包含和使用**关系，而非面向对象中严格的**派生**关系。不要为了继承而继承。
- **继承的合理适用场景**：
  - 如果是非常通用的、**非 UI 相关**的 JavaScript 类。
  - 且它们之间确实存在清晰的继承关系。
  - 此时使用 ES6 的类继承是完全合理的。

## 9. 核心内容总结 *Content-[19:45]
- **核心原则**：“组合优于继承”是 React 核心设计原则，践行它能显著提高代码质量。
- **组合的优势**：带来无与伦比的灵活性、松耦合特性和高可维护性，完美契合 React 声明式编程和组件化思想。
- **主要实践方式**：通过 `props`（尤其是 `props.children`）注入内容和行为；使用高阶组件和自定义 Hook 复用共享逻辑。
- **面试加分项**：能清晰描述组合优于继承的原因，并结合 `Card` 组件、`props.children` 或 Hook 等实际例子说明最佳实践，展现对 React 理解的深度。
