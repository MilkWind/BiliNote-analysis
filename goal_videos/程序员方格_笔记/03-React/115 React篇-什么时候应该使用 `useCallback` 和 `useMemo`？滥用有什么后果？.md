## 1. React 渲染机制与引用类型问题 *Content-[00:58]

- **核心渲染机制**：在 React 中，当父组件重新渲染时，默认情况下其所有子组件也会跟着重新渲染。
- **优化手段 `React.memo`**：为了避免不必要的渲染，React 提供了 `React.memo`。它会对子组件的 `props` 进行浅比较（Shallow Compare），只有当 `props` 发生变化时，子组件才会重新渲染。
- **引用类型的问题**：在 JavaScript 中，函数、对象和数组都是引用类型。这意味着即使它们的内容看起来一模一样，如果在不同的渲染周期中创建，它们的引用地址也是不同的。
- **导致的问题**：如果给 `React.memo` 包裹的子组件传递在父组件中定义的函数或对象作为 `prop`，当父组件因任何原因重新渲染时，这些函数或对象会被重新创建。即使逻辑或内容没有丝毫改变，它们的引用也改变了。`React.memo` 在进行浅比较时会认为 `prop` 改变，从而导致子组件依然重新渲染。
- **解决方案**：为了解决引用地址改变导致 `React.memo` 失效的问题，就需要使用 `useMemo` 和 `useCallback`。

## 2. useMemo 的核心作用与使用场景 *Content-[02:40]

- **核心作用**：`useMemo` 的主要作用是“记住”一个计算结果的值，相当于给计算结果加了一个缓存。
- **工作原理**：
  - 接收两个参数：一个创建函数（执行实际计算并返回结果）和一个依赖数组。
  - 只有当依赖数组中至少一个值发生变化时，才会重新执行创建函数得到新结果。
  - 否则，直接返回上一次缓存的结果。
- **代码示例（过滤列表）**：
  - 根据传入的 `items` 数组和 `filterTerm` 计算过滤后的列表。
  - 只有 `items` 或 `filterTerm` 变化时，`filter` 函数才会通过 `useMemo` 重新执行。
  - 如果组件因其他不相关的 `state` 更新而重新渲染，`visibleItems` 会直接使用上次缓存的结果，避免不必要的计算。
- **典型使用场景**：
  1. **昂贵的计算**：如大数据的复杂处理（排序、过滤、转换），避免每次渲染时都重新计算。
  2. **缓存对象或数组的引用**：传递引用稳定的对象或数组给 `React.memo` 组件，防止子组件因父组件不必要的 `prop` 引用变化而重新渲染。
- **代码示例（缓存对象引用）**：
  - 假设 `ChartComponent` 是用 `React.memo` 包裹的子组件。父组件 `App` 中创建 `dataOptions` 对象。
  - 如果不使用 `useMemo`，每次 `App` 渲染都会生成新的 `dataOptions` 对象，即使 `trackColor` 和 `trackType` 的值没变，也会导致 `ChartComponent` 不必要地重新渲染。
  - 使用 `useMemo` 后，只有 `trackColor` 和 `trackType` 真正发生变化时，`dataOptions` 的引用才会改变，从而确保子组件只在真正关心内容变化时才重新渲染。
- **面试回答话术**：
  - `useMemo` 是 React 提供的性能优化 Hook，主要作用是缓存计算结果。它接收回调函数和依赖数组，只有依赖变化时才重新执行并返回新值，否则返回缓存值。

## 3. useCallback 的核心作用与使用场景 *Content-[06:24]

- **核心作用**：`useCallback` 用于缓存函数本身（即函数的引用）。
- **工作原理**：
  - 组件内部定义的函数在每次渲染时都会被重新创建，引用地址改变。
  - `useCallback` 接收想缓存的回调函数和依赖项数组。
  - 只有依赖项变化时，才返回新的函数实例，否则返回缓存的实例。
- **代码示例**：
  - `handleIncrement` 使用空依赖数组，函数引用在整个组件生命周期中保持不变。即使 `userId` 变化导致 `App` 重新渲染，传递给 `MemoButton` 的函数引用依然稳定，不会导致按钮重新渲染。
  - `handleUserChange` 依赖 `userId`，只有 `userId` 变化时才返回新实例。
- **典型使用场景**：
  1. **传递给优化的子组件**：特别是通过 `React.memo` 包裹的子组件，依赖 `props` 的引用相等性防止不必要渲染。
  2. **作为其他 Hook 的依赖项**：如 `useEffect`、`useMemo`。使用 `useCallback` 确保函数依赖项的稳定性，避免其他 Hook 不必要的重复执行。
- **面试回答话术**：
  - `useCallback` 是 React 的性能优化 Hook，用来缓存函数实例。它接收内联回调函数和依赖数组，返回 memoized 版本，只有依赖变化时才会更新引用。
- **与 useMemo 的关系**：
  - `useCallback(fn, deps)` 在功能上等价于 `useMemo(() => fn, deps)`。
  - `useCallback` 本质上是一个语法糖，专门用于更清晰地表达“正在记忆一个函数”，在语义上区分缓存计算结果和缓存函数。

## 4. 滥用 useMemo 与 useCallback 的后果 *Content-[12:18]

- **核心观点**：“过早优化是万恶之源”，这两个 Hook 并非没有成本。
- **后果 1：自身的性能开销**
  - `useMemo` 和 `useCallback` 自身需要执行，包括比较依赖数组中的每一项，以及存储缓存的值或函数。
  - 如果被优化的计算或函数本身开销很小，或者依赖项复杂且频繁变化，使用 Hook 的成本可能大于收益，甚至导致轻微的性能下降。
- **后果 2：增加代码复杂度**
  - 过度使用会让代码变得复杂，可读性变差。
  - 到处使用这两个 Hook 包裹，使得组件逻辑维护不直观，增加了很多维护成本和心智负担。
- **面试回答话术**：
  - 滥用后果主要有两点：一是性能开销，依赖比较和缓存管理的成本可能超过收益，拖慢性能；二是降低代码可读性和可维护性，增加后续维护难度。

## 5. 谨慎使用与性能优化原则 *Content-[14:39]

- **何时谨慎使用或不用**：
  1. **开销本身很小的函数/值**：如返回常量或简单的 JSX 对象，重新计算的成本基本可以忽略不计。
  2. **仅在组件内部使用**：未作为 `prop` 传递给 `React.memo` 子组件，也未作为其他 Hook（如 `useEffect`）的依赖项。引用变化不会引起连锁的性能问题。
  3. **依赖项数组过于复杂或频繁变化**：比较依赖项的开销可能抵消优化带来的好处。
- **如何判断是否使用**：
  - **性能分析是王道**：在怀疑有性能问题时，首先使用 React DevTools 或 Profiler 定位性能瓶颈，找到耗时或频繁不必要重新渲染的组件。
  - **经验法则**：
    - 当子组件因 `props`（特别是对象或函数引用）频繁变化而不必要重新渲染时，考虑在父组件使用 `useMemo` 或 `useCallback`。
    - 当 `useEffect` 因依赖项中的函数引用频繁变化而重复执行时，考虑使用 `useCallback`。
    - 当计算逻辑非常耗时（如几十毫秒以上）且输入不频繁变化时，考虑使用 `useMemo`。
- **核心原则**：
  - 不要为了优化而优化。优化的前提是证实项目确实存在性能问题。
  - 优先保证代码的可读性和可维护性。
