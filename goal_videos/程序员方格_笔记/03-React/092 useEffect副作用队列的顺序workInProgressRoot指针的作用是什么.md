## useEffect 副作用队列的执行顺序 *Content-[00:00]
在 React 中，当多个组件都包含 `useEffect` 回调时，其副作用队列的执行顺序具有特定的规则：
- **执行顺序规则**：节点层级越深，`useEffect` 的执行顺序越靠前。
- **底层原因**：这与 React 源码的实现机制有关。`useEffect` 回调的收集过程是**倒序**进行的，即从最底层的节点开始，逐层向上进行收集。因此，底层节点的副作用会优先被收集并执行。

## workInProgressRoot 指针的作用 *Content-[00:24]
`workInProgressRoot` 是 React 源码中的一个核心指针，其主要作用如下：
- **本质定义**：它实际上就是 Fiber 节点，代表了 Fiber 树在 `render` 阶段遍历的进度。
- **进度标识**：它代表了处理 Fiber 节点的当前进度。
- **并发控制**：React 中并发任务的暂停和继续，正是基于这个指针来实现的。通过记录遍历进度，React 能够在中断后准确恢复执行。

## Hooks 解决了什么问题 *Content-[00:49]
Hooks 的核心价值可以精简为两点：**状态复用**与**逻辑复用**。
- **对比 Class 组件**：Class 组件本质上是 UI 复用，相对臃肿。如果要复用一段逻辑，必须将其封装并 return 一个 UI 出来。而 Hooks 不需要 return UI，使得代码结构的梳理更加友好和清晰。
- **生命周期误区**：在 React 官方理念中，Hooks（如 `useEffect`）**并不是**为了模拟 Class 组件的生命周期，不能完全对号入座。
  - 不能简单地将 `useEffect` 等同于 `componentDidMount`、`componentDidUpdate` 或 `componentWillUnmount`。
  - **执行时机差异**：`useEffect` 的调用是在渲染前（内部通过宏任务异步处理），但它的实际执行是在渲染后。因此，它并不完全等同于 `componentDidMount`。
- **核心总结**：Hooks 的核心在于逻辑复用，不应将其与 Class 组件的生命周期混为一谈。

## Redux 解决的核心问题 *Content-[02:39]
Redux 的核心定位是**数据状态管理**，它开启了“上帝视角”，实现数据到视图的一一对应。
- **三大核心优势**：
  1. **状态机管理**：将数据集中存放在 Store 仓库中，实现数据与视图的一一对应（注意：这并非单纯的组件通信）。
  2. **时间旅行**：支持数据回退功能，可以追踪和恢复历史状态。
  3. **方便调试**：利用 Action 和 Redux DevTools，可以极大地方便状态变化的调试。
- **核心思想**：Redux 的数据流思想是**自顶向下**的。在面试回答时，务必强调其“上帝视角”和“自顶向下”的特性，避免过度发散。

## Redux 与组件通信的深度辨析 *Content-[04:10]
面试中常被问及“Redux 是否解决了组件通信”，这需要深入剖析两者的本质区别：
- **Redux 的本质**：核心原理是通过 Action 修改 Store，使数据变化引起组件重新渲染。它是上帝视角，自顶向下分配数据（例如 Store 中的 A 属性对应组件 A，B 属性对应组件 B）。
- **组件通信的定义**：指组件 B 和组件 C 直接相互联系、相互通信。
- **破除“通信”错觉**：当组件 D 修改 Store 中 A 的数据，导致组件 A 状态更新时，表面上看像是组件间进行了通信，但这只是一种**错觉**。实际上，组件之间并没有直接通信，它们都是独立地与 Store 数据仓库进行交互。
- **真正的组件通信示例**：例如 Vue 中的 `mitt`（事件总线），一个组件发起事件，另一个组件监听事件，这才是真正的组件间通信。
- **面试答题策略**：
  - 当被问及此问题时，回答“是”或“否”都可以，**重点不在于得出绝对结论**。
  - 面试官看重的是你**分析问题的思路和辩证思维**。
  - 面试时切忌夸夸其谈、“说的越多错的越多”。理解透彻核心概念后，精简、准确地表达即可。
