## IndexedDB 简介与应用场景 *Content-[00:00]
- **IndexedDB** 是浏览器提供的本地存储方案之一，适用于前端层面上的大规模数据存储。
- 许多大型平台（如飞书等）都会利用 IndexedDB 进行前端数据的持久化存储。
- 在前端面试的场景题中，IndexedDB 存储空间大小的约束机制是一个高频考点。

## 浏览器层面的存储限制 *Content-[00:28]
IndexedDB 的存储空间约束首先受不同浏览器限制策略的影响：
- **Chrome**：可用空间通常为设备可用空间的 **60%**，整体来讲可用空间比较大。
- **Firefox**：没有硬性的空间限制要求，但当空间不足时会提示用户。
- **Safari**：默认限制在 **1GB** 以内。

## 设备层面的存储限制 *Content-[01:35]
除了浏览器策略，IndexedDB 的存储空间还受限于设备的物理磁盘空间：
- **桌面端/中端设备**：存储限制通常比较大，主要取决于硬盘的可用物理空间。
- **移动端设备**：存储空间相对较小，严格受限于设备本身的物理存储容量。

## 域名与同源策略限制 *Content-[02:20]
- **Origin（源）隔离**：每个 Origin（由协议、端口、域名组成）都拥有独立的存储配额。
- **同源策略**：受同源策略限制，不同 Origin 之间的存储空间是相对独立的，互不干扰。
- **隐私/无痕模式**：在浏览器的私有模式（无痕模式）下，存储空间的限制会更为严格。

## 查询可用空间的方法 *Content-[03:19]
可以通过 `StorageManager` 相关的 API 来查询当前可用的存储空间。
- 调用 `navigator.storage.estimate()` API 获取存储信息。
- 返回结果包含以下关键内容：
  - **总配额 (quota)**：当前可用的总存储空间。
  - **已使用空间 (usage)**：当前已经使用的存储空间。
  - **剩余空间**：通过 `总配额 - 已使用空间` 计算得出。

## 最佳实践：数据压缩存储 *Content-[05:16]
为了在有限的存储空间内存储更多数据，可以采用数据压缩的最佳实践：
1. **数据序列化**：首先使用 `JSON.stringify()` 将数据对象转换为字符串。
2. **流式压缩**：利用 `CompressionStream` API，在流管道中对序列化后的数据进行 **gzip** 压缩。
3. **存储压缩数据**：最终将压缩后的数据流存储到 IndexedDB 中，从而有效节省存储空间。

## AI 总结
IndexedDB 作为前端重要的大容量本地存储方案，其存储空间受浏览器策略（如 Chrome 60%、Safari 1GB）、设备物理磁盘以及同源策略（Origin）的共同限制。在实际开发中，开发者可以通过 `navigator.storage.estimate()` 实时监控空间使用情况，并结合 `CompressionStream` 对数据进行 gzip 流式压缩，以实现存储空间的最大化利用与优化。
