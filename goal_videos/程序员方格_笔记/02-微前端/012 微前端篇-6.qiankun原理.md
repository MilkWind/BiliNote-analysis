## 环境隔离体系：JS 沙箱与 CSS 沙箱 *Content-[00:02]

qiankun 微前端框架的稳定运行依赖于完善的环境隔离体系，主要包括 JS 沙箱和 CSS 沙箱。

### JS 隔离原理
- **核心思路**：基于 ES6 的 `Proxy` 特性，为每个子应用创建一个独立的沙箱运行时环境。
- **运行机制**：子应用运行时，访问和修改的并不是真实的 `window` 对象，而是一个被 qiankun 代理过的假 `window`（`fakeWindow`）。
- **变量挂载**：当子应用往 `fakeWindow` 上挂载变量时，实际上存储在隔离的 JS 对象中。
- **环境清理**：子应用卸载时，qiankun 只需将隔离环境整体清除，不会对主应用或其他子应用造成任何影响。

### CSS 隔离策略
qiankun 提供了两种 CSS 隔离策略：
1. **默认策略（样式前缀）**：基于容器作用域和前缀实现。加载子应用时，动态给所有样式添加特定前缀（如 `div[data-qiankun="subApp"]`），确保样式仅在子应用容器内生效。
2. **严格策略（Shadow DOM）**：开启 `strictStyleIsolation` 开关后，qiankun 会为子应用创建原生的 Shadow Root。Shadow DOM 是浏览器提供的原生能力，能将部分 DOM 结构和样式完全封装并与主文档隔离。隔离性最强，但存在副作用，如可能影响需要全局挂载的弹窗组件样式。

## CSS 隔离策略与代码演示 *Content-[02:43]

通过实际代码演示，可以直观理解 CSS 隔离的作用及样式污染问题。

### 无隔离时的样式污染
- 在主应用和子应用（React App）同时运行时，若子应用中定义了 `.logo { color: red; }` 样式。
- 由于未开启隔离，该样式会挂载到全局，导致主应用中同名的 `.logo` 元素（如右上角标题）字体变为红色，产生样式污染。

### 开启样式前缀隔离
- 配置 `experimentalStyleIsolation: true`。
- **效果**：子应用的样式不再影响全局，主应用标题样式恢复正常。
- **原理**：qiankun 自动为子应用的样式表增加作用域前缀（如 `div[data-qiankun="react-app"] .app`），通过 CSS 选择器限定样式只能在对应的子应用容器内生效。

### 开启 Shadow DOM 隔离
- 配置 `strictStyleIsolation: true`。
- **效果**：全局样式同样不受影响。
- **原理**：子应用的 DOM 结构被渲染在 Shadow Root 内部，样式也写在 Shadow Root 内部的 `<style>` 标签中。实现了物理级别的隔离，样式绝对不会逃逸到全局。

## JS 沙箱的两种实现方案 *Content-[12:30]

qiankun 的 JS 沙箱主要有两种实现方案，分别针对不同的浏览器环境。

### 快照沙箱 (SnapshotSandbox)
- **适用场景**：兼容不支持 ES6 `Proxy` 的低版本浏览器（如 IE11）。
- **核心流程**：
  1. **挂载前**：遍历当前 `window` 对象，记录所有属性及值，形成快照。
  2. **运行中**：子应用直接修改真实的 `window` 对象，沙箱同步记录这些变更。
  3. **卸载时**：对比当前 `window` 与快照的差异，将子应用修改过的属性全部还原。
- **优点**：不依赖现代浏览器特性，实现简单，兼容性极好。
- **缺点**：
  - **性能差**：每次激活和卸载都需要遍历整个 `window` 对象，耗时较长。
  - **隔离性差**：多个子应用同时运行时，修改的是同一个真实的 `window`，会互相影响。仅适用于同一时间只显示一个子应用的场景。
- **定位**：为了兼容性而保留的降级方案。

### Proxy 沙箱 (ProxySandbox)
- **适用场景**：现代浏览器（默认启用且首选的方案）。
- **核心机制**：利用 ES6 `Proxy` 对 `window` 对象进行包装。
  - 子应用代码中对 `window` 的操作实际上都是针对 `Proxy` 对象。
  - **写入拦截**：`Proxy` 的 `set` 操作不会写入真实的 `window`，而是写入 qiankun 内部维护的 `fakeWindow` 对象。
  - **清理机制**：卸载时，直接丢弃或清空 `fakeWindow`，无需比对和还原真实 `window`。
  - **多应用并行**：为每个子应用创建独立的 `fakeWindow` 和 `Proxy` 对象，实现完全隔离。
- **优点**：在隔离性、性能和可靠性上远优于快照沙箱。

### 两种沙箱方案对比总结
1. **修改目标**：快照沙箱修改真实 `window`；Proxy 沙箱修改内部 `fakeWindow`。
2. **还原方式**：快照沙箱需从快照还原；Proxy 沙箱直接清空 `fakeWindow`。
3. **多应用并行**：快照沙箱隔离性差，互相影响；Proxy 沙箱完全隔离。
4. **性能**：快照沙箱遍历和还原导致性能差；Proxy 沙箱利用原生代理拦截，性能好。
5. **浏览器要求**：快照沙箱兼容旧版浏览器；Proxy 沙箱需支持 ES6 `Proxy`。

## Proxy 沙箱的极简代码实现 *Content-[21:15]

通过极简代码实现，深入理解 Proxy 沙箱的工作原理。

### 核心属性初始化
- `proxyWindow`：空对象，即 `fakeWindow`，用于存储在沙箱内被修改的全局变量。
- `modifiedProps`：Set 集合，记录被修改过的属性名，方便调试和追踪。
- `active`：布尔值，控制沙箱的激活状态。
- `proxy`：核心的 `Proxy` 实例，代理 `proxyWindow` 对象，配置 `set`、`get`、`has` 等拦截器。

### 拦截器逻辑
- **`set` 拦截器**：
  - 检查沙箱是否处于 `active` 状态，防止卸载后仍被修改。
  - 将值赋给 `proxyWindow`（`fakeWindow`），并将属性名记录到 `modifiedProps` 中。全程不触碰真实的 `window`。
- **`get` 拦截器**：
  - 优先从 `proxyWindow` 中读取属性。
  - 若不存在，则从真实的 `window` 中读取（保证子应用能正常访问 `document`、`location` 等浏览器内置对象）。
  - **细节处理**：若读取到的是函数，需使用 `bind` 绑定上下文（`this` 指向真实 `window`），确保函数调用时上下文一致。
- **`has` 拦截器**：
  - 对应 `in` 操作符（如 `prop in window`）。
  - 只要 `proxyWindow` 或真实的 `window` 上存在该属性，即返回 `true`。

### 生命周期控制与使用
- 提供 `activate()` 和 `deactivate()` 方法控制沙箱状态。
- 使用时，通过 `proxy` 实例设置和读取变量，可验证写操作被隔离在沙箱内部，而读操作能正确代理到真实 `window` 的内置对象。

## 生命周期管理与扩展 *Content-[27:49]

qiankun 基于 single-spa 构建，在生命周期管理上既遵循规范又进行了扩展。

### single-spa 标准生命周期
一个符合规范的微应用需导出以下生命周期函数：
- `load`：加载阶段，获取应用代码（qiankun 中由 HTML Entry Loader 接管）。
- `bootstrap`：引导阶段，应用首次挂载前执行且仅执行一次，用于全局一次性初始化。
- `mount`：挂载阶段，每次激活时执行，负责将内容渲染到 DOM。
- `unmount`：卸载阶段，每次切换走时执行，负责清理 DOM、事件监听器等资源。
- `unload`：可选的彻底卸载阶段，清理所有资源，下次激活需重新 load。

### qiankun 的扩展机制
- **子应用层面**：约定不变，子应用（Vue/React）仍需导出 `bootstrap`、`mount`、`unmount` 三个生命周期，保证无缝接入 single-spa 生态。
- **主应用层面**：新增了一套全局生命周期钩子（如 `beforeLoad`、`beforeMount`、`afterMount` 等）。
- **扩展作用**：允许主应用在任意子应用发生生命周期变化时，执行通用逻辑（如展示全局 loading 动画、进行应用级别的数据埋点）。qiankun 并未改变子应用本身的生命周期，而是包了一层，为主应用提供了更多观察和干预的时机。

## 微应用的注册与运行流程 *Content-[31:17]

微应用的集成主要分为页面级（基于路由）和组件级（按需加载）两种模式。

### 页面级微应用（基于路由切换）
1. **主应用启动**：在页面布局中预留渲染子应用的容器，规划路由系统（Hash 或 History）及子应用访问路径。
2. **注册微应用**：调用 `registerMicroApps` API。配置项包括唯一的 `name`、`entry`（HTML 入口，区别于 single-spa 的 JS 入口）、`container`（容器）和 `activeRule`（激活规则）。
3. **启动 qiankun**：调用 `start` 函数启动服务，可传入全局配置（如沙箱隔离、资源预加载）。启动后会检查当前 URL，命中规则即开始加载。
4. **监听路由变化**：URL 改变时，通过 HTML Entry Loader 加载资源，创建并激活沙箱，依次调用子应用的 `bootstrap` 和 `mount` 渲染内容。离开时自动调用 `unmount` 卸载并释放资源。

### 组件级微应用（按需动态加载）
- **API 支持**：使用 `loadMicroApp` 函数，这是一个命令式的手动加载函数。
- **使用场景**：无需基于路由切换整个页面，仅在当前页面的某个位置嵌入其他应用的独立功能模块。
- **实现方式**：通常封装在 React/Vue 组件中。在组件挂载生命周期（如 `useEffect` 或 `mounted`）中调用 `loadMicroApp`，返回应用实例。
- **资源释放**：组件销毁时，必须手动调用实例的 `unmount` 方法，确保正常卸载并防止内存泄漏。
- **数据通信**：支持 `props` 传参，主应用可像给普通组件传参一样，将数据传递给微应用，实现组件级别的灵活集成。

## 经典边界问题：弹窗越界 *Content-[38:03]

在实际项目落地中，弹窗越界是几乎每个使用 qiankun 的团队都会遇到的棘手问题。

### 问题现象与原因分析
- **现象**：子应用中使用弹窗组件（如通过 `ReactDOM.createPortal` 挂载到 `document.body`），导致弹窗样式失效、错乱或变成无样式的原始 DOM。
- **根本原因**：
  - qiankun 的 CSS 沙箱（无论是前缀还是 Shadow DOM）都是以**子应用容器为边界**的。
  - 主流 UI 组件库为解决 `z-index` 层级和 `overflow: hidden` 遮挡问题，普遍将弹窗直接挂载到 `document.body` 末端。
  - 这导致弹窗在 DOM 结构上“逃逸”了子应用容器，脱离了 CSS 沙箱的保护。样式无法生效，且极易受到主应用或其他子应用的全局样式污染。

### 常见解决方案及局限性
1. **修改挂载节点**：
   - 利用 UI 库提供的 API，强制将弹窗挂载到子应用自身的容器内部，使其回到 CSS 沙箱内。
   - **局限性**：需要开发人员具备极强的规范意识；不同 UI 库 API 不统一，难以跨框架；无法控制第三方脚本强行插入 `body` 的弹窗。
2. **修改挂载类名结合构建工具**：
   - 给弹窗根节点添加特殊的全局唯一 class，通过 PostCSS 等工具在构建时配置不对该 class 进行作用域隔离。
   - **局限性**：属于 Hack 手段，对构建配置侵入性强，维护成本高。
- **结论**：弹窗越界是微前端的经典挑战，目前多通过团队约定和规范来解决，技术上尚无完美通用的底层解决方案。

## 模块共享方案 *Content-[51:05]

为了避免多个子应用重复打包公共依赖（如 Vue、React）导致带宽浪费和版本不一致，需要建立合理的模块共享策略。qiankun 本身不强制具体方案，但能与主流方案良好结合。

### 方案一：Import Map
- **原理**：浏览器新兴标准，允许在 HTML 中定义映射表，指定 `import` 语句应从哪个 URL 加载模块。
- **实践**：主应用在 `index.html` 维护统一的 `import map`，将公共依赖指向同一 CDN。子应用构建时配置不打包这些依赖，运行时共享同一份依赖。

### 方案二：Externals (传统方案)
- **原理**：在子应用的 Webpack 配置中将公共库声明为 `external`，假定运行时存在全局变量。
- **实践**：主应用通过 `<script>` 标签从 CDN 引入公共库并挂载到 `window` 全局。所有子应用直接访问全局变量，减少打包体积。

### 方案三：Module Federation (模块联邦)
- **原理**：目前最主流、最推崇的方案，专为跨应用模块共享设计，允许运行时动态从独立部署的应用中加载代码。
- **实践**：通常 qiankun 负责宏观的应用编排、路由和沙箱隔离；Module Federation 处理底层的应用间模块和组件的细粒度共享。

### 核心思想
无论选择哪种方案，核心都是识别并抽离项目群中的公共依赖，由主应用提供一份单例，供所有子应用在运行时共享，这是构建高性能、可维护微前端体系的必经之路。
