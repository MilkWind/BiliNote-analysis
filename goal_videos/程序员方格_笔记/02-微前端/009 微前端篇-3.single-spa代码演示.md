## 1. single-spa 项目结构与核心配置 *Content-[00:00]

本部分主要介绍 single-spa 真实示例代码的项目结构以及主应用的注册配置机制。

- **项目目录结构**
  - **root (主应用)**：包含一个基础的 `index.html` 文件，内部提供了 `app1` 和 `app2` 两个 `div` 容器，专门用于挂载对应的子应用。
  - **app1 / app2 (子应用)**：具体的微前端子应用目录。

- **主应用 (root-config) 配置**
  - 使用 `registerApplication` 方法将子应用注册到 single-spa 主应用中。
  - 核心配置参数包括：
    - `name`：代表该子应用的名称。
    - `app`：需要加载的应用资源，通常通过动态 `import()` 方法异步加载。
    - `activeWhen`：应用的激活规则。示例中使用了路由匹配方法，当路由匹配到哈希值 `#/app1` 时加载 app1，匹配到 `#/app2` 时加载 app2。
  - 配置完成后，通过调用 `start()` 方法正式启动主应用。

- **子应用配置**
  - 每个子应用都需要导入并导出其最核心的生命周期钩子方法：`bootstrap`、`mount` 和 `unmount`。
  - 导出后，可在子应用的 HTML 文件中引入对应的 JS 文件，以完成应用的加载准备。

## 2. single-spa 运行机制与生命周期演示 *Content-[02:01]

通过实际运行代码，展示 single-spa 在路由切换时的应用加载、卸载机制以及生命周期的执行顺序。

- **运行效果**
  - 访问 `#/app1` 路由时，app1 的内容被加载并渲染。
  - 切换路由至 `#/app2` 时，app1 被卸载，同时 app2 被加载并渲染。

- **生命周期执行顺序**
  - **首次加载 app1**：执行 `bootstrap`（初始化动作） -> 执行 `mount`（渲染 app1）。
  - **切换至 app2**：执行 app1 的 `unmount`（卸载 app1） -> 执行 app2 的 `bootstrap`（首次加载必须经历初始化） -> 执行 app2 的 `mount`（渲染 app2）。
  - **切换回 app1**：执行 app2 的 `unmount` -> 执行 app1 的 `mount`。

- **核心特性**
  - `bootstrap` 生命周期在整个页面的生命周期中**只会执行一次**，仅代表初始化过程。
  - 初始化完成后，后续的路由切换只会不断地循环执行 `mount` 和 `unmount`，不会再次触发 `bootstrap`。

## 3. 多应用同时激活特性演示 *Content-[04:14]

演示 single-spa 的 `activeWhen` 配置特性，验证其同时加载和激活多个应用的能力。

- **配置修改**
  - 将 `activeWhen` 的路由匹配规则修改为一个函数，并使其始终返回 `true`。
  - 注意：`activeWhen` 必须是一个字符串、正则或函数，直接赋值为布尔值 `true` 会报错。

- **运行效果**
  - 刷新页面后，app1 和 app2 两个子应用被同时挂载到各自的容器中。
  - 控制台无报错，页面正常显示两个应用的内容。

- **特性总结**
  - single-spa 支持同时加载和激活多个应用。
  - 即使有多个应用同时处于激活状态，它们也是互相独立、互不冲突的。

## 4. 主子应用数据传递 (customProps) *Content-[06:23]

讲解如何在 single-spa 架构中实现主应用向子应用传递数据。

- **主应用传递数据**
  - 在 `root-config` 的 `registerApplication` 配置中，添加 `customProps` 属性。
  - 在 `customProps` 中定义需要传递给子应用的具体状态或变量（例如传递变量 `global-app1`）。

- **子应用接收数据**
  - 在子应用的每一个生命周期方法（`bootstrap`、`mount`、`unmount`）中，都可以接收一个 `props` 参数。
  - 通过在生命周期钩子中打印 `props` 对象，即可获取到主应用传递过来的 `customProps` 数据（如成功读取到 `global-app1`）。

## 5. single-spa 的缺陷与隔离问题 *Content-[08:33]

深入剖析 single-spa 作为基础加载框架所存在的严重缺陷，特别是 JS 和 CSS 隔离缺失带来的问题。

- **整体缺陷概述**
  - single-spa 本质上只是一个应用加载框架，并未实现严格的 JS 隔离和 CSS 隔离策略，这也是早期微前端未能大规模推广的原因之一。

- **JS 隔离缺失演示**
  - **操作**：在 app1 中设置一个全局变量 `window.global-var`。
  - **结果**：在 app2 中可以直接打印并读取到该全局变量。
  - **风险**：如果多个子应用使用了同名的全局变量，会导致逻辑冲突，极易引发难以排查的 Bug。

- **CSS 隔离缺失演示**
  - **操作**：在 app1 的样式文件中为 `h2` 标签设置红色字体。
  - **结果**：不仅 app1 中的 `h2` 标签变红，app2 中的 `h2` 标签也受到了影响变成了红色。
  - **风险**：全局样式污染，子应用之间的样式互相干扰。

- **结论**
  - JS 和 CSS 隔离问题是 single-spa 的致命缺陷。
  - 为了解决这些隔离问题，后续的微前端框架（如 qiankun 乾坤）应运而生，并提供了完善的沙箱和样式隔离机制。
