## 微前端架构下的依赖困境 *Content-[00:00]

在微前端架构下，每个子应用都是独立开发和部署的。如果不加任何处理，每个应用都会将 React、Vue 等框架完整打包到自己的产物中，这会带来一系列严重问题：

1\. **资源浪费**：如果一个子页面加载了五个子应用，用户就可能下载五份功能几乎完全相同的 React 库，对网络性能造成极大损耗。
2\. **多实例冲突**：这是最棘手的问题之一。多个不同版本的 React 实例在同一页面运行时，极易触发 `Invalid hook call` 等运行时错误，导致应用崩溃。
3\. **版本混乱**：不同子应用依赖不同版本的库，会让整个系统的维护和问题排查变得非常困难。

**解决方案**：Module Federation 提出了 `shared` 配置。它本质上是一套在运行时进行依赖协商和共享的精巧机制，不仅解决打包优化问题，更关系到微前端应用的稳定性和性能。其核心理念是在保证各个应用独立开发的前提下，实现依赖的智能共享。

## shared 配置的声明方式 *Content-[02:05]

`shared` 的配置方式非常灵活，可以从简单到精细，适应不同的开发阶段和需求：

- **数组形式（基础配置）**：
  - 在 `shared` 属性中提供一个包含依赖名称的数组，例如 `['react', 'react-dom']`。
  - Webpack 会自动从 `package.json` 文件中读取依赖的版本号，并采用默认的共享策略。
  - 这种方式非常便捷，适合在项目初期或快速原型开发时使用。

- **对象形式（精细化配置）**：
  - 为每一个共享的依赖配置一个详细的对象，内部可以指定多个参数。
  - **优势**：可以精细控制每个依赖的共享行为，进行更灵活的版本管理，并提供更好的错误处理机制。
  - 对于构建稳定、可维护的大型微前端项目至关重要。

## shared 核心参数拆解 *Content-[03:28]

在对象形式的精细化配置中，有四个核心参数需要重点掌握：

1\. **`singleton`（单例模式）**
  - 设置为 `true` 时，告诉 Module Federation 该依赖在整个应用生态中必须且只能有一个实例。
  - **核心作用**：确保全局唯一性。对于 React、Vue 等自身包含内部状态、上下文和调度器的框架来说，这是防止多实例冲突、保证应用稳定运行的核心配置。

2\. **`requiredVersion`（版本范围）**
  - 用来指定当前应用可以接受的共享依赖的版本范围。
  - 遵循 **SemVer**（语义化版本）规范，支持 `^`、`~`、`>=` 等操作符（例如 `^18.2.0` 表示兼容所有 18.x.x 版本）。
  - 若不手动指定，Webpack 会默认从项目的 `package.json` 中读取版本号。

3\. **`strictVersion`（严格版本匹配）**
  - 默认值为 `false`，用于决定版本匹配的严格程度。
  - **`false`（默认）**：遵循 SemVer 兼容规则进行匹配（例如 18.3.0 可以满足 `^18.2.0` 的要求）。
  - **`true`（严格模式）**：要求版本必须完全一致。牺牲了一定的灵活性，但带来了更高的确定性，适用于对依赖版本有严格要求的场景。

4\. **`eager`（加载策略）**
  - 默认值为 `false`，控制共享依赖的加载策略。
  - **`false`（默认）**：依赖会被打包成一个独立的 chunk，在需要时才会被异步加载。初始包体积小，加载速度快，适合绝大多数依赖。
  - **`true`**：共享依赖直接打包进应用的入口文件，实现同步加载。避免了额外的网络请求，适合需要优先加载的核心库（如 polyfill 或基础工具库）。

## 运行时的版本协商机制 *Content-[06:45]

Module Federation 真正的魅力在于其全自动的运行时版本协商机制，这也是其相比传统方案最大的创新点。

**智能决策流程**：
1. Host（主应用）启动时，将 React 连同版本信息注册到全局的共享作用域中。
2. 当 Host 需要加载远程模块（如执行动态 `import`）时，Module Federation 运行时介入。
3. 运行时加载远程模块入口文件前，分析出该远程应用需要哪些共享依赖及其版本要求。
4. 将这些要求与全局共享作用域中已有的依赖版本进行比较，进入智能决策环节。

**三种典型场景分析**：

- **场景一：未配置 shared**
  - Host 和 Remote 都没有配置，各自为政。
  - 结果：每个应用打包一份完整的 React，浏览器存在多个 React 实例。造成严重资源浪费，且极大概率引发多实例冲突和严重错误。

- **场景二：正确配置 shared**
  - Remote 和 Host 都正确配置了 `shared`，声明 React 为单例并指定兼容版本范围。
  - 结果：Remote 加载时版本协商成功，直接复用 Host 提供的 React 实例。整个生态只有一个 React，实现资源高效利用和稳定运行。

- **场景三：版本冲突（不兼容）**
  - 假设 Host 共享 React 18.2.0，Remote 明确要求 React 17.0.2，且双方均设置 `singleton: true`。
  - **协商失败**：18.2.0 不满足 17.0.2 的要求。
  - **强制降级**：由于单例模式的强约束，运行时为了保证全局唯一，不会加载 Remote 的 17.0.2，而是强制 Remote 使用 Host 已加载的 18.2.0 版本。
  - **警告提示**：运行时会在浏览器控制台输出一条明确的警告信息。
  - **潜在风险**：Remote 被迫在不兼容的版本下运行，可能导致未知的兼容性错误。

## 与传统 external 方案的对比 *Content-[11:35]

很多开发者会联想到传统的 `externals` 配合 UMD 模块的方案。`shared` 机制相比传统方案具有显著优势：

**传统 external 方案的局限性**：
- 典型做法是在 HTML 中通过 `<script>` 从 CDN 引入库，在 Webpack 中声明为外部依赖。
- **版本硬编码**：版本写死在 HTML 中，非常僵化。
- **协调成本高**：升级库时，所有业务团队都需要同步修改和发布，牵一发而动全身。
- **中心化且无协商**：完全缺乏灵活的版本协商能力，是一种中心化的管理模式。

**Module Federation shared 方案的优势**：
- 每个应用只需在自己的构建配置中声明 `shared` 和版本要求。
- **去中心化管理**：最大程度保留各个团队的自主权。
- **自动协商**：基于 SemVer 规范在运行时自动协商。
- **健壮的回退机制**：即使出现不兼容，也有智能回退机制和清晰警告，保证系统健壮性。

**核心差异对比表**：

| 维度 | 传统 external 方案 | Module Federation shared 方案 |
| :--- | :--- | :--- |
| **版本控制** | 全局统一，所有应用被动接收 | 各应用独立，更加灵活 |
| **版本协商** | 完全不支持 | 运行时自动协商（核心特性） |
| **SemVer 支持** | 完全无感 | 完全基于 SemVer 规范工作 |
| **升级影响范围** | 牵一发而动全身 | 兼容范围内升级几乎无感知 |
| **回退机制** | CDN 失效或版本错误即崩溃 | 提供自动降级加载自身依赖的能力，更健壮 |

## shared 与 bundle splitting 的区别 *Content-[14:37]

这两个概念解决的是不同维度的优化策略，切勿混淆：

- **Bundle Splitting（代码分割）**：
  - **作用域**：单一应用内部。
  - **实现方式**：通常通过 Webpack 的 `splitChunks` 配置，将 `node_modules` 中的公共库抽离成单独的 chunk，或按路由拆分业务代码。
  - **目标**：将单体庞大的应用拆分成多个小代码块，实现按需加载。

- **Module Federation shared**：
  - **作用域**：跨越多个独立应用之间。
  - **目标**：让多个独立的微前端应用能够同时共享同一个依赖实例，避免在应用之间重复加载公共资源，并通过运行时动态协商来管理版本。
  - **区别**：这是静态编译的 bundle splitting 策略无法做到的跨应用依赖共享。

## 课程总结 *Content-[15:47]

1\. **理解 shared 的本质**：它不仅仅是一个打包配置项，其背后是一整套精密的、在运行时发生的依赖协商机制。
2\. **牢记四个关键参数**：
   - `singleton`：控制是否强制单例（React/Vue 等框架必须开启）。
   - `requiredVersion`：定义版本范围。
   - `strictVersion`：控制版本匹配的严格程度。
   - `eager`：决定是同步还是异步加载。
3\. **掌握版本协商流程**：Host 注册依赖到共享空间 -> Remote 加载时查询和匹配 -> 智能决定是复用版本还是降级。
4\. **明确核心优势**：相比 external 等传统方案，`shared` 采用去中心化的管理模式，赋予各业务团队更高的自主权，同时通过自动协商保证了应用的整体性能和健壮性。
