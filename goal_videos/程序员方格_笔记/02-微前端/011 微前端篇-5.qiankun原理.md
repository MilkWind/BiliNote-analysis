## qiankun 整体定位与核心设计理念 *Content-[00:01]

在前面深入拆解了 single-spa 的核心原理、应用方式以及实际使用中遇到的痛点（如接入成本、样式隔离、JS 沙箱等）之后，本节将聚焦于一个更加完善的工程化方案——**qiankun**，以解决 single-spa 的核心痛点。

### 整体定位
qiankun 的核心定位是：**以最少的成本，将一个已有的多 SPA（单页应用）系统升级成可维护的微前端架构**。

### 核心设计理念
为了实现上述目标，qiankun 沉淀了以下四个核心设计理念：

1\. **约定优于配置**：直接使用 single-spa 需要手动配置大量底层细节（如子应用的打包格式）。qiankun 提供了一套完整的标准约定，包括统一的应用注册格式和入口规范。开发者只需遵守规范，即可省去繁琐的配置工作，使接入更简单且不易出错。
2\. **封装底层实现**：qiankun 的内核其实是 single-spa，但它并未将 single-spa 的复杂性暴露给用户，而是将其封装，提供了一套更友好、更上层的 API。这意味着开发者甚至不需要深入理解 single-spa，直接使用 qiankun 的能力即可配置微前端框架。
3\. **增加工程能力**：这是 qiankun 最核心的价值。它在 single-spa 的基础上增加了大量开箱即用的工程化能力，如 HTML Entry、JS/CSS 沙箱、应用间通信、资源预加载等。这些都是真实生产环境落地微前端所必需，而 single-spa 本身并不提供的能力。
4\. **对现有项目友好**：呼应“最少成本”的目标，qiankun 尽量不侵入子应用的开发模式。理想情况下，子应用甚至不需要知道自己正运行在微前端环境中，仍可按原有方式进行开发、构建和部署，这使得对旧项目进行渐进式改造成为可能。

综上所述，qiankun 是一个基于 single-spa，但为企业级应用场景提供了更完整、更成熟工程化解决方案的微前端框架。

## 核心特性一：HTML Entry 机制 *Content-[04:20]

HTML Entry 是 qiankun 增加的重要工程能力之一，大幅提升了开发体验。

### 核心痛点分析
在标准的独立前端项目中，最终打包产物通常是一个 `index.html` 文件以及被其引用的一堆 JS 和 CSS 文件。但在 single-spa 场景下，主应用加载子应用时存在以下限制：
- single-spa 要求子应用必须导出一个可直接执行的 JS bundle。
- 该 bundle 必须包含 `bootstrap`、`mount`、`unmount` 等生命周期函数。
- 子应用通常需要被打包成 UMD 或 SystemJS 格式。

这意味着，如果子应用原本产出的是标准 HTML，就必须改造其结构和配置。对每个要接入的子应用进行这种侵入式改造，成本非常高。

### qiankun 的解决方案：HTML Entry
qiankun 内置了 `import-html-entry` 库（即 HTML Entry Loader），完美解决了上述痛点。

**工作原理**：
- 注册微应用时，开发者**只需提供子应用的 HTML 入口 URL**，无需关心子应用打包成了什么格式。
- qiankun 在背后请求该入口 URL，获取 HTML 文件内容。
- 像浏览器一样解析 HTML，找到所有的 `<script>` 和 `<link>` 标签。
- 按顺序加载 JS 和 CSS 静态资源，并将 JS 脚本放入**沙箱环境**中执行，确保子应用的生命周期函数能够被正确捕获和管理。
- 智能处理 HTML 中静态资源（如图片、字体）的相对路径问题，确保资源正确加载。

**核心价值**：
抹平了主应用和子应用之间的集成障碍。主应用只需通过 URL 统一管理所有子应用，而子应用可以保持最常规、最标准的开发和构建模式，几乎不需要做任何侵入式改造，极大降低了微前端的接入成本。

### 代码配置对比
- **single-spa**：在 root 文件中需要引入一个静态 JS 文件，该 JS 文件内部暴露 `bootstrap`、`mount`、`unmount` 三个生命周期。
- **qiankun**：在主应用配置文件中直接配置子应用的 HTML 入口 URL。`import-html-entry` 会自动解析 HTML 内容，提取 JS 和 CSS 资源，并为后续工作做好准备。

## 核心特性二：沙箱隔离机制与痛点分析 *Content-[10:21]

通过 HTML Entry 将子应用加载进来后，会引出下一个关键问题：**环境隔离**（即沙箱机制）。在 single-spa 中，如果没有沙箱隔离，会面临以下严重的痛点：

### 无沙箱隔离的具体痛点
1\. **全局变量污染**：所有子应用都运行在同一个 `window` 全局环境上。如果应用 A 定义了一个全局变量，应用 B 又定义了同名变量并覆盖了它，应用 A 的状态就会被破坏。
2\. **版本冲突**：不同子应用可能依赖同一个第三方库的不同版本（例如应用 A 依赖 1.0 版本，应用 B 依赖 2.0 版本）。如果它们都向全局注册了同名的方法或对象，会导致无法预料的后果。各种 Polyfill 的冲突也是同样的道理。
3\. **CSS 全局污染**：如果应用 A 和应用 B 存在同名的 CSS 样式，后加载的样式会覆盖先加载的样式，导致页面样式错乱。
4\. **内存泄漏**：如果子应用在 `mount` 时添加了全局事件监听器或启动了 `setInterval` 定时器，但在 `unmount` 时忘记清理，即使应用已经退出，这些监听和定时器仍会在后台持续运行。这不仅会持续消耗内存，甚至会在不该响应的时候触发诡异的逻辑。

### qiankun 的解决方案
为了解决上述全局污染、版本冲突、CSS 覆盖和内存泄漏等问题，qiankun 提供了一套完整的**沙箱隔离方案**（包含 JS 沙箱和 CSS 沙箱），确保各个子应用在独立、安全的环境中运行。
