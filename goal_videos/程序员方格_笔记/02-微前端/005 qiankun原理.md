## qiankun 的整体定位与核心设计理念 *Content-[01:24]

qiankun 的整体定位非常精准：**以最少成本将一个已有的多 SPA（单页应用）系统，升级成可维护的微前端架构**。为了实现这一目标，qiankun 沉淀了以下四个核心设计理念：

1\. **约定优于配置**
如果直接使用 single-spa，许多底层细节（如子应用的打包格式）都需要开发者自行配置。而 qiankun 提供了一套完整的标准约定，例如统一的应用注册格式和入口规范。开发者只需遵守这些规范，就能省去大量繁琐的配置工作，使接入过程更简单且不易出错。

2\. **封装底层实现**
qiankun 的内核依然是 single-spa，但它并没有将 single-spa 的复杂性和底层细节暴露给用户，而是将其封装起来，提供了一套更加友好、上层的 API。这意味着开发者甚至不需要深入理解 single-spa，直接使用 qiankun 的能力就能配置出一个微前端框架。

3\. **增加工程能力**
这是 qiankun 最核心的价值所在。它在 single-spa 的基础上增加了大量开箱即用的工程化能力，例如 HTML Entry、JS/CSS 沙箱、应用间通信、资源预加载等。这些都是真实生产环境中落地微前端所必需的能力，而 single-spa 本身并不提供这些功能。

4\. **对现有项目友好**
这呼应了“最少成本”的设计目标。qiankun 尽量不侵入子应用的开发模式。在理想情况下，一个子应用甚至不需要知道自己正在微前端框架中运行，它仍然可以按照原有的方式进行开发、构建和部署。这使得对旧项目进行渐进式改造成为可能。

综上所述，qiankun 是一个基于 single-spa，但为企业级应用场景提供了更完整、更成熟工程化解决方案的微前端框架。

## 核心特性一：HTML Entry (HTML 入口) *Content-[04:20]

HTML Entry 是 qiankun 提供的一个大幅提升开发体验的核心功能。要理解它的价值，首先需要明确它解决的核心痛点。

**single-spa 的痛点：**
在一个标准的前端项目中，打包产物通常是一个 `index.html` 文件以及被其引用的 JS 和 CSS 文件。在微前端场景下，主应用通常只知道子应用的入口地址，并不知道该 HTML 内部包含多少个 `<script>` 标签以及它们的加载顺序。
如果直接使用 single-spa，它要求子应用必须导出一个直接可执行的 JS bundle，并且该 bundle 中必须包含 `bootstrap`、`mount`、`unmount` 等生命周期函数。这意味着，如果子应用原本产出的是标准 HTML，就必须改造其构建配置（例如打包成 UMD 或 SystemJS 格式）。这种侵入式改造对每一个接入的子应用来说，成本都非常高。

**qiankun 的解决方案：**
qiankun 内置了一个名为 `import-html-entry` 的库（即 HTML Entry Loader）。其核心作用和工作流程如下：
- **极简接入**：注册微应用时，开发者无需关心子应用打包成了什么格式，只需提供其 HTML 入口 URL 即可。
- **自动解析与加载**：qiankun 会在背后请求该入口 URL 获取 HTML 内容，像浏览器一样解析 HTML，找到所有的 `<script>` 和 `<link>` 标签。
- **按序执行与沙箱隔离**：按顺序加载 JS 和 CSS 静态资源，并将 JS 脚本放入沙箱环境中执行，从而确保子应用的生命周期函数能够被正确捕获和管理。
- **路径处理**：智能处理 HTML 中静态资源的相对路径问题，确保图片、字体等资源能够正确加载。

**核心价值：**
HTML Entry 抹平了主应用和子应用之间的集成障碍。主应用只需通过 URL 统一管理所有子应用，而子应用可以保持最常规、最标准的开发和构建模式，几乎不需要做任何侵入式改造，极大地降低了微前端的接入成本。

**代码配置对比：**
- **single-spa**：需要在 root 文件中引入一个静态 JS 文件，该 JS 文件负责暴露子应用的 `bootstrap`、`mount` 和 `unmount` 三个生命周期。
- **qiankun**：在主应用的配置文件中直接配置子应用的 HTML 入口 URL。`import-html-entry` 会自动解析 HTML 内容，提取 JS 和 CSS 资源，并将其放入框架对应位置为后续工作做准备。

## 核心特性二：沙箱隔离与环境隔离 *Content-[10:13]

通过 HTML Entry 将子应用加载进来后，会引出下一个关键问题：**环境隔离（沙箱）**。如果没有沙箱机制，多个子应用共享运行环境会导致以下严重问题：

1\. **全局变量污染**
所有子应用都运行在同一个 `window` 环境下。如果应用 A 定义了一个全局变量，随后应用 B 又定义了同名的全局变量并覆盖了 A 的值，就会导致应用 A 的状态被破坏。

2\. **版本冲突与 Polyfill 冲突**
如果应用 A 依赖某个库的 1.0 版本，而应用 B 依赖同一个库的 2.0 版本，且它们都向全局注册了同名的方法或对象，就会引发无法预料的后果。各种 Polyfill 的冲突也是同样的道理。

3\. **CSS 全局污染**
如果应用 A 和应用 B 存在同名的 CSS 样式类，后加载的样式会覆盖先加载的样式，直接导致页面样式错乱。

4\. **内存泄漏**
如果一个子应用在 `mount`（挂载）时添加了一个全局事件监听器，或者启动了一个 `setInterval` 定时器，但在 `unmount`（卸载）时忘记清理这些资源。那么即使该应用已经退出，这些监听器和定时器依然会在后台持续运行，不仅消耗内存，还可能在不应响应的时候触发诡异的逻辑错误。

为了解决上述环境隔离带来的种种问题，qiankun 提供了一套完整的沙箱隔离方案（包含 JS 沙箱和 CSS 沙箱），以确保各个子应用之间的互不干扰。
