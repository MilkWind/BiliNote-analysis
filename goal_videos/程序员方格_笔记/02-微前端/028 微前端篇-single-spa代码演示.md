## 项目结构与主应用配置 *Content-[00:00]

在 single-spa 的真实示例代码中，项目主要包含三个核心目录：`root`（主应用）、`app1` 和 `app2`（子应用）。

### 主应用（root）配置
- **基础结构**：`root` 目录下包含一个最简单的 `index.html`，其中定义了 `app1` 和 `app2` 两个 `div` 容器，专门用于挂载对应的子应用。
- **应用注册**：在 `root-config` 文件中，通过 `registerApplication` 方法将子应用注册到 single-spa 主应用中。
- **核心配置项**：
  1\. **name**：代表该 app 的唯一名称。
  2\. **app**：指定要加载的 app，通常通过动态 `import()` 方法将资源加载到项目中。
  3\. **activeWhen**：定义激活规则。示例中使用路由匹配方法，当路由匹配到 `#/app1` 时加载 app1 资源，匹配到 `#/app2` 时加载 app2 资源。
- **启动应用**：完成所有注册配置后，调用 `start()` 方法正式启动主应用。

### 子应用（app1 / app2）配置
子应用需要导入并导出其最核心的生命周期钩子方法，主要包括：
- `bootstrap`
- `mount`
- `unmount`

导出这些方法后，主应用即可通过引入对应的 JS 文件完成子应用的加载与生命周期管理。

## 运行效果与生命周期机制 *Content-[02:01]

通过实际运行项目，可以清晰地观察到 single-spa 的路由切换与生命周期执行机制。

### 路由切换与渲染
- 访问 `#/app1` 路由时，app1 的内容被加载并渲染。
- 切换路由至 `#/app2` 时，app1 被卸载，同时 app2 被加载并渲染。

### 生命周期打印分析
通过控制台打印，可以验证生命周期钩子的执行顺序：
1. **首次加载 app1**：执行 app1 的 `bootstrap`（初始化动作） -> 执行 `mount`（渲染 app1）。
2. **切换至 app2**：执行 app1 的 `unmount`（卸载 app1） -> 执行 app2 的 `bootstrap`（首次加载必须经历初始化） -> 执行 app2 的 `mount`。
3. **再次切换回 app1**：执行 app2 的 `unmount` -> 执行 app1 的 `mount`。
   - **核心特性**：此时 app1 **不会**再次执行 `bootstrap`。因为 `bootstrap` 在整个页面的生命周期中**只会执行一次**，仅代表初始化过程。后续切换只会不断循环执行 `mount` 和 `unmount`。

## activeWhen 配置与多应用同时激活 *Content-[04:14]

single-spa 的 `activeWhen` 配置不仅支持路由字符串匹配，还支持函数返回布尔值，这赋予了它同时激活多个应用的能力。

### 演示操作
- 将 `activeWhen` 的配置从路由匹配字符串修改为一个直接返回 `true` 的函数。
- 刷新页面后，控制台未报错，app1 和 app2 被同时挂载到了各自对应的容器中。

### 核心结论
- single-spa 支持**同时加载和激活多个应用**。
- 即使配置了多个 app 同时激活，它们之间也是互相不冲突的，能够稳定共存。

## 主应用向子应用传递数据 *Content-[06:23]

在微前端架构中，主应用与子应用之间的数据通信至关重要。single-spa 提供了通过 `customProps` 传递数据的机制。

### 传递数据（主应用）
- 在 `root-config` 文件中，注册应用时可以配置 `customProps` 属性。
- 在该属性中定义需要传递给子应用的具体状态或变量（例如传递一个名为 `globalApp1` 的变量）。

### 接收数据（子应用）
- 子应用的每一个生命周期方法（`bootstrap`、`mount`、`unmount`）都可以接收一个 `props` 参数。
- 在子应用内部，直接通过打印或访问 `props` 对象，即可获取到主应用通过 `customProps` 传递过来的数据（如 `globalApp1`）。

## single-spa 的缺陷：JS 与 CSS 隔离问题 *Content-[08:33]

尽管 single-spa 是一个优秀的微前端加载框架，但它存在一个明显的缺陷：**没有做严格的隔离策略**（包括 JS 隔离和 CSS 隔离）。这也是早期微前端未能大力推广的具体痛点之一。

### JS 隔离缺陷
- **现象**：在 app1 中设置一个全局变量（如 `window.globalVar`），在 app2 中同样可以获取到该变量。
- **隐患**：如果两个子项目使用了同名的全局变量，会导致逻辑冲突，极易引发难以排查的 Bug。

### CSS 隔离缺陷
- **现象**：在 app1 中为 `h2` 标签添加样式设置为红色，切换到 app2 后，app2 中的 `h2` 标签也变成了红色。
- **隐患**：样式发生了全局污染，子应用之间的 CSS 样式互相影响，无法做到独立隔离。

### 总结
JS 和 CSS 隔离的缺失是 single-spa 非常严重的缺陷。为了解决这些痛点，后续诞生了如 qiankun（乾坤）等更完善的微前端框架，它们在 single-spa 的基础上补齐了沙箱隔离和样式隔离能力。
