## 微前端概述与单体应用的困境 *Content-[00:00]

微前端是当前前端领域非常重要且越来越普遍的架构模式，是构建可扩展、可维护的大型前端系统的一种现代化解决方案。在深入微前端之前，需要先了解传统单体应用所面临的困境：

- **代码仓库庞大复杂**：随着业务快速迭代和功能叠加，代码库变得极其复杂。新成员加入团队可能需要数周甚至数月才能了解整个项目，维护成本极高。
- **模块紧密耦合缺乏边界**：在单体应用中，微小的改动（如修改公共组件或全局工具函数）可能引发“蝴蝶效应”，在其他不起眼的角落产生意想不到的 bug，导致发布新版本充满风险。
- **技术栈升级困难**：例如将一个使用了 5 年的 Angular 项目升级为 Vue 或 React，几乎等同于彻底重写，这种颠覆式重构的风险和成本是企业难以承受的。
- **多团队协作效率低下**：多个团队在同一代码库协作时，共用同一套构建流程和发布节奏。一个团队因 bug 延期会导致其他团队被迫等待；此外，频繁的代码合并冲突和长达十几二十分钟的打包时间也会严重拖累团队效率。

## 微前端的定义与核心目标 *Content-[03:54]

为了解决上述维护性、安全性、技术迭代和团队协作上的痛点，微前端架构应运而生。

- **核心概念**：不再将所有功能塞进一个庞大笨重的前端应用里，而是将其拆分成若干个更小的“微应用”。
- **微应用特点**：各个微应用各自独立开发、独立上线、独立运行，最后由“主应用”将它们有序地整合在一起，形成一个连贯统一的整体。
- **最终目标**：让多个独立的 Web 应用能够和谐地在同一个页面运行，同时保证它们之间有非常清晰的边界，做到互不干扰。
- **核心技术挑战**：基于上述目标，同时实现“聚合”与“隔离”是所有微前端框架共同需要解决的核心技术问题。

## 微前端的早期探索：iframe 与 SSI *Content-[05:11]

在“微前端”术语被正式提出之前，开发者已经在使用一些现有技术来模拟这种思想：

- **iframe**：
  - **优点**：提供浏览器原生、最彻底的运行时隔离。JS 变量、全局变量、CSS 等一切都被隔离在独立的 iframe 中，做到绝对互不干扰、互不污染。
  - **缺点**：
    - 通信困难：只能依赖 `postMessage` 等 API 实现应用间通信，实现繁琐。
    - 加载性能差：会阻塞主页面的 `onload` 事件。
    - UI 集成体验糟糕：弹窗会被 iframe 边界截断，路由和浏览器历史管理复杂。
- **SSI (Server Side Includes)**：
  - 允许在 Web 服务器将公共页面片段返回给浏览器之前进行拼接。
- **总结**：这些方案虽然体现了分离与聚合的思想，但难以适应现代单页应用（SPA）的复杂场景，无法解决现代前端的工程化问题。

## single-spa：奠定现代微前端基础 *Content-[07:40]

经历了 iframe 的早期探索后，社区迎来了第一个里程碑式的框架——**single-spa**，它真正奠定了现代微前端框架的基础。

- **设计哲学**：不追求大而全，聚焦解决最核心的问题——微应用调度。
- **核心贡献**：定义了一套标准化的生命周期协议。
  - 当 URL 发生变化时，single-spa 像应用路由器一样匹配需要激活的微应用。
  - 首次加载时执行 `bootstrap` 钩子，用于加载脚本和资源。
  - 加载完成后执行 `mount` 钩子，将应用渲染到页面指定的 DOM 节点上。
  - 导航离开、当前应用不再需要显示时，执行 `unmount` 钩子，完成卸载工作。
- **优势**：实现了技术栈无关。主应用无需关心微应用是 React、Vue 还是 Angular，只需在正确的时间调用正确的钩子。
- **缺陷**：框架非常轻量，仅提供调度，不提供任何 JS 和 CSS 的隔离方案。如果两个微应用定义了相同的全局变量或 CSS 类名，就会发生冲突，导致落地门槛极高。

## 乾坤（qiankun）：生产级微前端解决方案 *Content-[10:36]

为了解决 single-spa 留下的隔离痛点，阿里巴巴于 2019 年推出了**乾坤（qiankun）**，目标是成为生产级的微前端解决方案。

- **定位**：并非取代 single-spa，而是基于其进行二次封装，内部依然使用 single-spa 的应用调度和生命周期管理能力。
- **核心贡献**：提供开箱即用的 JS 沙箱和 CSS 隔离方案。
  - **JS 沙箱**：基于 `Proxy` API 实现。微应用运行时，为其创建一个代理的 `window` 对象，拦截微应用对 `window` 的所有操作，从而防止污染真实的全局 `window`。
  - **CSS 隔离**：自动处理微应用的样式表，为所有 CSS 规则添加唯一的属性选择器，保证样式只在自身应用内生效；同时也提供 Shadow DOM 方案。
- **优势**：内置完整的隔离机制，开发者无需手动处理环境污染问题，极大降低了微前端的上手和落地门槛，迅速成为国内最受欢迎的微前端框架之一。

## Webpack 5 模块联邦：依赖共享与去中心化 *Content-[12:54]

2020 年，Webpack 5 发布了一个颠覆性的功能——**模块联邦（Module Federation）**。它本身不是框架，而是构建工具内置的特性，提供了与沙箱隔离完全不同的思路。

- **核心理念**：沙箱强调“隔离”，而模块联邦强调“共享”。允许 JS 应用在运行时动态加载另一个独立部署应用暴露的远程模块。
- **核心优势**：
  - **依赖共享**：如果主应用和微应用依赖同一个库的同一个版本（如 React），运行时该库只会被加载一次并共享给所有应用，从根本上避免重复打包，极大优化性能（无需像乾坤那样通过 `externals` 手动处理）。
  - **开发体验极佳**：消费远程微应用的代码本质上就像 `import` 一个 NPM 包，模糊了远程应用和本地模块的界限。
  - **去中心化**：不再严格区分主应用和微应用，任何应用既可以是消费者，也可以是提供者。
- **代价**：强绑定 Webpack 5 生态，需要对应用进行一系列改造，且配置相对复杂。

## 无界（wujie）：iframe 与 Web Component 的结合 *Content-[15:37]

乾坤的 `Proxy` 沙箱在极少数情况下存在沙箱逃逸风险及性能损耗，而模块联邦对 Webpack 版本有强绑定。为此，腾讯在 2021 年之后推出了**无界（wujie）** 框架。

- **架构设计**：结合 iframe 和 JS 沙箱的优点，通过 Web Component 容器和 iframe 沙箱实现核心逻辑。
- **核心理念**：让隔离回归 iframe（提供最安全、彻底的天然隔离），但通过对 iframe 进行大量“魔改”来解决原生 iframe 的所有痛点。
  - 重写 iframe 的路由和通信机制，使应用之间的交互和路由跳转变得如乾坤般丝滑。
  - 通过预加载等机制解决 iframe 加载慢的问题。
- **优势**：追求极致的开箱即用，开发者几乎不需要做额外配置即可将现有应用快速接入，在隔离性、性能和开发者体验之间找到了极佳的平衡点。

## 如何系统性拆解微前端框架 *Content-[18:14]

学习一个新的微前端框架时，仅看原理和文档是不够的，必须带着问题从以下四个核心维度进行系统性剖析：

1\. **隔离机制**
- 搞清楚框架如何保证微应用之间互不干扰。
- JS 隔离：是像乾坤一样基于 `Proxy` 实现运行时沙箱，还是像无界一样使用 iframe？
- CSS 隔离：选用的是 Shadow DOM、动态修改 CSS 选择器，还是 iframe 天然隔离？
- 理解隔离原理有助于预判框架可能存在的性能问题和边界问题。

2\. **核心运行机制**
- 主应用如何调度子应用？
- 通过什么方式获取子应用的 HTML、JS 和 CSS 资源，并如何解析和执行它们？
- 定义的生命周期在什么时期被触发？URL 改变时，内部的路由匹配机制是怎样的？

3\. **通信体系**
- 隔离带来了稳定性，但也给应用间的通信交互带来挑战。
- 了解官方推荐的通信方案（如乾坤提供的 `initGlobalState` 全局状态方案，或原生浏览器事件通信）。
- 探究这些通信方式是如何在隔离环境下正常工作的。

4\. **依赖复用与工程化**
- 框架如何处理 React、Vue 等公共依赖以优化性能？是使用模块联邦原生的共享，还是借助 `import map` 或 Webpack 的 `externals` 配置？
- 是否提供配套的脚手架、CLI 工具来简化开发和调试流程？工程化支持直接决定了开发体验和效率。

## AI 总结 *Content-[22:33]

本节课程系统梳理了微前端架构的演进历程与核心原理。首先从单体应用面临的代码耦合、升级困难、协作效率低等痛点出发，引出了微前端“聚合与隔离”的核心目标。随后，详细回顾了微前端技术的发展史：从早期的 iframe 与 SSI，到奠定调度基础的 single-spa，再到提供开箱即用隔离方案的乾坤（qiankun），以及主打依赖共享的 Webpack 5 模块联邦，最后介绍了结合 iframe 与 Web Component 优势、追求极致开箱即用的无界（wujie）。最后，课程总结了系统性拆解微前端框架的四个核心维度（隔离机制、运行机制、通信体系、依赖复用），为开发者在技术选型、源码阅读及大厂面试中提供了清晰的方法论与实战指导。
