## 引言与背景介绍 *Content-[00:01]
在微前端领域，我们已经探讨过乾坤（qiankun）的核心机制，包括其路由接管、应用加载以及通过沙箱机制确保子应用隔离的原理。接下来，我们将深入分析另一个经典的微前端框架——无界（wujie）。
- **背景**：无界是由腾讯团队提供的微前端框架，曾在业内较为流行，但近两年已停止频繁更新，表明其在工程实践中遇到了一些瓶颈。
- **学习目标**：
  1\. **核心技术**：深入理解无界的双沙箱原理。
  2\. **工程实践**：客观分析其在实际应用中做出的权衡、取舍以及遇到的具体问题。

## 沙箱方案对比：Proxy vs iframe *Content-[01:27]
在深入无界之前，对比两种主流沙箱方案有助于理解其设计初衷。

### 1\. Proxy 沙箱（以乾坤为代表）
- **核心思路**：在同一个 JavaScript 线程中，通过 Proxy 包装主应用的 window 对象，为每个子应用创建一个 fake window。子应用对全局变量的读写都会被 Proxy 拦截，实现逻辑隔离。
- **局限性**：
  - **线程阻塞**：所有子应用代码运行在同一个 JS 主线程，共享事件循环。若某子应用执行高计算量任务或陷入死循环，会导致整个应用卡死。
  - **模拟不完美**：用 Proxy 模拟完整的 window 对象极其复杂，很多浏览器原生的深层能力难以 100% 完美模拟。

### 2\. iframe 沙箱（浏览器原生方案）
- **核心思路**：提供物理隔离，天然拥有独立的 window、location、history 对象，甚至独立的原型链（如 `Array.prototype`）、定时器、模块缓存。支持独立的 CSP（内容安全策略）和同源策略。
- **局限性（体验割裂）**：
  - 弹窗范围无法超出 iframe 边界。
  - 主应用的遮罩层无法覆盖 iframe 内容。
  - 主子应用的滚动条相互独立。
  - 路由同步困难。

## 无界的核心设计思路 *Content-[04:26]
无界旨在结合上述两种方案的优点，其核心思路可以概括为：**用浏览器原生的能力做物理隔离，再用代理和桥接做体验缝合**。

- **物理隔离层**：
  - **JS 沙箱**：选用 iframe，让子应用脚本运行在独立、受保护的环境中，从根本上解决 JS 线程互相阻塞的问题。
  - **样式沙箱**：采用 Web Components 技术栈中的 Shadow DOM。子应用的 DOM 结构渲染在独立的 Shadow Root 中，确保 CSS 样式不会泄露污染主应用，主应用样式也不影响子应用。
- **体验缝合层**：
  - 通过一系列 Proxy 代理，在运行子应用脚本的 iframe 与渲染主应用文档流的 Shadow DOM 之间建立 Bridge（通信机制）。
  - 成功解决了传统 iframe 在 UI 交互和路由同步方面的痛点，实现体验统一。

## 深入解析：为什么选择 iframe 作为 JS 沙箱 *Content-[06:29]
无论 Proxy 模拟的 fake window 多么精巧，都无法完全替代 iframe 提供的浏览器原生保障。iframe 作为 JS 沙箱具有以下显著优势：
1\. **独立的作用域**：每个 iframe 拥有独立的 window、location、history 对象，子应用可不受约束地使用全局 API，避免冲突。
2\. **隔离的原型链**：若子应用依赖旧版库修改了 `Array.prototype`，该修改仅在 iframe 内部生效，不会污染外部环境。
3\. **独立的定时器**：`setTimeout` 和 `setInterval` 挂载在独立的 window 上，保证时间相关逻辑的准确性。
4\. **隔离的模块解析和缓存**：使用 ES Module 时，每个 iframe 维护独立的模块缓存。即使主、子应用加载同一库的不同版本，实例也不会冲突。
5\. **安全边界**：可为每个 iframe 设置独立的 CSP，精细化控制资源加载和脚本执行；跨域时浏览器的同源策略也会提供额外安全保障。

## 无界的工作流程与三大核心代理 *Content-[09:24]
无界的整体工作流程可分为三个主要阶段：

### 阶段一：创建沙箱环境
- 创建一个**与主应用同域**的 iframe（后续通信和代理的基础）。
- 在主应用 DOM 中创建自定义 Web Component（如 `<wujie-app>`），并在其内部创建 Shadow DOM 作为 UI 渲染容器。
- 准备一系列 Proxy 代理对象，用于 iframe 内部与主应用的交互。

### 阶段二：加载和解析子应用资源
- 通过 fetch API 获取子应用入口 HTML 文件。
- **资源分类与归位**：
  - 提取所有 `<script>` 标签内容，注入到 iframe 中（JS 归 JS 沙箱管）。
  - 提取 `<body>` 标签的所有 DOM 节点，渲染到 Shadow DOM 内部。
  - 提取 `<style>` 和 `<link>` 引用的 CSS，处理后注入到 Shadow DOM 中（UI 和样式归 Shadow DOM 管）。

### 阶段三：运行期的代理
子应用在 iframe 中运行后，其对核心 API 的调用会被预设的 Proxy 拦截并转发。无界最核心的三种代理如下：
1\. **document 代理**：实现体验缝合的关键。拦截 `document.querySelector`、`createElement` 等方法，将操作范围重定向到外部的 Shadow DOM 根节点，确保所有 DOM 操作都在 Shadow DOM 容器内进行。
2\. **window 代理**：
  - **数据通信**：控制子应用如何通过 props 注入的全局变量访问主应用。
  - **安全防护**：阻止子应用意外或恶意修改主应用的 window 对象，保障主应用稳定。
3\. **location 代理**：负责路由同步。捕获子应用内部路由变化（如 Vue Router/React Router 修改 URL），不改变 iframe 的 location，而是通知主应用更新地址栏真实 URL，实现主子应用联动，保证刷新和分享链接的体验一致性。

## 工程实践：CORS 跨域问题解析 *Content-[15:02]
初次使用无界的开发者常困惑于“为什么子应用必须配置跨域”。
- **根本原因**：在无界架构中，无论是加载子应用的 HTML/JS/CSS 资源，还是子应用运行时发起的 API 数据请求，**网络请求的发起者都是主应用**。
- **浏览器视角**：请求的 origin 是主应用。如果子应用服务器未在 HTTP 响应头中配置 `Access-Control-Allow-Origin`（即未配置 CORS），浏览器出于安全考虑会执行同源策略，拦截响应。
- **结论**：配置 CORS 并非无界框架本身的强制要求，而是其底层工作机制（主应用代为请求）与浏览器安全模型共同决定的。

## 主子应用通信机制 *Content-[17:33]
应用运行后，无界提供三种主要的主子应用通信机制：
1\. **props 注入（最推荐）**：
  - 类似 Vue/React 组件通信，主应用在 `<wujie-app>` 标签上向下传递数据或函数。
  - 子应用内部通过 `window.$wujie.props` 获取数据。
  - 遵循单向数据流，清晰可控。
2\. **window.parent**：
  - 因无界创建的 iframe 必须与主应用同域，浏览器允许 iframe 内部脚本通过 `window.parent` 直接访问主应用的 window 对象。
  - **注意**：这种方式非常直接，但会在主子应用间形成强耦合，需谨慎使用以防滥用。
3\. **Event Bus（事件总线）**：
  - 无界提供全局的 `bus` 对象，实现发布-订阅模式。
  - 适合没有直接父子关系的组件或应用间进行去中心化的通信。

## 无界的局限性与三大核心痛点 *Content-[20:04]
无界 GitHub 代码库近期更新缓慢，主要是因为“iframe + Shadow DOM + Proxy”的技术路线在当前浏览器能力边界内已被探索得足够深入。剩下的疑难杂症多源于浏览器底层的结构性限制，强行修复会引入更多复杂性。以下是三个典型痛点：

### 痛点一：ownerDocument 属性冲突
- **现象**：子应用 JS 在 iframe 中运行，通过 `document.createElement` 创建的元素，其 `ownerDocument` 天然指向 iframe 内部的 document，而非主应用的 document。
- **冲突场景**：
  - **若劫持为主应用 document**：Popper.js 等定位库在计算弹窗位置时，会基于主文档的滚动和视口计算，导致元素在 Shadow DOM 内部时弹窗位置严重偏移。
  - **若不劫持（保持 iframe document）**：老版本 React（17 之前）的事件系统依赖事件委托，将监听器统一绑定在 document 根节点。由于事件无法穿透 iframe 到达主应用的 document，会导致老版本 React 事件系统完全失效。
- **结论**：这是一个两难境地，无界无法用完美方案满足所有场景，只能做出妥协。

### 痛点二：创建同源空白 iframe 的难题
- **理想需求**：创建一个同源且干净的 iframe（类似 `about:blank`），以便无障碍进行通信和 DOM 代理。
- **浏览器限制**：若直接设置 `iframe.src = 'about:blank'`，浏览器会为其分配一个独立且不透明的 origin，导致其与父页面跨域，无法直接访问内部对象。
- **妥协方案**：在主应用下部署一个极简的静态文件（如 `blank.html`），将 iframe 的 src 指向该文件。
- **代价**：
  - 引入额外静态文件，增加部署和维护复杂度。
  - iframe 创建依赖网络请求，非纯粹的程序化同步创建，极端情况下可能引发加载/初始化顺序问题。
- **本质**：浏览器安全模型未提供程序化创建同源空白 iframe 的原生 API。

### 痛点三：割裂的 History 与状态管理
- **场景**：用户进入子应用 A，随后切换路由导致子应用 A 的 iframe 被销毁以节省内存。当用户点击回退时，URL 恢复，主应用重新创建 iframe 并从头加载子应用 A。
- **问题**：虽然页面内容正确，但子应用内部的所有中间状态（路由栈、组件本地状态、表单输入、滚动位置等）在 iframe 销毁时全部丢失。
- **为何难以完美修复**：
  - 完美恢复需要在 iframe 销毁前对整个子应用进行完整快照（序列化路由栈、组件状态、表单数据、网络缓存等），并在重新创建时注入。
  - 注入过程必须与子应用使用的框架（React/Vue/Angular）的生命周期完美对齐，为各种框架和场景做通用快照机制的复杂度极高，几乎不可能。
- **本质**：浏览器原生的 History API 只关心顶层 URL 字符串，与 iframe 的生命周期完全解耦。

## 全面评估与总结 *Content-[36:12]
### 优点
- **务实且高性价比**：没有重新发明复杂的隔离机制，而是充分利用浏览器原生能力，从根本上避免了大规模使用 Proxy 模拟沙箱带来的性能瓶颈和兼容性风险。
- **下限高**：稳定性和隔离性有充分保障。

### 局限性
- **结构性限制**：本质是在浏览器现有的安全模型和事件模型上进行“缝合”，无法绕过底层限制。
- **缝合感**：如 `ownerDocument` 冲突、同源空白 iframe 创建、History 割裂等问题，都是缝合感的具体体现。
- **工程要求**：对于复杂的交互业务，需要团队建立额外的工程规范和约束来规避局限性。

### 结论
无界不是一个完美的银弹，但它是一个非常出色的、立足于现实的工程化解决方案。它从清晰的架构和对浏览器底层机制的深刻理解出发，在隔离性、稳定性和性能方面做出了合理的取舍。
