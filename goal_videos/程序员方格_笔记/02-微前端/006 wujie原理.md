## 1. 引言：从 qiankun 到 wujie *Content-[00:01]
在深入探讨 wujie（无界）之前，我们先简要回顾 qiankun（乾坤）的核心机制，包括其如何接管路由、完成应用加载，以及如何通过沙箱机制确保子应用间的相互隔离。
接下来，我们将聚焦于另一个经典的微前端框架——**wujie**。这是由腾讯团队提供的一个微前端框架，曾在之前非常流行，但近两年已停止更新。本节内容不仅会深入解析其核心技术实现（即“双沙箱”原理），还会站在客观角度分析其在工程实践中的权衡、取舍以及遇到的局限性，帮助大家建立对 wujie 更加立体和深入的认识。

## 2. 沙箱方案对比：Proxy 与 iframe *Content-[01:30]
为了理解 wujie 的设计初衷，我们需要对比两种主流的沙箱方案：

- **Proxy 沙箱（以 qiankun 为代表）**
  - **核心思路**：在同一个 JavaScript 线程中，通过 `Proxy` 包装主应用的 `window` 对象，为每个子应用创建一个 `fake window`。当子应用读写全局变量时，操作会被 `Proxy` 拦截，实现逻辑隔离。
  - **局限性**：所有子应用代码仍运行在同一个 JS 主线程，共享同一个事件循环。若某个子应用执行高计算量任务或陷入死循环，会导致整个应用卡死。此外，用 `Proxy` 完美模拟浏览器原生的深层 `window` 能力非常复杂，难以做到 100% 还原。

- **原生 iframe 沙箱**
  - **核心思路**：提供物理级别的隔离，天然拥有独立的 `window`、`location`、`history` 对象，甚至 `Array.prototype` 原型链、定时器（`setTimeout`）和模块缓存都是完全独立的。还可以设置独立的 CSP（内容安全策略），并受同源策略保护。
  - **局限性**：传统 iframe 在用户体验上存在严重割裂感。例如：子应用弹窗无法超出 iframe 边界；主应用遮罩无法覆盖 iframe 内容；主子应用滚动条相互独立；路由同步困难。

## 3. 无界的核心设计思路 *Content-[04:26]
针对上述两种方案的优缺点，wujie 的核心思路可以概括为：**用浏览器原生的能力做物理隔离，再用代理和桥接做体验缝合。**

- **物理隔离**：
  - **JS 隔离**：选用 `iframe` 作为 JS 沙箱，让子应用脚本运行在独立受保护的环境中，从根本上解决 JS 线程互相阻塞的问题。
  - **样式隔离**：采用 Web Component 技术栈中的 `shadow DOM`。子应用的 DOM 结构渲染在独立的 `shadow root` 中，确保 CSS 样式不会相互污染。
- **体验缝合**：
  - 通过一系列 `Proxy` 代理，在运行子应用的 `iframe` 与渲染主应用文档流中的 `shadow DOM` 之间建立通信桥梁（Bridge）。
  - 这种设计既保留了 `iframe` 强大的隔离能力和性能优势，又解决了传统 `iframe` 在 UI 交互和路由同步上的痛点。

## 4. 为什么选择 iframe 作为 JS 沙箱 *Content-[06:33]
无论 `Proxy` 模拟的 `fake window` 多么精巧，都无法完全替代 `iframe` 提供的浏览器原生保障。`iframe` 作为 JS 沙箱具有以下显著优势：

1. **独立的作用域**：每个 `iframe` 都有独立的 `window`、`location` 和 `history`，子应用可不受约束地使用全局 API，无需担心冲突。
2. **隔离的原型链**：若子应用依赖旧版库修改了 `Array.prototype`，在 `iframe` 中该修改仅在当前环境生效，不会污染外部。
3. **隔离的定时器**：每个子应用拥有独立的定时系统，保证时间相关逻辑的准确性。
4. **隔离的模块解析和缓存**：使用 ES Module 时，每个 `iframe` 维护独立的模块缓存。即使主子应用加载同一库的不同版本，实例也不会冲突。
5. **安全边界**：可为每个 `iframe` 设置独立的 CSP，精细化控制资源加载和脚本执行；跨域时同源策略也会提供额外安全保障。

## 5. 无界的工作流程与核心代理机制 *Content-[09:24]
wujie 的运行流程主要分为三个阶段：

### 5.1 创建沙箱环境
- 创建一个与主应用**同域**的 `iframe`（这是后续通信和代理的基础）。
- 在主应用 DOM 中创建自定义 Web Component（如 `<wujie-app>`），并在其内部创建一个 `shadow DOM` 作为子应用 UI 的渲染容器。
- 准备一系列 `Proxy` 代理对象，用于连接 `iframe` 内部与主应用。

### 5.2 加载和解析子应用资源
- 通过 `fetch API` 获取子应用的入口 HTML 文件。
- **资源分类与归位**：
  - 提取所有 `<script>` 标签内容，注入到 `iframe` 中（JS 归 JS 沙箱管）。
  - 提取 `<body>` 内的 DOM 节点，渲染到 `shadow DOM` 内部。
  - 提取 `<style>` 和 `<link>` 引用的 CSS，处理后注入到 `shadow DOM` 中（UI 和样式归 CSS 沙箱管）。

### 5.3 运行期代理
子应用在 `iframe` 中运行后，其对核心 API 的调用都会被预设的 `Proxy` 拦截并转发。wujie 最核心的三种代理包括：
- **document 代理**：体验缝合的关键。拦截 `document.querySelector` 或 `createElement` 等操作，将其重定向到外部的 `shadow DOM` 根节点，确保所有 DOM 操作都在 `shadow DOM` 容器内进行。
- **window 代理**：承担两个职责。一是作为数据通信通道（通过 `props` 注入全局变量）；二是作为安全防护工具，阻止子应用意外或恶意修改主应用的 `window` 对象。
- **location 代理**：专门负责路由同步。捕获子应用内部路由变化（如 Vue Router 或 React Router 修改 URL），不直接改变 `iframe.location`，而是通知主应用更新地址栏真实 URL，实现主子应用联动。

## 6. 跨域问题（CORS）解析 *Content-[15:02]
初次使用 wujie 的开发者常会困惑：为什么子应用必须配置跨域（CORS）？
- **根本原因**：在 wujie 架构中，无论是加载子应用的 HTML/JS/CSS 资源，还是子应用运行时发起的 API 请求，**网络请求的实际发起者都是主应用**。
- **浏览器安全模型**：从浏览器视角看，请求的 `origin` 是主应用域名。如果子应用服务器没有在 HTTP 响应头中配置 `Access-Control-Allow-Origin`，浏览器出于同源策略会拦截响应，导致主应用无法获取资源，子应用自然无法加载。
- 因此，配置 CORS 并非 wujie 框架本身的强制要求，而是其底层工作机制与浏览器安全模型共同决定的。

## 7. 主子应用通信机制 *Content-[17:36]
应用运行后，wujie 提供了三种主要的主子应用通信机制：

1. **props 注入（最推荐）**：
   - 类似 Vue/React 组件传参，主应用在 `<wujie-app>` 标签上向下传递数据或函数。
   - 子应用内部通过 `window.$wujie.props` 获取数据。遵循单向数据流，清晰可控。
2. **window.parent**：
   - 由于 wujie 创建的 `iframe` 与主应用同域，iframe 内部脚本可通过 `window.parent` 直接访问主应用的 `window` 对象。
   - **注意**：这种方式会导致主子应用强耦合，需谨慎使用以防滥用。
3. **Event Bus（事件总线）**：
   - wujie 提供全局的 `bus` 对象，实现发布-订阅模式。
   - 适合没有直接父子关系的组件或应用间的去中心化通信。

## 8. 无界面临的工程挑战与痛点 *Content-[20:04]
尽管 wujie 设计巧妙，但在工程实践中仍面临一些源于浏览器底层机制的结构性限制：

### 8.1 ownerDocument 属性冲突
- **现象**：在 `iframe` 中通过 `document.createElement` 创建的元素，其 `ownerDocument` 天然指向 `iframe` 内部的 `document`，而非主应用的 `document`。
- **痛点 1（定位库失效）**：如 `popper.js` 等定位库依赖 `ownerDocument` 获取全局视口和坐标系。若 wujie 强行劫持 `ownerDocument` 指向主应用，弹窗位置计算会基于主文档的滚动和视口，导致在 `shadow DOM` 内的弹窗位置严重偏移。
- **痛点 2（老版本 React 事件失效）**：React 17 之前的合成事件系统将监听器统一绑定在 `document` 根节点。在 `iframe` 沙箱中，事件冒泡到 `iframe` 的 `document` 就停止了，无法穿透到主应用。为了让老版本 React 正常工作，又必须让 `ownerDocument` 指向主应用或代理事件。
- **结论**：这是一个两难境地，wujie 无法用完美方案满足所有场景，只能做出妥协。

### 8.2 创建同源空白 iframe 的妥协
- **理想状态**：创建一个同源且干净的 `iframe`（类似 `about:blank`），以便无障碍进行通信和 DOM 代理。
- **浏览器限制**：直接设置 `iframe.src = 'about:blank'`，浏览器会为其分配一个独立且不透明的 `origin`，导致与父页面跨域，无法直接访问内部对象。
- **妥协方案**：在主应用下部署一个极简的静态文件（如 `blank.html`），将 `iframe` 的 `src` 指向它。
- **代价**：引入了额外的静态文件，增加了部署和维护复杂度；且 `iframe` 的创建依赖一次网络请求，而非纯粹的程序化同步创建，极端情况下可能引发加载顺序问题。

### 8.3 History API 与 iframe 生命周期割裂
- **现象**：当用户从子应用 A 切换到其他页面时，为节省内存，wujie 可能会销毁子应用 A 的 `iframe`。当用户点击浏览器“回退”按钮时，主应用路由监听到变化，会重新创建 `iframe` 并从头加载子应用 A。
- **痛点**：虽然页面内容恢复正确，但子应用内部的所有中间状态（如内部路由栈、组件本地状态、表单输入、滚动位置等）在 `iframe` 销毁时已全部丢失。
- **根本原因**：浏览器原生的 `history API` 和 `iframe` 生命周期是完全解耦的。`history` 只关心顶层 URL 字符串，完全不知道 `iframe` 内部发生的复杂状态变化。
- **为何难以修复**：要实现完美恢复，需要在 `iframe` 销毁前对整个子应用进行完整快照（序列化整个运行中的应用），并在重建时注入，且需与 Vue/React/Angular 等框架的生命周期完美对齐。这种通用的状态快照和恢复机制复杂度极高，几乎不可能完美实现。

## 9. 总结：客观评价无界框架 *Content-[36:12]
- **优点**：wujie 是一个非常务实且高性价比的方案。它没有重新发明复杂的隔离机制，而是利用原生 `iframe` 和 `shadow DOM` 实现物理级别的硬隔离。这从根本上避免了大规模使用 `Proxy` 模拟沙箱带来的性能瓶颈和兼容性风险，下限非常高，稳定性有保障。
- **局限性**：其本质是在浏览器现有的安全模型和事件模型上进行“缝合”，无法绕过底层的结构性限制。`ownerDocument` 冲突、同源空白 `iframe` 的创建妥协、以及 `history` 与 `iframe` 生命周期的割裂，都是这种缝合感的具体体现。
- **结论**：wujie 不是一个完美的银弹，但对于复杂交互业务，团队可以通过建立额外的工程规范和约束来规避局限性。它立足于现实，在隔离性、稳定性和性能方面做出了出色的取舍，是一个非常优秀的工程化解决方案样例。

## AI 总结
wujie（无界）微前端框架的核心创新在于采用“iframe + shadow DOM”实现物理级别的 JS 与样式双隔离，并通过 Proxy 代理机制进行体验缝合。这种设计有效解决了传统 Proxy 沙箱的性能瓶颈与隔离不彻底问题，提供了极高的稳定性和下限。然而，受限于浏览器底层的安全模型与事件机制，wujie 在工程实践中仍面临 ownerDocument 冲突、同源 iframe 创建妥协以及路由状态丢失等结构性痛点。总体而言，wujie 并非完美的银弹，但凭借其务实的设计与对浏览器底层机制的深刻理解，依然是一个极具价值且出色的微前端工程化解决方案。
